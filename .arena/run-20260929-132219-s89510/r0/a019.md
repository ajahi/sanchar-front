# Sanchar frontend: review and flow check

## The short answer

The flow you described is **not what the code does yet**. Four things stand out:

1. After Instagram login the user lands in the **inbox**, not the dashboard.
2. A logged-in tenant **cannot connect or reconnect Instagram or Facebook**. The Channels screen only handles WhatsApp.
3. The Channels screen **shows Facebook and Instagram as "connected" with fake data**, and its webhook "ping" always passes.
4. The **reply box can send a half-typed message to the wrong customer**.

The code compiles (`npx tsc --noEmit --incremental false` gave no errors). I read every file in the flow. I did not run the app against your backend, so anything that depends on the backend is marked **(backend)**.

## The flow as it actually runs

| Step | What happens | Where | Matches your intent? |
|---|---|---|---|
| 1. Visit any page, no cookie | Redirect to `/login`, query string kept | `middleware.ts:21` | Yes |
| 2. Click "Continue with Instagram" | Plain link to `/api/v1/social-accounts/instagram/login`, proxied to FastAPI | `login/page.tsx:188`, `middleware.ts:15-16` | Yes |
| 3. Instagram callback | Backend sets `ns_session` and redirects somewhere **(backend)**. Errors come back as `/login?ig_error=` and are shown | `login/page.tsx:20-26` | Unknown |
| 4. Landing | A user with a cookie who opens `/login` is sent to `/`, the **inbox**. Email login also goes to `/` | `middleware.ts:22`, `login/page.tsx:37` | **No** |
| 5. Dashboard | Only reachable by clicking DASHBOARD in the header | `Header.tsx:91-101` | **No** |
| 6. Conversations on the left | One flat list with ALL / IG / WA / FB filter buttons, not grouped per channel | `SidebarNav.tsx:318-363` | Roughly |
| 7. Click a conversation | Messages load for that thread and refresh when it changes | `App.tsx:87-96` | Yes, with bugs (see 7, 9) |

## Findings, most serious first

### 1. Login does not land on the dashboard
- `middleware.ts:22` and `app/login/page.tsx:37` both send the user to `/`, which is the inbox.
- The Instagram callback redirect is set in the backend and I cannot see it **(backend)**. If it also sends users to `/`, the middleware line does not matter for Instagram login.

**Change (frontend):**
```diff
--- middleware.ts
-  if (hasSession && isLogin) return NextResponse.redirect(new URL('/', req.url));
+  if (hasSession && isLogin) return NextResponse.redirect(new URL('/dashboard', req.url));
--- app/login/page.tsx
-      window.location.assign('/'); // full load so middleware sees the new cookie
+      window.location.assign('/dashboard'); // full load so middleware sees the new cookie
```
Also change the backend's post-login redirect to `/dashboard`.

I chose this small change over moving the inbox to `/inbox` and making `/` the dashboard. The bigger move is right when you build the public landing page for SEO (finding 13), but it touches every header link. Do it then.

### 2. Any backend hiccup logs the user out
- `getMyTenant()` throws for every non-OK response (`api.ts:25`). Both callers respond by calling `logout()` and going to `/login` (`App.tsx:61`, `PageHeader.tsx:232`).
- So a 500, a 502 while the backend restarts, or a slow proxy ends the session. During testing this will look like random logouts.
- If the backend is fully down, `logout()` itself throws. The `.catch(handleSignOut)` promise then rejects and the user stays on a half-loaded page.
- The 5-second conversation poll (`App.tsx:78`) only logs errors. A really expired session leaves a frozen inbox with no redirect.

**Change:** sign out only on a real 401.
```ts
// api.ts
export class HttpError extends Error {
  constructor(public status: number, message: string) { super(message); }
}
export async function getMyTenant(): Promise<Tenant> {
  const res = await fetch('/api/v1/tenants/me');
  if (!res.ok) throw new HttpError(res.status, 'Not authenticated');
  return res.json();
}
// App.tsx:61 and PageHeader.tsx:232
.catch((e) => { if (e?.status === 401) handleSignOut(); else console.error(e); })
```
Throw `HttpError` from `listConversations` too, and sign out on 401 inside the poll's `.catch`.

### 3. A logged-in tenant cannot link Instagram or Facebook
- `/login` redirects any user with a cookie away (`middleware.ts:22`), so the "Continue with Instagram" button is unreachable once you are in.
- The Channels modal has a real WhatsApp link form (`MetaSettingsModal.tsx:269-341`) but no Instagram or Facebook action at all.
- `ProfileModal.tsx:68` tells the user to "Log in with Instagram again to refresh". That is impossible without logging out first.
- Facebook has no connect path anywhere, yet the FB filter and cards exist.

**Change:** add a "Connect / reconnect Instagram" link in the Channels modal, `<a href={INSTAGRAM_LOGIN_URL}>`. Whether that call attaches the account to the current tenant or creates a new one depends on the backend **(backend)**. Hide the Facebook card until it has a connect flow.

### 4. Channels screen shows fake "connected" data
- `MetaSettingsModal.tsx:187` "LINKED & ACTIVE" and `:215` "VERIFIED" are always shown. The names and IDs come from `initialMetaStatus` in `mockData.ts:229-248` ("Himalayan Silk", `@himalayan_silk_np`), and `App.tsx:31` never updates them.
- The real profile is already available (`getInstagramProfiles`, used by `ProfileModal`). The Channels card ignores it.
- Callback URL `https://api.socialsync.np/v1/meta/webhook` and verify token `socialsync_meta_wh_sec_991823` (`:62`, `:401`) are invented. Your real webhook is `/api/v1/webhooks/...`. Someone who copies these into Meta will get a dead subscription.
- "PING WEBHOOKS" (`:105-112`) waits 800 ms and prints "HTTP 200 OK". It calls nothing.
- "Save Configuration" (`:114-117`) only changes a local name and saves nothing.
- `bName` is set once from the default business name, "Himalayan Silk & Handicrafts (काठमाडौँ)" (`App.tsx:25`), before the real name loads (`MetaSettingsModal.tsx:61`). Pressing Save without editing puts that fake name back in the header.
- `RightInspector.tsx:183-212` always shows all three channels as active with "Meta Webhooks 200 OK".

**Change:** drive the Instagram card from `getInstagramProfiles()`, show "NOT CONNECTED" when it returns an empty list, delete the fake callback, token and ping block, and hide the inspector stamp.

### 5. The reply box can send to the wrong person and loses text on failure
- `InboxFeed` is not keyed by thread (`App.tsx:389`), so `inputText` survives a thread switch. Type a reply, click another customer, press Enter: it goes to the new customer.
- `handleSend` clears the box before the request finishes (`InboxFeed.tsx:96-100`). If sending fails, the user sees a browser `alert` (`App.tsx:155`) and the text is gone. A likely cause is Meta's 24-hour reply window. Nothing in the UI shows that window; `InboxFeed.tsx:433` always says "Window: Active".

**Change:**
```diff
--- App.tsx
-            <InboxFeed
+            <InboxFeed
+              key={activeThread?.id}
--- InboxFeed.tsx
-  const handleSend = () => {
-    if (!inputText.trim()) return;
-    onSendMessage(inputText.trim(), 'human');
-    setInputText('');
-  };
+  const handleSend = async () => {
+    const text = inputText.trim();
+    if (!text) return;
+    if (await onSendMessage(text, 'human')) setInputText(''); // clear only on success
+  };
```
Make `handleSendMessage` return `true` on success and `false` on failure, and show the error in the pane instead of `alert()`.

### 6. Buttons that put fake text in front of real customers
- "AI DRAFT" calls `/api/v1/ai/reply`, which 404s today (`api.ts:41`). On failure it **fills the reply box with a canned Nepglish message** (`InboxFeed.tsx:120`). One click on SEND delivers it to a real customer.
- The four QUICK REPLIES (`:126-131`) include a made-up coupon (`VINTAGE10`), a made-up tracking link and a 10% discount approval. These are one click from a live send.

**Change:** on failure show an error and leave the box alone. Remove the quick replies, or load them from tenant data.

### 7. The message pane goes blank when the selected thread disappears
- The poll keeps any non-empty `activeThreadId` (`App.tsx:76`). If that id is not in the fresh list, `activeThread` falls back to `threads[0]` (`:102`), but messages are only fetched for the stale id (`:89-96`).
- Result: the first conversation shows with **no messages** until you click something. You can trigger it with "+ INBOUND", which invents `thread-<timestamp>` ids that the next poll wipes.

**Change:**
```diff
-          setActiveThreadId((id) => id || fresh[0]?.id || '');
+          setActiveThreadId((id) => (fresh.some((t) => t.id === id) ? id : fresh[0]?.id ?? ''));
```

### 8. "Take over as human" does nothing lasting
- `handleToggleTakeover` (`App.tsx:122-139`) only edits local state. The next poll (5 s) replaces it with the server's `mode` (`api.ts:102`). This needs a backend call **(backend)**.
- Also `api.ts:102` maps every mode except `'ai'` to `NEEDS_HUMAN`. A thread a human already handled, or one that is closed, shows the red "HUMAN ESCALATION REQUIRED" banner and is counted in the escalation number. The `status` field the backend sends is ignored (`api.ts:62`). Confirm the real `mode` and `status` values **(backend)**.
- Sending a human message does not switch the thread to manual, so the bot may keep replying **(backend)**.

### 9. Inbox display problems for real data
- **First run is confusing.** A tenant who has just logged in has zero conversations. The left side says "No threads match the selected filter" (`SidebarNav.tsx:392`) and the centre says "Select a conversation from the left feed" (`InboxFeed.tsx:87`). Add a real empty state ("No messages yet. Send a DM to your linked account") with a link to Channels.
- **Previews are empty.** Only the open thread has messages loaded, so every other card says "No messages yet" (`SidebarNav.tsx:398,437`). The list endpoint needs to return a last-message preview **(backend)**.
- **Fake confidence.** `CONF: 0.00` on every card (`SidebarNav.tsx:455`). AI messages show `CONFIDENCE: 0.00` and an empty `SOURCE:` (`InboxFeed.tsx:307-333`). Hide these when the value is missing. In `RightInspector.tsx:41,72` the intent and knowledge-base source are blank for real threads.
- **Wrong labels.** `system` messages become "Human Operator (Merchant)" (`api.ts:85`) with "OPERATOR OVERRIDE SENT VIA GRAPH API" (`InboxFeed.tsx:370`). AI messages are labelled "SocialSync AI" (`:316`).
- **Times.** `fmtTime` (`api.ts:80`) shows only HH:MM, so a message from 4 September looks like today. Show the date when it is not today. If the backend sends timestamps without a `Z` or offset, browsers read them as local time and the display will be shifted **(backend)**.
- **Not scrolled to the newest message.** The message pane never scrolls down (`InboxFeed.tsx:284`).
- **Grouping.** You asked for "listed as per social media". The current list is one mixed list with filters. If you want grouping, add a section header per channel.
- **Paging.** The list call has no limit or paging (`api.ts:106`). Check whether the backend caps it **(backend)**.

- It always prints WhatsApp, Instagram and Facebook rows (`dashboard/page.tsx:8-27`). A fresh Instagram-only tenant sees rows of zeros and no hint to connect anything. The empty `top_queries` message is fine.
- The escalation badge on the dashboard is the sum of 24-hour handover counts (`dashboard/page.tsx:41`). The inbox badge counts threads currently needing a human (`App.tsx:103`). Same badge, two meanings.

- Metric names ("New messages", "Messages handled", "Handover") cannot be checked against the backend **(backend)**.

### 12. Routing and proxy risks
- **Static files.** The matcher `'/((?!api|_next|favicon.ico).*)'` (`middleware.ts:27`) no longer skips paths with a dot (the `.bak` did). Logged-out visitors, including crawlers, are redirected to `/login` for `robots.txt`, `sitemap.xml`, images and `public/*`. Nothing breaks today because those files do not exist yet, but it will the day you add them. Use `'/((?!api|_next|.*\\..*).*)'`; `/api/v1/:path*` stays as the second entry.
- **Public routes.** Everything under `/api` skips the login check: `/api/health`, `/api/meta/*` and `/api/amit`.
- **Webhooks.** `/api/v1/webhooks/*` returns `NextResponse.next()` (`middleware.ts:11-13`). With no nginx in front, Next has no such route and answers 404. The comment says nginx handles this in production, but `docker-compose.yml` has no nginx. Meta's webhook only works if the proxy sits in front of this container, or Meta points at the backend directly.
- **`BACKEND_URL`.** Read with `process.env` in middleware. Check once inside the built container that it reaches the backend, because I only ran the code as source.
- **Session check.** The middleware only checks that the cookie exists, not that it is valid. Fine for now, but it makes finding 2 matter.
- **Cookie flags** (`Secure`, `SameSite`, `HttpOnly`) are set by the backend **(backend)**. The reply POSTs use cookie authentication only, so confirm `SameSite=Lax` or stricter.

### 13. SEO and Meta app review
- The whole app is `ssr:false` and login-gated. Only `/login` is indexable. That is fine today. For SEO later you need a public `/` and the inbox somewhere like `/inbox`.
- `app/layout.tsx` gives every page the same title. Add `metadataBase`, per-page titles, an Open Graph image (the Twitter card asks for a large image and has none), and `robots: noindex` on `/dashboard` and the inbox. `login/page.tsx` is a client component, so add a small server wrapper to export its metadata.
- The privacy policy and terms on the login page are plain `<span>`s (`login/page.tsx:246-248`). Meta requires a working privacy policy URL, and a data-deletion URL for Instagram and Facebook login.
- Login-page claims to remove before review: "FREE FOREVER" (`:92`), "GDPR / Nepal Telecomm Ready" (`:289`), "ESTD. 1932" (`:71`), "Meta Graph v21.0 Compliant".
- The two email/password labels have no `htmlFor` (`login/page.tsx:212,226`). Add ids so screen readers and tests can link them.
- `<html lang="en">` while the product is Nepali and English. Set `lang` per page when content is public.

### 14. Repo hygiene
- `conversation_example.json` holds real Instagram usernames and IDs of real people. Remove it from git if the repo is shared.
- `middleware.ts.bak` and `tsconfig.tsbuildinfo` are tracked. Remove them from git and add `*.tsbuildinfo` to `.gitignore`.
- `Dockerfile` runs as root. Add `USER node` before `CMD`.
