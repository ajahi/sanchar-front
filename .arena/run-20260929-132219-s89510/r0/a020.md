# Sanchar frontend: flow check and code review

Scope: `next-app` (Next 15 app router, React 19). I read every file in the flow, and `npx tsc --noEmit --incremental false` is clean, so nothing below is a type error. I did not run the app against your backend. Anything that depends on FastAPI is marked **[backend]**.

## Verdict

The pieces exist (Instagram login, session cookie, inbox with real conversations and messages, a dashboard, a WhatsApp linking modal). The flow you described breaks in four places:

1. Login does not end on the dashboard. It ends on the inbox.
2. When the backend is down or restarting, the app can get stuck in a redirect loop between `/` and `/login`.
3. The core feature, the auto-reply, is drawn wrongly. Every AI message shows `CONFIDENCE: 0.00` and an empty `SOURCE:`.
4. The Channels screen shows fake "connected" status and can overwrite the tenant's real business name with a mock name.

The dashboard itself is thin. It shows counts only, for a fixed 24 hours.

## One trace through the flow

This is a concrete run through the code, using the mock values that would appear. Say a tenant, Sita, owns `@himalayan_silk_np`.

| Step | What the code does | Reference |
|---|---|---|
| 1 | Opens `/`. She has no cookie, so the middleware sends her to `/login`. | `middleware.ts:21` |
| 2 | Clicks "Continue with Instagram". This is a plain `<a href="/api/v1/social-accounts/instagram/login">`. The middleware rewrites it to FastAPI, which redirects to instagram.com. | `login/page.tsx:145`, `middleware.ts:16` |
| 3 | Approves. The backend callback sets `ns_session` and redirects somewhere. **[backend]** | not in this repo |
| 4 | If it redirects to `/`, or to `/login` (the middleware then forwards to `/`, `middleware.ts:22`), she lands on `app/page.tsx`. That is the inbox, not the dashboard. | `app/page.tsx:8` |
| 5 | For a moment the header reads "Himalayan Silk & Handicrafts (काठमाडौँ)". That is hard-coded, and it stays until `/tenants/me` answers. | `App.tsx:25` |
| 6 | The left list fills every 5 s. Every card says `CONF: 0.00`, and every card except the open one says "No messages yet". | `SidebarNav.tsx:437,455` |
| 7 | She must find the small DASHBOARD pill to reach the metrics. There she sees `WhatsApp 0 / Instagram 12 / Facebook 0` for "Last 24 hours". | `Header.tsx:136`, `dashboard/page.tsx:67` |

Steps 4 to 7 are where the flow diverges from what you intended.

## Findings, ranked

### P0: blocks or breaks the flow

**1. Instagram login lands on the inbox, not the dashboard.**
- Evidence: `middleware.ts:22` and `login/page.tsx:37` both send to `/`. `/` is the inbox (`app/page.tsx`). The dashboard is only at `/dashboard`.
- Fix. Don't rely on the backend's redirect target. Make `/` the dashboard entry and move the inbox to `/inbox`:
  - Create `app/inbox/page.tsx` with the current contents of `app/page.tsx`.
  - Replace `app/page.tsx` with:
    ```tsx
    import { redirect } from 'next/navigation';
    export default function Home() { redirect('/dashboard'); }
    ```
  - `PageHeader.tsx:37` becomes `router.push(tab === 'inbox' ? '/inbox' : \`/inbox?tab=${tab}\`)`.
  - `PageHeader.tsx:40` becomes `/inbox?tab=inbound`.
  - `App.tsx:118` becomes `replaceState(null, '', '/inbox')`.
- Trade-off. The alternative is to change the two redirects to `/dashboard` and have the backend callback redirect to `/dashboard`. That is 3 edits, but it fails silently if the backend still says `/`. Moving the inbox is about 5 edits and works whichever URL the backend picks. It also frees `/` for a marketing page later (see SEO). What you give up: a one-time change to bookmarks and links to `/`.
- **[backend]** Check what the callback redirects to.

**2. Redirect loop when the backend is down or returns 5xx.**
- Evidence:
  - `App.tsx:54-61` and `PageHeader.tsx:27-31` treat any failure of `getMyTenant` as "session dead" and call `handleSignOut`.
  - `getMyTenant` throws on any non-2xx (`api.ts:149`), so a 502 from the proxy counts.
  - Sign-out POSTs `/auth/logout`, which also fails, so the httpOnly cookie is not cleared.
  - It then does `location.assign('/login')`. The middleware sees `ns_session`, sends the user back to `/`, and the cycle repeats (`middleware.ts:22`).
- If the network is fully down, `await logout()` throws and nothing redirects. The user is left on a spinner.
- During testing, every backend restart or deploy will hit this.
- Fix:
  1. Give the error a status: in `api.ts`, `export class HttpError extends Error { constructor(public status: number, m: string) { super(m); } }`, and have `getMyTenant` throw `new HttpError(res.status, 'Not authenticated')`.
  2. Sign out only on 401: `.catch((e) => e.status === 401 ? expire() : setLoadError('Server unreachable. Retrying…'))`.
  3. Let the middleware clear a stale cookie without needing the backend:
     ```ts
     if (hasSession && isLogin) {
       if (req.nextUrl.searchParams.has('expired')) {
         const res = NextResponse.next(); res.cookies.delete('ns_session'); return res;
       }
       return NextResponse.redirect(new URL('/dashboard', req.url));
     }
     ```
     and set `expired()` to `location.assign('/login?expired=1')`.
  4. Wrap `logout()` in `try/finally` so the redirect always happens.
- This also fixes the stale-cookie case. Today, a user with an old cookie who fails Instagram login lands on `/login?ig_error=…`, gets bounced to `/`, and the error text is lost.

**3. Every AI auto-reply is rendered as "CONFIDENCE: 0.00 / SOURCE:".**
- Evidence: the backend DTO has no confidence or source (`api.ts:194-214`, `MessageDto`). `InboxFeed.tsx:307-308` falls back to `thread.confidenceScore`, which is never set. Line 330 prints `(conf ?? 0).toFixed(2)` and line 333 prints `SOURCE: {source}`, which is empty. Line 316 labels the sender "SocialSync AI (RAG-Enabled)", an old product name.
- Fix: render the badges only when the value exists, and rename the sender.
  ```tsx
  {conf != null && <span …>CONFIDENCE: {conf.toFixed(2)}</span>}
  {source && <span …>SOURCE: {source}</span>}
  ```
  Do the same for `SidebarNav.tsx:454-456`, where `CONF: 0.00` shows on every real card. Change the label to "Sanchar AI (auto-reply)".
- `sender_type: 'system'` is mapped to `human` (`api.ts:209`), so system messages show as "Human Operator … OPERATOR OVERRIDE SENT VIA GRAPH API" (`InboxFeed.tsx:370`). Add a `system` sender or hide them.

**4. The Channels modal misreports status and can overwrite the real business name.**
- Fake status:
  - The Facebook card says "● LINKED & ACTIVE" with a mock page (`MetaSettingsModal.tsx`, Facebook card, from `initialMetaStatus` in `mockData.ts:229`).
  - The Instagram card says "● VERIFIED" with the mock handle `@himalayan_silk_np` (line 215). This is the card a real Instagram-login tenant will look at first.
  - Only the WhatsApp card is real (`getWhatsAppAccounts`).
  - The modal has no way to connect Facebook or reconnect Instagram, although your flow says "link other channels".
- Fake diagnostics:
  - "PING WEBHOOKS" is a `setTimeout` that always prints "HTTP 200 OK … Verified" (lines 106-111).
  - The callback URL `https://api.socialsync.np/v1/meta/webhook` and the verify token `socialsync_meta_wh_sec_991823` are hard-coded (lines 62, 401).
  - The Verify Token is rendered in the page. Whatever it is, it now ships to every browser.
- Data-loss bug:
  - `useState(businessName)` (line 61) runs once. The modal is mounted from the first render, when `businessName` is still the mock string from `App.tsx:25`.
  - The real tenant name arrives later and `bName` never re-syncs.
  - Open Channels, then click "Save Configuration". `handleSave` (line 114) pushes `'Himalayan Silk & Handicrafts (काठमाडौँ)'` back into the header.
  - Nothing is persisted anyway, because there is no PATCH call. The language setting is the same.
- Fix:
  - Now: remove Save and the name and language fields, or disable them with "coming soon".
  - Use `getInstagramProfiles()` (already in `api.ts`) for the Instagram card.
  - Delete the fake webhook block, or wire it to a real backend health check.
  - If you keep the name field: `useEffect(() => { if (isOpen) setBName(businessName) }, [isOpen, businessName])`.

### P1: wrong or misleading behaviour in the inbox and dashboard

**5. Human takeover does not stick.** `App.tsx:122-139` only edits React state. The 5 s poll (`App.tsx:73-75`) rebuilds `status` from the server `mode` (`api.ts:226`), so it reverts. The button suggests the AI is paused. In reality the AI keeps answering. This is worse than a dead button. **[backend]** Needs a mode endpoint (e.g. PATCH conversation). Until then, hide the button. Also check whether `POST …/messages` flips the mode.

**6. The sidebar is not "listed per social media".**
- It is one flat list with ALL/IG/WA/FB filter chips (`SidebarNav.tsx:318-363`). There are no per-channel counts or groups.
- Previews are empty for every non-open thread (`SidebarNav.tsx:398,437`) because messages load only for the open thread. **[backend]** Add `last_message_preview` to the conversations DTO.
- Changing the filter doesn't change the open conversation. The centre pane still shows a thread the list no longer contains. Select the first visible thread when the filter changes.
- `activeThread` falls back to `threads[0]` (`App.tsx:102`), so the list can highlight nothing while the pane shows something.

**7. Sending: text is lost on failure and the view does not scroll.**
- `InboxFeed.tsx:98-99` clears the input before the request finishes, and `App.tsx:155` reports failure with `alert()`. The typed reply is gone. Await the send, clear only on success, and show an inline error.
- The message list has no scroll-to-bottom (`InboxFeed.tsx:284`). A long conversation opens at its oldest message, and new messages appear off-screen.
- The UI always claims "Meta 24h Window: Active" and "Meta Customer Service Window: Active • Encryption: E2E Verified" (lines 163, 433). Both are static. A reply after 24 h fails, and the UI will not have warned the user. **[backend]** Compute the window from the last customer message.

**8. The right panel and footer show invented data for real threads.**
- Real threads have no `detectedIntent` or `ragSourceDoc`, so "Live Context" is blank or shows an empty badge (`RightInspector.tsx:41,72`). "RAG ACTIVE", "ACTIVE CHANNELS" and "Meta Webhooks 200 OK" (lines 30, 183-213) are permanent.
- Store Catalog, delivery prices and "Discount policy … VINTAGE5" (lines 92-119) come from `mockData.ts`. They read like real store facts.
- Footer: `LATENCY: {(latencyMs / 100).toFixed(1)}s` (`Footer.tsx:24`) shows 120 ms as "1.2s". The divisor should be 1000. `TOKEN_USAGE 412/10000` is a constant.

**9. The dashboard is a fixed-window counter page.**
- `getDashboard()` is always `days=1` (`api.ts:253`, `dashboard/page.tsx:82`). There is no selector and no refresh.
- It prints all three channels even if only Instagram is connected (`dashboard/page.tsx:67`). A new Instagram-only tenant sees `WhatsApp 0 / Facebook 0` and no "connect" prompt.
- The response is trusted. A missing key renders `undefined`.
- The nav badge on this page is the sum of `handover` over the window (line 41). The inbox badge counts threads that are currently NEEDS_HUMAN (`App.tsx:103`). Same badge, two meanings.
- For "all the metrics", the profile numbers (followers, follows, media) already exist in `getInstagramProfiles()`, but only inside a modal. Show them on the dashboard.
- Minor:
  - There are two `<h1>`s (`Header.tsx:87` plus the page).
  - Errors show raw text with no retry.
  - `key={q.text}` collides on duplicate queries.

**10. The 5 s poll fails silently.** `listConversations().catch(console.error)` (`App.tsx:78`) handles neither a 401 nor an outage. There is no backoff, and a slow response can overlap the next tick. Reuse the status check from fix 2, and pause polling while the tab is hidden.

### P2: dead or dangerous code and launch blockers

**11. `app/api/meta/*` and other leftovers.**
- The middleware skips every `/api/...` path except `/api/v1`, so these routes are public:
  - `webhook-logs` GET returns anything anyone POSTed.
  - `webhook` returns `EVENT_RECEIVED` for any body, with no signature check. If the Meta app callback were ever pointed here, messages would be dropped with a 200.
  - `test-connection` always returns success.
- Delete the `app/api/meta` folder.
- Delete `app/api/amit/page.tsx`, which is an empty public page at `/api/amit`.
- Remove `app/api/health`'s "SocialSync" and Gemini fields, or keep it as a plain health route.
- Also remove:
  - `middleware.ts.bak`.
  - The unused mock exports in `mockData.ts` (`initialThreads` and others).
  - The whole simulator, sandbox and AI Draft feature, unless you hide it behind a dev flag. `/api/v1/ai/reply` returns 404 (`api.ts:165`) and simulated threads vanish on the next poll.
- `tsconfig.tsbuildinfo` is tracked. Add `*.tsbuildinfo` to `.gitignore` and `git rm --cached` it.
- `conversation_example.json` is tracked. It holds real-looking Instagram usernames and IDs, so remove it or anonymise it before the repo is shared.

**12. Meta app review and legal.**
- Terms and privacy are plain `<span>`s (`login/page.tsx:203,205`). Instagram and Facebook login reviews need a live privacy policy URL and a data-deletion URL.
- The login page makes unverifiable claims: "Meta Graph v21.0 Compliant", "GDPR / Nepal Telecomm Ready", and "FREE FOREVER". Remove them before submission.
- There is no email sign-up. A merchant who only wants WhatsApp cannot create a workspace (the page says to connect Instagram to create one), and email login works only for existing users.

**13. SEO (later, but cheap to plan for now).**
- `/` is `ssr:false` and login-gated, so crawlers get a redirect to `/login`. Only `/login` is indexable, and it shares the site-wide title and description.
- Missing:
  - `robots.txt`, `sitemap.xml`, `metadataBase`, an og:image and a canonical URL.
  - Per-page `metadata`. `/login` is a client component, so put its `metadata` in a small `login/layout.tsx`.
- `<html lang="en">` sits over Nepali content.
- Five Google font families load through a manual `<link>` (`layout.tsx:31-36`). `next/font` would avoid the render-blocking request.
- Layout for later: a public marketing `/`, and `/inbox` and `/dashboard` protected, with `robots: { index: false }`.
- Static-file caution:
  - The matcher (`middleware.ts:27`) no longer skips paths containing a dot, unlike `middleware.ts.bak`.
  - Today only an unused `sanchar-mailbox.svg` is affected. The day you add `public/robots.txt`, a logged-out crawler is redirected to `/login`.
  - Add `|.*\\..*` back to the exclusion when you add those files.

## Corrections to the first review

- The email-login redirect is at `login/page.tsx:37`, not 34.
- The sidebar preview code is at `SidebarNav.tsx:398,437`.
- "Dashboard handles expired sessions better" is not true. Both pages use the same sign-out-on-any-error pattern, so the loop in finding 2 hits both.
- The static-file redirect is a latent issue, not a current breakage (see item 13).
- The first review missed findings 2, 3 and 4 and the footer unit bug.

## Fix order

1. Findings 2 and 1 together (session and landing logic).
2. Findings 3 and 4 (misleading UI on the main path).
3. Hide the takeover button and the simulator, and delete `app/api/meta`.
4. Inbox and dashboard polish (6 to 10).
5. Legal pages and SEO structure before Meta review.
