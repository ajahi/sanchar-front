# Sanchar frontend: flow check and code review

Everything below comes from reading the code. I did not run the app or `tsc`, and there is no backend here, so the OAuth callback, the response shapes and the cookie behaviour are unverified. Anything that depends on the backend is marked (B). Confidence is stated where it changes what you should do.

## Verdict in one paragraph

The intended flow is: Instagram login, then a dashboard with all metrics, then conversations grouped by channel on the left, then the messages of the clicked conversation. Today the plumbing works for the last two steps. Real conversations and messages load, and replies send. Three things break the story:

1. Login does not end on the dashboard.
2. The dashboard is a 24-hour count table, not "all the metrics".
3. The Channels modal, the AI bubbles and the inspector show fabricated data next to real data. After an Instagram login you see a fake Facebook page, a fake Instagram handle and "CONFIDENCE: 0.00" on real AI replies.

## Flow trace, step by step

| Step | What the code does | Matches intent? |
|---|---|---|
| 1. `/login` | The Instagram button is a plain `<a href="/api/v1/social-accounts/instagram/login">` (`login/page.tsx:186-194`, `api.ts:29`). Middleware rewrites it to FastAPI (`middleware.ts:15-17`). | Yes |
| 2. OAuth return | The backend sets the httpOnly `ns_session` cookie and redirects somewhere (B). Failures come back as `/login?ig_error=...`, and the page reads them (`login/page.tsx:21-25`). | The landing is unknown (B) |
| 3. Landing | Middleware sends a logged-in visitor on `/login` to `/` (`middleware.ts:22`). Email login does `location.assign('/')` (`login/page.tsx:37`). `/` is the inbox (`app/page.tsx`). | **No: it lands on the inbox, not the dashboard** |
| 4. Dashboard | Only reachable through the header's DASHBOARD link (`Header.tsx:91-101`). | Not the landing |
| 5. Conversations by channel | One flat list with ALL/IG/WA/FB filter buttons (`SidebarNav.tsx:71-116`). | Partly: filtered, not grouped, and the buttons have no counts |
| 6. Click a conversation | `setActiveThreadId`, then an effect fetches `/conversations/:id/messages` (`App.tsx:89-96`). It refetches whenever `last_message_at` changes on the 5-second poll. | Yes |

## Findings, ranked

### Blockers and high severity

**H1. Login does not land on the dashboard (`middleware.ts:22`, `login/page.tsx:37`, backend callback).**
- Both frontend paths end at `/`, which is the inbox.
- The Instagram path goes wherever the backend redirects. That is the one piece I cannot see (B).
- Do not fix this by changing only the two frontend lines. If the backend redirects to `/`, they never run for the Instagram path.
- Make the frontend correct whatever the backend does. In `middleware.ts`, after the session check, add:
  ```ts
  if (hasSession && pathname === '/') return NextResponse.redirect(new URL('/dashboard', req.url));
  ```
- Then move the inbox to `app/inbox/page.tsx`. The file is the current `app/page.tsx`, unchanged.
- Update these references from `/` to `/inbox`:
  - `PageHeader.tsx:37`
  - `PageHeader.tsx:40`, where `/?tab=…` becomes `/inbox?tab=…`
  - `App.tsx:118`, `history.replaceState(null,'','/')`
  - the Header INBOX button, so it routes to `/inbox` instead of being a `setActiveTab` no-op on the dashboard
- Also change `login/page.tsx:37` to `/dashboard`.
- Confidence about the diagnosis: high. Confidence that this is what you wanted: high, since you said the user "is then to be shown dashboard".

**H2. Real AI replies render as `CONFIDENCE: 0.00` and `SOURCE: ` (`InboxFeed.tsx:307-333`, `api.ts:83-90`).**
- `toChatMessage` never sets `confidence` or `source`.
- The AI bubble does `conf = msg.confidence ?? thread.confidenceScore`, then `(conf ?? 0).toFixed(2)`. Real threads never set `confidenceScore` either. The badge therefore always shows 0.00 in green.
- The source badge prints an empty string.
- Baseline reviews caught only the sidebar copy of this (`SidebarNav.tsx:208`). The bubble one is more visible.
- Fix: render each badge only when the value is defined. For example `{conf != null && <span>CONFIDENCE: {conf.toFixed(2)}</span>}`, and the same for `source`. Apply the same guard at `SidebarNav.tsx:207-209`.
- If the backend does return confidence per message, map it in `toChatMessage` (B).

**H3. The Channels modal lies about what is connected (`MetaSettingsModal.tsx:186-228`, `App.tsx:31`, `mockData.ts:229-241`).**
- Facebook is hard-coded as "LINKED & ACTIVE" with the page "Himalayan Silk & Handicrafts" and ID `109827364120938`.
- Instagram is hard-coded as "VERIFIED" with `@himalayan_silk_np`.
- Right after a real Instagram login, the user sees a stranger's handle.
- The real data already exists. `getInstagramProfiles()` (`api.ts:149`) is used by `ProfileModal` but not here.
- Fix:
  - Call `getInstagramProfiles()` in the modal, the same way `loadWhatsApp` works.
  - Show the real handle and ID, or "NOT CONNECTED" with a link to `INSTAGRAM_LOGIN_URL`.
  - Replace the Facebook card with "Not available yet" until a Facebook endpoint exists.
- Do not pass `initialMetaStatus` into production props at all (`App.tsx:31`, `PageHeader.tsx:38`). `Header` does not even read `metaStatus`, so it is already dead.

**H4. Expired or failing sessions behave inconsistently (`App.tsx:54-62`, `App.tsx:67-85`).**
- `getMyTenant().catch(handleSignOut)` signs the user out on any error, including a 500 or a network blip. A backend restart logs everyone out.
- Change `getMyTenant` in `api.ts:23` to throw a typed error carrying `res.status`. Sign out only on 401.
- The 5-second poll does the reverse. `listConversations` and `listMessages` failures only go to `console.error`. After the cookie expires mid-session, the inbox silently freezes and never returns to `/login`.
- Fix: on 401 in `listConversations`, run `handleSignOut`. Otherwise show a small "connection lost, retrying" banner.
- `handleSignOut` is `await logout()` then `assign`. If `logout()` rejects because the backend is down, the redirect never happens and the user is stuck. Wrap it in `try/finally`.

**H5. The dashboard is not "all the metrics" and does not react to your login (`app/dashboard/page.tsx:34-71`, `api.ts:129`).**
- It fetches `days=1` only. There is no selector, no refresh and no polling.
- It always lists WhatsApp, Instagram and Facebook rows (`:8-12`, `:19`). A tenant who has just linked Instagram sees a wall of zeros and no "connect WhatsApp/Facebook" prompt.
- The metrics are message counts, top queries and handover counts. There is nothing on response time, AI versus human share, open escalations or trend.
- Fix, in order of effort:
  1. Add a 1/7/30-day selector (`getDashboard(days)` already accepts it).
  2. Read `getInstagramProfiles()` and `getWhatsAppAccounts()`, and show only connected channels plus "Connect …" cards.
  3. Ask the backend for the other metrics (B).

### Medium severity

**M1. The takeover toggle does not stick (`App.tsx:122-139`, `InboxFeed.tsx:177-195`).**
- It only mutates local state. The next poll runs `toThread`, which sets `status` from `c.mode` (`api.ts:102`), so the toggle reverts within 5 seconds.
- The button does nothing on the backend, so the AI keeps replying.
- This needs a backend PATCH such as `/conversations/:id {mode}` (B).
- Until it exists, hide the button. A working-looking control that doesn't work is worse than none.

**M2. Any non-`ai` mode is shown as NEEDS HUMAN (`api.ts:102`).**
- `status: c.mode === 'ai' ? 'AUTO_PILOT' : 'NEEDS_HUMAN'`.
- A `paused`, `off` or `closed` mode will flash the red pulsing banner and inflate both escalation counts (`SidebarNav.tsx:133`, `Header`).
- Compare against the specific value the backend uses for a human handover (B).

**M3. The "escalations" badge means two different things (`dashboard/page.tsx:41` versus `App.tsx:103`).**
- On the inbox it is the number of threads currently NEEDS_HUMAN.
- On the dashboard it is the sum of `handover` over the last 24 hours, and it appears on the INBOX pill.
- Same label, different number. On the dashboard, either drop the badge or use the same source.

**M4. Sidebar previews are empty for most threads (`SidebarNav.tsx:151`, `190`).**
- Messages are fetched only for the open thread, so every other thread shows "No messages yet". This is untrue for threads with history.
- Either have `/conversations` return `last_message` (B), or show nothing rather than a false statement.

**M5. Message list correctness (`api.ts:80-90`, `App.tsx:87-96`).**
- `fmtTime` shows only HH:MM. A conversation spanning days shows no date. Add a date separator.
- `sender_type: 'system'` is mapped to `'human'` (`api.ts:85`). System notes appear as "Human Operator (Merchant)" with "OPERATOR OVERRIDE SENT VIA GRAPH API" (`InboxFeed.tsx:359,369`).
- The `agent` versus `ai` distinction relies on `sender_type` only. `ai_generated` is ignored.
- Switching threads shows an empty pane until the fetch returns, with no loading state.
- A sort order is assumed. If the API returns newest first, chats read backwards (B).

**M6. Static text presented as live status.**
- `InboxFeed.tsx:433`: "Meta Customer Service Window: Active • Encryption: E2E Verified". The 24-hour window is never computed. Replies after the window fail on the backend and you get an `alert()`.
- `RightInspector.tsx:182-212`: the "ACTIVE CHANNELS" stamp shows all three icons as connected, plus "● Meta Webhooks 200 OK". Both are constants.
- `MetaSettingsModal.tsx:105-112`: "PING WEBHOOKS" is a `setTimeout` that prints "HTTP 200 OK — Inbound Webhooks Verified for Messenger, Instagram, & WhatsApp". It cannot fail.
- `MetaSettingsModal.tsx:401-405`: the callback URL `https://api.socialsync.np/v1/meta/webhook` and the verify token `socialsync_meta_wh_sec_991823` are placeholders. If someone pastes them into Meta, it breaks.
- Only the WhatsApp PING (`:254-260`) is real. Delete or replace the rest.

**M7. "Save Configuration" saves nothing (`MetaSettingsModal.tsx:114-117`, `App.tsx:433`).**
- It updates local state only. A refresh restores the tenant name from the backend.
- The dialect selector is also local only.

**M8. Public routes without the middleware (`middleware.ts:27`).**
- The matcher's negative lookahead excludes everything starting with `api`. That includes `app/api/meta/*` and `app/api/amit/page.tsx`, which are therefore reachable without a session.
- `app/api/meta/webhook/route.ts` accepts any POST without signature verification and stores it in memory. `test-connection` always returns success.
- Nothing in the frontend calls these. The real webhook goes to FastAPI.
- Delete `app/api/meta/`.
- `app/api/health` reports "SocialSync AI" and `hasGeminiKey`. Keep it for the Docker healthcheck, but drop the env-key boolean and rename it.

**M9. The matcher no longer excludes static files (`middleware.ts:27`).**
- `/robots.txt`, `/sitemap.xml`, `/sanchar-mailbox.svg` and OG images all redirect to `/login` for logged-out visitors. `middleware.ts.bak` had the exclusion.
- The current UI does not reference any public asset, so nothing visible breaks today. It bites the moment you add SEO files.
- Fix: `matcher: ['/((?!api|_next|.*\\..*).*)', '/api/v1/:path*']`.
- Doing that also lets the future public landing page work (see the SEO section).

**M10. Webhook path in dev and compose (`middleware.ts:8-13`, `docker-compose.yml`).**
- `/api/v1/webhooks/*` is passed to Next, which has no such route, so it returns 404 unless nginx sits in front and routes it to FastAPI.
- `docker-compose.yml` has only the `web` service. The comment says "nginx routes them directly", but no nginx is defined here.
- Meta's callback URL must not point at this Next origin. Say so in the README, or rewrite webhooks too if you can accept the body-forwarding risk (B).

### Low severity and cleanup

- **Leaked defaults.** `App.tsx:25` initialises `businessName` to "Himalayan Silk & Handicrafts (काठमाडौँ)", which flashes in the header before `/tenants/me` returns. Start with `''` (the dashboard already does).
- **Header dead branch.** `Header.tsx:184-193`: while `currentUser` is null it renders "LOGIN / SIGN UP" with `onOpenAuthPage` undefined, so clicking does nothing. It also flashes on every page load. Render nothing while loading.
- **Dev-only tools in the production UI.**
  - `+ INBOUND`, `SIMULATE CUSTOMER`, `AI DRAFT` and the RAG sandbox all call `/api/v1/ai/reply`. Its own comment says it 404s (`api.ts:41`).
  - The simulator adds threads with ids like `thread-<ts>`. The next poll (`App.tsx:73-75`) replaces the whole array, so they vanish within 5 seconds.
  - Gate them with `process.env.NEXT_PUBLIC_DEV_TOOLS === '1'`.
  - `handleGenerateAiDraft` (`InboxFeed.tsx:118-121`) catches a failure and puts a fake Nepali "we're reviewing your query" apology into the reply box. A merchant could send it to a real customer. Show an error instead.
- **Mock catalog and FAQs.** `mockData.ts` inventory, FAQs and the Catalog modal are local state, never persisted. The Footer (`Footer.tsx:12`, `App.tsx:99-100`) shows made-up token usage 412 and latency 120 ms.
- **`alert()` on send failure** (`App.tsx:155`). Use an inline error. Also, `handleSend` clears the input before the request completes, so a failed send loses the typed text (`InboxFeed.tsx:96-100`).
- **Stale brand strings.** "SocialSync AI (RAG-Enabled)" on the AI bubble (`InboxFeed.tsx:316`), "Ask Gemini" in a tooltip, `SocialSync` in `health/route.ts`. The product is Sanchar.
- **Repo hygiene.**
  - `middleware.ts.bak` and `tsconfig.tsbuildinfo` are tracked. Delete the first and untrack the second.
  - `app/api/amit/page.tsx` renders `null`. Delete it.
  - `conversation_example.json` is tracked and contains real-looking Instagram user IDs and usernames from a Graph API response. Remove it from the repo (and from history if the repo is shared).
- **Login page.**
  - "terms of service" and "privacy policy" are `<span>`s (`login/page.tsx:246-248`). Meta app review requires real, public privacy-policy and data-deletion URLs. Build them before submitting.
  - The labels have no `htmlFor`, so clicking a label does not focus its input.
  - There is no post-login return path, so a deep link `/inbox?…` is lost after login.
  - Copy such as "ESTD. 1932", "Free forever" and "100% sulphur-free" is theme fluff. It is fine for a prototype, but not for a public page.
- **Backend-scale risk (B).** `listConversations` polls the full list every 5 seconds with no pagination or `since` parameter. That is fine for testing, but it will hurt with hundreds of threads.
- **Runtime env in middleware.** `BACKEND_URL` falls back to `http://localhost:8000` (`middleware.ts:3`). In the container that fallback silently sends every API call to itself if the variable is missing. Low confidence that it is a problem, since `env_file: .env` supplies it at runtime. Check once with `curl -i http://<host>:3000/api/v1/tenants/me` inside the container.

## SEO note (you said this matters later)

- `/` is `ssr:false` and login-gated, so crawlers see a redirect to `/login`.
- `/login` is the only indexable page. It does get server-rendered, because it is a client component that Next pre-renders.
- Every page shares one `<title>` from `app/layout.tsx`.
- The plan that fits the fix in H1:
  - `/` becomes a public marketing page for logged-out visitors.
  - Logged-in visitors are redirected from `/` to `/dashboard` by the middleware line above.
  - The inbox lives at `/inbox`.
  - Add a per-page `metadata` export for `/login` (`export const metadata` needs a server component, so split the form into a client child).
  - Add `robots.txt` and `sitemap.xml`, and mark `/dashboard` and `/inbox` as `noindex`.
- This depends on M9 first.
