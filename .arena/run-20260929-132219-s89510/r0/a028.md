# Sanchar frontend: review and flow check (Instagram login, dashboard, conversations)

Method: I read every file on the flow (middleware, login, dashboard, inbox `App.tsx`, `api.ts`, Header, PageHeader, SidebarNav, InboxFeed, RightInspector, MetaSettingsModal, ProfileModal, mockData, types, `app/api/**`, Dockerfile, compose, `.env.example`). `npx tsc --noEmit --incremental false` passes with no output. I did not run the app or see the backend, so anything marked **[backend?]** depends on FastAPI behaviour I can't see.

## Assumptions and open questions

| Open question | Assumption I made |
|---|---|
| Where does the backend redirect after the Instagram callback? The frontend has no callback route, so this is decided in FastAPI. | It redirects to `/` (the inbox). Nothing in the frontend contradicts this, and the middleware comment suggests error cases land on `/` or `/login`. |
| Do `GET /conversations`, `/dashboard` and `/tenants/me` return 401 for a bad or expired cookie? | Yes, the usual FastAPI behaviour. |
| Does the backend pause AI replies when a human takes over? | Unknown. There is no frontend call for it, so I treat it as missing. |
| Is the deployment behind nginx (as the middleware comment says) or hit directly on :3000 during testing? | nginx in the deployed setup, direct or tunnelled in local dev. |
| Which audience matters more now: you testing the flow, or Meta app review and SEO? | Flow correctness first, then Meta review, then SEO. You said "testing and developmental phase" and "SEO later". |

## How I settled the disagreements between reviewers

I read the code as three reviewers would: an auth and flow QA, a React and data-correctness reviewer, and a Meta-platform and deployment reviewer. They disagreed in three places.

1. **Post-login target.** The flow reviewer wanted `/dashboard` as the landing page. The SEO reviewer wanted `/` reserved for a future public landing page. Decision: land on `/dashboard` now, using one redirect constant in each place, and move the inbox to `/inbox` when the landing page is built. Cost: a small rename later.
2. **Mock features.** The React reviewer wanted them deleted. The QA reviewer wanted them kept as demo aids. Decision: remove the mock elements that can reach a real customer or misstate real status now (findings 4 and 5). Keep the simulator and sandbox files but hide them from tenants. Cost: no in-app demo until you add a dev flag.
3. **Session handling.** Options were a fix per call site, or one wrapper. Decision: one wrapper, because the same silent-401 bug sits in five call sites.

## Findings, most severe first

### 1. High: login lands on the inbox, not the dashboard
`middleware.ts:22` and `login/page.tsx:37` send users to `/`. The Instagram callback redirect is in the backend, so changing the frontend alone won't fix the Instagram path.

Fix, frontend side:
```diff
- if (hasSession && isLogin) return NextResponse.redirect(new URL('/', req.url));
+ if (hasSession && isLogin && !req.nextUrl.searchParams.has('expired'))
+   return NextResponse.redirect(new URL('/dashboard', req.url));
```
```diff
- window.location.assign('/'); // full load so middleware sees the new cookie
+ window.location.assign('/dashboard');
```
Backend side: make the Instagram callback redirect to `/dashboard`. If you can't touch it, the fallback is to make `/` the dashboard and move the inbox to `/inbox` (rename `app/page.tsx` and `app/dashboard/page.tsx`, and change the three `router.push('/')` calls in `PageHeader.tsx`). That needs no backend change but delays the public landing page.

### 2. High: session handling is wrong in both directions
- **Any failure logs the tenant out.** `getMyTenant` throws a generic error on any non-OK response (`api.ts:23-27`). Both callers do `.catch(handleSignOut)` (`App.tsx:61`, `PageHeader.tsx:30`). A backend restart, a 500 or a network blip therefore POSTs logout and sends you to `/login`.
- **A real expiry is invisible after mount.** The 5-second poll only does `console.error` (`App.tsx:78`). Send, profile, WhatsApp link and dashboard calls just show errors. The dashboard only recovers because `PageHeader` runs its own `getMyTenant`.
- **Possible redirect loop [backend?].** With a stale cookie, `/` fails, `logout()` runs, and you go to `/login`. Middleware sees the cookie and bounces you back to `/`. This loops unless the logout endpoint clears the cookie even when the session is invalid.
- `await logout()` (`App.tsx:48`, `PageHeader.tsx:22-25`) throws on a network error, so the redirect never happens.

Fix: one wrapper for all authenticated calls in `api.ts`, and a `?expired=1` bypass (already added in the middleware diff above).
```ts
export async function apiFetch(url: string, init?: RequestInit) {
  const res = await fetch(url, init);
  if (res.status === 401 && !location.pathname.startsWith('/login'))
    location.assign('/login?expired=1');   // stale cookie is overwritten by the next login
  return res;
}
```
Replace `fetch(` with `apiFetch(` in every function except `login`. Change `getMyTenant` to throw `new Error(\`tenant lookup failed (${res.status})\`)` and remove `.catch(handleSignOut)` in both callers. Make `logout()` wrap its fetch in `try/catch`. Have the login page show "Session expired, please sign in" when `expired` is present.

### 3. High: "Take over as human" does nothing
`handleToggleTakeover` (`App.tsx:122-139`) only edits local state. The next poll (`App.tsx:73-75`) replaces `status` from the server's `mode`, so it reverts within 5 seconds. The merchant believes the AI is paused while it may still reply, so the customer could get both replies **[backend?]**.

Fix: add a backend endpoint (for example `PATCH /conversations/{id}` with `{mode}`), call it, then apply the response. Until then, disable both buttons (`InboxFeed.tsx:177-194`) with a "coming soon" title. Also check whether sending a human message flips the mode on the backend.

### 4. High: fake status shown as real in the Channels flow
- `mockData.ts:150-169` marks Facebook, Instagram and WhatsApp as connected ("Himalayan Silk", `@himalayan_silk_np`).
- `MetaSettingsModal.tsx:186-189` shows "LINKED & ACTIVE" and `:214-216` shows "VERIFIED" for those fakes. This is the screen a tenant uses to check that linking worked. Only the WhatsApp card is live (`:231-377`).
- `MetaSettingsModal.tsx:61` sets `useState(businessName)` once. The modal is always mounted, so it captures the fake default "Himalayan Silk & Handicrafts (काठमाडौँ)" before the tenant loads. Clicking **Save Configuration** (`:114-117`) writes that fake name into the header. Nothing is persisted either, and a reload reverts it.
- `:105-112` "PING WEBHOOKS" is a timer that always says "HTTP 200 OK — Inbound Webhooks Verified".
- `:401-405` shows a callback URL (`api.socialsync.np/v1/meta/webhook`) and a verify token that are not your real ones. The token is baked into the client bundle. If it is a real token, it leaks.
- `RightInspector.tsx:182-213` ("ACTIVE CHANNELS", "Meta Webhooks 200 OK") is static.
- `Footer.tsx:10-11` shows constant latency and token numbers (also `App.tsx:99-100`).

Fix:
- Build the Instagram card from `getInstagramProfiles()` (already used by `ProfileModal`) with "Connect Instagram" linking to `INSTAGRAM_LOGIN_URL`.
- Show Facebook as "not available yet".
- Delete the fake webhook block, or show the real webhook URL.
- Add `useEffect(() => setBName(businessName), [businessName, isOpen])`.
- Remove or disable **Save Configuration** until a settings endpoint exists.
- Drive the right-panel stamp and the header from the same real data.

### 5. High: mock content can be sent to real customers
- `InboxFeed.tsx:126-131` has one-click "quick replies" with an invented coupon (`VINTAGE10`), an invented tracking link (`courier.np/track/SS98234`) and "10% discount approved". They go straight into the send box.
- `InboxFeed.tsx:118-121`: `/api/v1/ai/reply` returns 404 today (`api.ts:41`). So every **AI DRAFT** click puts a fake Nepglish "we are reviewing your query" message into the input.
- `InboxFeed.tsx:430-436` and `:163` claim "Encryption: E2E Verified", "Meta 24h Window: Active" and "OPERATOR OVERRIDE SENT VIA GRAPH API". They are static text. The real 24-hour window is never computed, although `windowExpiresAt` exists in the type. Sending after 24 hours will fail and reach only an `alert()` (`App.tsx:155`).

Fix: delete `cannedResponses`. Make the AI DRAFT catch show an inline "AI drafting unavailable" message instead of writing into the input, or hide the button. Compute the window from the last customer message. Replace `alert()` with an inline error.

### 6. Medium: conversation list is thin and partly wrong
- **Previews.** Messages are fetched only for the open thread (`App.tsx:88-96`). Every other card reads "No messages yet" (`SidebarNav.tsx:151,190`). Ask the backend for a `last_message` preview field. Until then, render nothing rather than that text.
- **Times.** Times are `HH:MM` only (`api.ts:80-81,100`). A message from last week looks like today. Show the date once it is not today.
- **Status.** `status: c.mode === 'ai' ? 'AUTO_PILOT' : 'NEEDS_HUMAN'` (`api.ts:102`) treats any other mode value, and ignores the DTO's `status` field, so closed or paused conversations may count as escalations **[backend?]**. Map values explicitly.
- **Confidence and labels.** Real threads show `CONF: 0.00` (`SidebarNav.tsx:207-209`) and AI messages show `CONFIDENCE: 0.00` and an empty `SOURCE:` (`InboxFeed.tsx:329-334`). Hide those badges when the value is missing. AI messages are labelled "SocialSync AI (RAG-Enabled)". Every non-customer, non-AI message, including `system` and WhatsApp agent messages, is shown as "Human Operator (Merchant)" (`api.ts:85`).
- **Right panel.** Intent and source are blank for real threads (`RightInspector.tsx:41,72`), and "Delivery Rs.150 / VINTAGE5" (`:105-119`) is shown to every tenant.
- **Order.** The frontend does not sort. It relies on the backend returning newest first, and the first item is auto-selected (`App.tsx:76`) **[backend?]**.

### 7. Medium: simulators corrupt the live inbox
`handleTriggerInboundWebhook` (`App.tsx:253-324`) creates a `thread-<timestamp>` thread and makes it active. The next poll drops it (`App.tsx:73-75`). `activeThreadId` still points at it, so the pane falls back to `threads[0]` but the message-loading effect (`:89-96`) fetches for the dead id, which fails (`console.error`). The pane looks empty until you click. The same stale-id problem happens whenever the active thread disappears from the list. Simulated messages are also lost on the next poll, and `askAi` 404s anyway.

Fix: hide `+ INBOUND` (`Header.tsx:143-151`), `SIMULATE CUSTOMER` (`InboxFeed.tsx:197-259`), the RAG sandbox and the catalog tab from tenants. In the poll, reset `activeThreadId` to `fresh[0]` if the current id is not in `fresh`. Catalog, FAQ, token usage and latency are all mock.

### 8. Medium: dashboard gaps
- Fixed `days=1`, no selector, no refresh, no link to the conversations behind a number.
- Always lists WhatsApp, Facebook and Instagram (`dashboard/page.tsx:8-12,19`), so a fresh Instagram-only tenant sees zeros for WhatsApp and Facebook and no "connect" prompt. Show connected channels only, using the existing profile and WhatsApp endpoints, with an empty-state link to Channels.
- The badge on the dashboard header counts handovers in the window (`:41`), while the inbox badge counts threads currently needing a human (`App.tsx:103`). Same label, different numbers.
- If a key is missing, `data.top_queries.length` (`:59`) or `Object.values(data.handover)` (`:41`) throws and blanks the page. A missing channel count renders as empty, not "undefined". Guard with `?? []` and `?? {}`.
- Add a range control: `const [days, setDays] = useState(1)` with `getDashboard(days)` in the effect.

### 9. Medium: middleware blocks public files and leaves `/api/*` unprotected
- The matcher `'/((?!api|_next|favicon.ico).*)'` (`middleware.ts:27`) lost the `.*\\..*` exclusion that `middleware.ts.bak` had. Logged-out visitors, including crawlers and Meta reviewers, get redirected to `/login` for `/robots.txt`, `/sitemap.xml`, `/sanchar-mailbox.svg` and any OG image. Use `'/((?!api|_next|favicon.ico|.*\\..*).*)'`.
- The same `api` exclusion means `/api/health`, `/api/amit` and `/api/meta/*` skip the login check. `/api/meta/webhook-logs` returns logged payloads to anyone. Delete these (finding 11).
- Any public page you add (`/privacy`, `/terms`, `/data-deletion`, a landing page) must be allow-listed in the same function. Replace `isLogin` with `PUBLIC.has(pathname)`.
- The `webhooks` bypass (`:11-13`) returns `NextResponse.next()`. Without nginx in front, for example `next dev` behind a tunnel, Meta's webhook hits Next and gets a 404. The comment that a rewrite "re-serializes the body" is doubtful, because Next streams the body for external rewrites. Test with a signed payload before relying on either claim. In dev, point the tunnel at FastAPI.
- `BACKEND_URL ?? 'http://localhost:8000'` (`:3`) fails silently inside Docker if the variable is missing. Throw in production instead.
- **[backend?]** The proxy sets the upstream `Host`. If FastAPI builds the Instagram `redirect_uri` from the request URL, it may produce `http://api:8000/...` and Meta will reject it. Run uvicorn with `--proxy-headers` or hard-code the public callback URL.

### 10. Medium: Meta app review blockers on the login page

Those pages must be public (see finding 9). Claims such as "Meta Graph v21.0 Compliant", "GDPR / Nepal Telecomm Ready" and "FREE FOREVER" (`:96,287-289,92`) are unverified and reviewers read them.
