# Sanchar frontend: review and flow check (Instagram login -> dashboard -> conversations)

## Verdict

The pieces exist, but the flow you described does not run end to end yet.

- **Login works in principle.** The Instagram button hits the FastAPI proxy, the backend sets the `ns_session` cookie, and the middleware gates every page on that cookie.
- **Nothing sends the user to the dashboard.** The code lands them on the inbox (`/`), or wherever the backend callback redirects, which I cannot see.
- **The inbox shows real conversations and messages, but the surrounding UI is still the mock prototype.** Several controls do nothing real: human takeover, Channels status, webhook PING, and the AI confidence/source badges. Some of them show green, "verified" or made-up state. With real data this misleads the merchant.
- **Two bugs quietly corrupt what the user sees.** The business name can be overwritten with a demo name, and system messages are displayed as if the merchant typed them.
- **The middleware makes public pages impossible.** That blocks both Meta app review (privacy policy and data-deletion URLs) and your later SEO work.

`npx tsc --noEmit` passes (exit 0, no output) and left the working tree unchanged. I did not run the app against a backend. Each finding is marked **[verified in code]** or **[needs backend]**.

## Assumptions

- "Dashboard" means `app/dashboard/page.tsx`, and "conversations on the left" means `SidebarNav` in the inbox at `/`.
- Your sentence ("logs in using Instagram and is then shown the dashboard") is the target. Email/password login is a secondary path.
- The backend is a black box. Wherever a finding depends on it, I say so and give a `curl` check in the last section.
- `.next/` in the repo is a stale build (Sep 15, older middleware), so I used the source only.

## 2. Findings, most severe first

Severity scale: **P0** blocks the intended flow. **P1** wrong or misleading behaviour a tenant will hit. **P2** should fix before launch. **P3** cleanup.

### P0

**F1. The user does not land on the dashboard.** [verified in code; the backend half needs backend]

- The frontend has two hard-coded landing points: `middleware.ts:22` and `login/page.tsx:37`. Both go to `/`.
- The Instagram callback's redirect target lives in the backend. If it redirects to `/`, the user sees the inbox. If it redirects to `/dashboard`, it works, but only by backend luck.
- The robust fix is to make `/` a router and move the inbox to `/inbox`. Then it does not matter where the backend sends the browser. Patch A below does this.
- Bonus: `/` stops being overloaded. Today it is the inbox, the post-login target and the only URL a crawler sees.
- Simplest alternative: change those two lines to `/dashboard` and set the backend callback to `/dashboard`.

**F2. The session layer is wrong in four ways, and one of them can loop forever.** [verified in code; loop needs backend]

1. `getMyTenant` (`api.ts:23-27`) throws "Not authenticated" for any non-OK status, including 500, 502 and backend restarts. `App.tsx:54-62` and `PageHeader.tsx:27-31` treat every error as a dead session and call `logout()` then `/login`. A 30-second backend restart therefore logs every open tab out.
2. `signOut` and `handleSignOut` do `await logout()` and then redirect. If the logout fetch rejects (network error), the redirect never runs and the user is stuck on a blank page.
3. Redirect loop risk. The middleware only checks that the cookie exists (`middleware.ts:19`).
   - With a stale or forged cookie: `/login` redirects to `/`, `/tenants/me` returns 401, `logout()` runs, and the browser goes to `/login`.
   - If `/auth/logout` needs a valid session, or does not send `Set-Cookie ... Max-Age=0`, the cookie survives and the loop repeats.
   - An httpOnly cookie cannot be cleared from JS.
4. A mid-session expiry is not handled in the inbox. The 5 s poll (`App.tsx:67-85`) and the message fetch only `console.error`. The user sees a frozen inbox with no message. The dashboard is covered only because its `PageHeader` makes a separate `getMyTenant` call.

Fix: use one `apiFetch` wrapper, redirect only on 401, and add an `expired` flag to break loops. See Patch B.

**F14. The middleware blocks every public page.** [verified in code]

- Any logged-out request other than `/login` redirects to `/login` (`middleware.ts:21`).

## 3. Why these bugs cluster (the system view)

1. **Mock state and real state live in the same components, so nothing tells the user which is which.** `App.tsx` mixes server data (`threads`) with prototype state (`inventory`, `metaStatus`, `tokenUsage`, `businessName`). The result is F4, F6, F11, F16 and F17. The fix is structural: real data comes only from `api.ts`, and anything without a backend is hidden or clearly marked "demo".
2. **There is no single API and session layer.** Eleven `fetch` calls handle status codes differently, so 401, 5xx and network failures behave differently in each place (F2, F8, F15).
3. **`/` and the middleware carry too many roles.** `/` is the inbox, the landing target, and the URL a crawler sees. The middleware allows exactly one public page. This produces F1, F12, F14, and the SEO problem in section 5.
4. **Second-order effect of fixing F1 alone.** A new tenant who lands on the dashboard sees zeros and no next step, and the sidebar has no conversations yet. Add an empty state with "Connect a channel" and "Messages will appear when customers write" (part of Patch G).

### Patch B: one API wrapper, 401-only sign-out, loop breaker (fixes F2)

async function apiFetch(url: string, init?: RequestInit): Promise<Response> {
