# Sanchar frontend: review and flow check (Instagram login -> dashboard -> conversations)

I read every file on the flow (`middleware.ts`, `app/*`, `src/App.tsx`, `src/api.ts`, all of `src/components/*` that the flow touches, `mockData.ts`, `app/api/**`, Docker files). I did not run the app or the backend, and I did not run `tsc`, because it would write `tsconfig.tsbuildinfo` into your project. Every finding below was checked against the code. Where the outcome depends on backend behaviour I cannot see, it is tagged **[backend]** and has a confidence level.

## 1. Verdict

The plumbing works: proxying `/api/v1/*`, the session cookie gate, the Instagram login link, the conversation poll, the message fetch, sending a reply, and the dashboard fetch are all wired to real endpoints. Three things stop it matching the flow you described:

1. **Instagram login does not land on the dashboard.** It lands on the inbox.
2. **A failure of `/tenants/me` for any reason (backend down, 5xx, network blip) causes an endless reload loop.** It is not limited to expired sessions.
3. **The UI shows fake state next to real state.** The Channels modal, the AI bubbles, the badges and the footer all say things that are not true for a real tenant. A first-time Instagram user sees "Facebook LINKED & ACTIVE", "WhatsApp connected" and "Meta Webhooks 200 OK".

### Flow, step by step

| Step | Intended | Actual | Status |
|---|---|---|---|
| Click "Continue with Instagram" | Start OAuth | `login/page.tsx:186` plain `<a href="/api/v1/social-accounts/instagram/login">`, rewritten to FastAPI by `middleware.ts:15-17`. A plain `<a>` is right (no Next prefetch). | OK |
| OAuth callback | Session cookie set, then land on dashboard | Backend sets `ns_session`. The failure path returns `/login?ig_error=...`. Success destination is decided by the backend. Nothing in this repo sends anyone to `/dashboard`. | Diverges **[backend]** |
| Route guard | Logged in goes forward, logged out goes to `/login` | `middleware.ts:19-22` checks only that the cookie exists. Logged-in visits to `/login` go to `/` (the inbox). | Diverges |
| Dashboard | Landing page with all metrics | `/dashboard` is a separate page, one header pill away. It shows 4 blocks (new messages, top queries, handled, handover) for a fixed 24h. | Reachable, not the landing page |
| Conversation list | Grouped per social media, left side | One mixed list with ALL/IG/WA/FB filter buttons (`SidebarNav.tsx:71-116`). | Partial (filter, not grouping) |
| Open a conversation | Messages appear | `App.tsx:88-96` fetches `/conversations/{id}/messages`. It starts at the top of the chat, not the latest message. | Works, with UX bugs |
| Reply | Sent to the customer | `sendReply` -> backend. Works, but the draft is lost on failure (see #9). | Works, with bugs |

## 2. Findings, ranked

Severity: **P0** breaks the flow or can hurt a real customer. **P1** wrong behaviour a tester will hit soon. **P2** misleading or unpolished. **P3** cleanup.

### P0

**1. Post-login landing is the inbox, not the dashboard.** (`middleware.ts:22`, `login/page.tsx:37`, and the backend callback **[backend, high confidence that it is `/`]**)
There are three places that choose the destination, and they must agree: the backend callback redirect, the `hasSession && isLogin` bounce, and the email login's `location.assign('/')`.
Fix the two you own:
```ts
// middleware.ts:22
if (hasSession && isLogin) return NextResponse.redirect(new URL('/dashboard', req.url));
// login/page.tsx:37
window.location.assign('/dashboard');
```
Then make the backend callback redirect to `/dashboard` as well. Until that is changed, a fresh Instagram login still shows the inbox, because the callback response itself goes to `/`. A simpler alternative: make `/` the dashboard and move the inbox to `/inbox`. That also fixes the SEO issue in #14.

**2. Reload loop whenever `/tenants/me` fails for a non-auth reason.** (`App.tsx:54-62`, `App.tsx:47-50`, `PageHeader.tsx:22-31`, `middleware.ts:22`)
Trace with the backend stopped, or `BACKEND_URL` wrong:
1. The rewrite to the backend fails, so Next returns a 5xx.
2. `getMyTenant` throws ("Not authenticated" for any `!res.ok`).
3. `.catch(handleSignOut)` runs `logout()`. That is also a 5xx, but `fetch` does not reject on 5xx, so the code continues.
4. `location.assign('/login')` runs. The cookie is still there, so middleware bounces `/login` to `/`.
5. Go to step 1.

The loop repeats about twice a second and the user never sees an error. It hits both the inbox and the dashboard (`PageHeader` has the same code). Compose only reads `BACKEND_URL` from `.env` (`docker-compose.yml:6`), and the middleware fallback is `http://localhost:8000` (`middleware.ts:3`). So a missing env var inside a container triggers the loop with no error message.
It also loops on a genuinely dead session if the logout endpoint needs auth and returns 401 without clearing the cookie **[backend, medium]**.
Also, if `logout()` itself rejects (network error), `handleSignOut` throws and nothing redirects.

Fix, in three parts. Sign out only on 401, show an error for anything else, and let the login page break the bounce:
```ts
// api.ts
export class ApiError extends Error { constructor(public status: number, m: string) { super(m); } }
export async function getMyTenant(): Promise<Tenant> {
  const res = await fetch('/api/v1/tenants/me');
  if (!res.ok) throw new ApiError(res.status, 'Failed to load account');
  return res.json();
}
// App.tsx and PageHeader.tsx
.catch((e) => (e?.status === 401 ? expire() : setLoadError('Cannot reach the server. Retrying...')));
// expire(): location.assign('/login?expired=1')   (do not depend on logout() succeeding)
// middleware.ts
const passThrough = req.nextUrl.searchParams.has('expired') || req.nextUrl.searchParams.has('ig_error');
if (hasSession && isLogin && !passThrough) return NextResponse.redirect(new URL('/dashboard', req.url));
```
`login/page.tsx` should also delete or ignore the stale cookie; only the backend can clear an httpOnly cookie, so keep `logout()` best-effort (`.catch(() => {})`).
The `ig_error` case in the fix above closes a related gap. Today, if a user with an old cookie starts Instagram login and it fails, `/login?ig_error=...` is redirected to `/` and the error is dropped.

**3. Human takeover reverts within 5 seconds.** (`App.tsx:122-139` vs `App.tsx:73-75`)
The button only edits local state. The next poll rebuilds every thread from the server (`{...t, messages}`), overwriting `status` and `escalationReason`. So "TAKE OVER AS HUMAN" and "RESOLVE & RE-ENABLE AI" do nothing that lasts, and the AI is not told to stop. If the backend keeps auto-replying while an operator types, both will answer the customer **[backend, unknown]**. Needs a PATCH endpoint such as `PATCH /conversations/{id} {mode}`. Until it exists, hide the buttons or mark them "local preview only".

**4. "AI DRAFT" can put a fake message into the box that sends to real customers.** (`InboxFeed.tsx:114-121`)
`askAi` 404s today (`api.ts:41`). The catch block then writes a canned Nepglish sentence ("...query review bhairakheko cha...") into the reply input. One click on SEND delivers it to a real Instagram user. On error, show an inline message and leave the input alone.

### P1

**5. Every real AI reply shows `CONFIDENCE: 0.00` and an empty `SOURCE:`.** (`InboxFeed.tsx:307-308, 330-333`; `api.ts:83-90`)
`MessageDto` carries no confidence or source, so `msg.confidence ?? thread.confidenceScore` is `undefined`. It renders `0.00`, which is below your 0.75 threshold, on genuine answers. Same story in the sidebar: `CONF: 0.00` on every card (`SidebarNav.tsx:208`). Render each badge only when the value exists. If the backend stores confidence, add it to the DTO **[backend]**.

**6. Every AI bubble is labelled "SocialSync AI (RAG-Enabled)", and system messages show as "Human Operator (Merchant)".** (`api.ts:85`, `InboxFeed.tsx:316, 359, 369`)
`sender_type` `system` and `agent` both map to `'human'`. The human bubble always says "OPERATOR OVERRIDE SENT VIA GRAPH API", even for a message that failed or one typed by someone else. Add a `'system'` sender and render it as a centred note. Rename the label to Sanchar.

**7. Channels modal edits overwrite the tenant name with the mock name.** (`MetaSettingsModal.tsx:61, 114-117`, `App.tsx:25, 54-62, 425-436`)
`bName` is initialised once, from `useState(businessName)`. The modal is mounted from the first render, when `businessName` is still the hard-coded "Himalayan Silk & Handicrafts (काठमाडौँ)" (`App.tsx:25`). The tenant name arrives later and `bName` never re-syncs. So the field shows the mock name, and clicking "Save Configuration" without touching it replaces the real header name with the mock one. It also saves nothing to the backend. Fix: `useEffect(() => setBName(businessName), [businessName, isOpen])`, and hide Save until there is a `PATCH /tenants/me`.

**8. A failed or slow send loses the text and can send twice.** (`InboxFeed.tsx:96-100, 102-106`, `App.tsx:142-157`)
- `handleSend` clears the input before the async send finishes. If the send fails, an `alert()` appears and the typed reply is gone.
- Enter triggers `handleSend` with no in-flight guard, so a double-press sends twice.
- Enter fires during Nepali/Devanagari IME composition (choosing a candidate). Guard with `if (e.key === 'Enter' && !e.nativeEvent.isComposing)`. This matters for your users.
- Instagram only allows replies within 24h of the customer's last message, so failures will be common. The footer claims "Meta Customer Service Window: Active" unconditionally (`InboxFeed.tsx:433`) and the header only shows it when `customerCity` exists, which real threads never have (`:161-164`). Compute the window from the last customer message time.

Fix: make `onSendMessage` return a promise, clear the input only on success, disable the button while pending, and show the error inline.

**9. Simulator actions corrupt real threads and can blank the chat pane.** (`App.tsx:182-206, 253-287, 76, 88-96, 102`)
- "SIMULATE CUSTOMER" appends a fake customer message to a real conversation. Messages are kept across polls, and the refetch only fires when `last_message_at` changes, so the fake bubble stays and looks like a real customer message.
- "+ INBOUND" creates `thread-<timestamp>` and sets it as `activeThreadId`. The next poll removes that thread, but `activeThreadId` stays stale. Meanwhile `activeThread` silently falls back to `threads[0]` (`:102`), while the messages effect keeps fetching the dead id and hitting the backend with a bad id. Result: the first real thread is shown with an empty chat pane until you click another thread.
- Both call `askAi`, which 404s (`:211, 291`).

Fix: validate the id on each poll (`setActiveThreadId(id => fresh.some(t => t.id === id) ? id : fresh[0]?.id ?? '')`), and put all simulator UI behind `process.env.NEXT_PUBLIC_DEV_TOOLS === '1'`.

**10. Fake connection status is shown as real.** (`mockData.ts:229-248`, `MetaSettingsModal.tsx:186-189, 194-198, 214-227, 401-405`, `RightInspector.tsx:182-213`, `PageHeader.tsx:38`)
- Facebook card: "LINKED & ACTIVE" with a made-up page name and ID. Nothing in the app can link Facebook, so this is always false.
- Instagram card: "VERIFIED" with `@himalayan_silk_np`, even though `ProfileModal` fetches the real account (`api.ts:149`). The two screens contradict each other for the account the user just logged in with.
- "ACTIVE CHANNELS" shows three lit icons and "Meta Webhooks 200 OK" (`RightInspector.tsx:210-212`). It is static.
- "PING WEBHOOKS" always succeeds after an 800 ms timer (`MetaSettingsModal.tsx:105-112`). Callback URL is `https://api.socialsync.np/v1/meta/webhook`, a hard-coded verify token sits in the client bundle (`:62`, it is a secret-looking string in shipped JS), and none of it matches the real webhook route `/api/v1/webhooks/*`.
- The only real card is WhatsApp (`getWhatsAppAccounts`).

Fix: drive the Instagram card from `getInstagramProfiles()`, the WhatsApp card as now, and show Facebook as "Not connected / coming soon". Derive the "ACTIVE CHANNELS" icons from those same calls. Delete `PING WEBHOOKS` and the fake URL/token block, or wire it to a real backend health call. A tenant with no channel linked should see an onboarding prompt, not a green board.

**11. New tenants land in an empty, unexplained screen.** (`InboxFeed.tsx:78-92`, `SidebarNav.tsx:145-149`, `dashboard/page.tsx:19-24`)
After a first Instagram login there are no threads. The inbox says "No Thread Selected: select a conversation from the left feed", but the left feed says "No threads match the selected filter" (wrong text when there is no data at all). The dashboard shows Instagram, WhatsApp and Facebook rows of zeros. Show only connected channels, and when there are none, show "Connect a channel" linking to `/?tab=settings`.

**12. Session expiry mid-use is silent.** (`App.tsx:78`, `api.ts:106-116`)
The poll does `.catch(console.error)` every 5 seconds forever. `getMyTenant` runs once at mount. After the cookie expires, the inbox freezes with stale data and no message. Have `api.ts` throw `ApiError(status)` from a shared `request()` helper, and on 401 anywhere redirect to `/login?expired=1`. The poll also keeps running in hidden tabs; skip it when `document.hidden`.

### P2

**13. Dashboard details** (`dashboard/page.tsx`, `api.ts:129`)
- Window fixed at `days=1`; no selector, no refresh, no auto-refresh. The inbox refreshes every 5 s, the dashboard never.
- A single error string replaces the page with no retry button.
- `counts[ch]` renders `undefined` if the backend omits a channel; use `counts[ch] ?? 0`.
- The escalation badge on the INBOX pill is `sum(handover)` over the window (`:41`), while in the inbox the same badge counts threads currently needing a human (`App.tsx:103`). Two numbers, same label. On the dashboard, pass `0` or fetch the live count.
- Duplicate React keys if two queries have the same text (`:62`, use `key={i}` or `text+count`).
- Your instant win: the Instagram data the user just logged in with (username, followers, posts) already exists (`getInstagramProfiles`) but is not shown on the dashboard.

**14. SEO and routing.** (`middleware.ts:19-22, 27`, `app/page.tsx:8`, `app/layout.tsx`)
- `/` is both the app and the home page, `ssr: false`, behind the login gate. A crawler is redirected to `/login` and sees no marketing content. If SEO matters, make `/` a public landing page (server component, in the matcher's allow list) and move the inbox to `/inbox` (and use `/dashboard` as the post-login page).
- The matcher `'/((?!api|_next|favicon.ico).*)'` no longer excludes paths with a dot (the `.bak` did: `.*\\..*`). Anything in `public/`, `robots.txt`, `sitemap.xml`, OG images will redirect to `/login` when logged out. Right now `public/` holds only `sanchar-mailbox.svg` (unreferenced) so nothing visibly breaks, but it will as soon as you add `robots.txt` or an OG image. Add `|.*\\..*` back, or list explicit public paths.
- The same matcher excludes any path that starts with `api` (`/apidocs`, `/api-keys`), and all of `/api/*` except `/api/v1` bypasses the auth gate (see the `app/api/meta/*` item under P3).
- One `<title>` for every page. `/dashboard` and `/login` are `'use client'`, so they cannot export `metadata`. Add a `metadata` export in tiny server `layout.tsx` files (`app/login/layout.tsx`, `app/dashboard/layout.tsx`), with `robots: { index: false }` on the app pages.
- No favicon and no `metadata.icons` (`public/sanchar-mailbox.svg` is unused); `/favicon.ico` is excluded from the middleware and 404s.
- Fonts are pulled from Google Fonts with a `<link>` (`layout.tsx:19-25`, five families, render-blocking). Use `next/font` before you care about Core Web Vitals.
- Two `<h1>`s on `/dashboard` (Header and page).

**15. Sidebar.** (`SidebarNav.tsx`)
- Thread cards are `<div onClick>`, not keyboard-reachable (line 158). Make them `<button>`s.
- The preview shows "No messages yet" for every thread except the open one (`:151, 190`), because messages load only for the active thread. Ask the backend for `last_message_preview` in `/conversations` **[backend]**.
- "N ACTIVE" is just `threads.length` (`:~68`). The conversation `status` field is fetched (`api.ts:62`) but never used, so closed conversations look active.
- Order is whatever the API returns; sort by `lastMessageAt` desc in the client.
- Channel filters for channels the tenant has not connected are always shown.
- Times are `HH:MM` only (`api.ts:80-81`). A conversation from last week and one from a minute ago look the same. Show the date when older than today.

**16. Mapping `mode` to "needs human" is too broad.** (`api.ts:102`)
`c.mode === 'ai' ? AUTO_PILOT : NEEDS_HUMAN`. Any other value (`human`, `paused`, a new mode, null) becomes a pulsing red "HUMAN ESCALATION REQUIRED" banner, "HIGH PRIORITY" and a header count. The AI layer is not shipped yet (`api.ts:41`, "M4"), so if conversations default to a non-`ai` mode, every thread will scream "needs human" **[backend, unknown default]**. Map `'human'` explicitly and treat unknown values as neutral.

**17. Chat pane never scrolls to the newest message.** (`InboxFeed.tsx:284-374`)
There is no ref, `scrollIntoView` or `scrollTop` anywhere in `src/` or `app/`. Open a long conversation, or send a reply, and you stay at the top. There is also no loading or empty state for a thread whose messages are still loading, and no pagination on `/messages`.

**18. Mock content still visible everywhere.** (`RightInspector.tsx:92-119`, `Footer.tsx:20-26`, `Header.tsx:50, 165`, `App.tsx:99-100`)
- Catalog, delivery prices, "Discount policy ... VINTAGE5" and FAQs come from `mockData.ts`. The AI will not use them; they live only in React state.
- Footer: `LATENCY 1.2s` (120 ms divided by 100 and labelled seconds, so it is also wrong arithmetic), `TOKEN_USAGE: 412/10000`, "SOCIALSYNC AI", and "META GRAPH API v21.0 ACTIVE" are static. Same "v21.0" text appears in login, header and modals.
- Avatar initials fall back to `'NP'` for every user (`Header.tsx:165`).
- Login page claims ("FREE FOREVER", "ESTD. 1932", "GDPR / Nepal Telecomm Ready", "Meta Graph v21.0 Compliant") are marketing copy that Meta app review or a customer could hold against you.

**19. Login form.** (`login/page.tsx:212-237, 244-249`)
- The two `<label>`s have no `htmlFor`, so they are not associated with their inputs; a screen reader announces unlabeled fields and clicking the label does nothing.
- "terms of service" and "privacy policy" are `<span>`s, not links (Meta requires a privacy policy URL, and a data-deletion URL for Instagram/Facebook login, before app review).
- `ig_error` and `ig_error_description` are echoed straight from the URL (`:24`). React escapes them, so it is not XSS, but anyone can craft a `/login?ig_error=...` link with arbitrary support-scam text. Map known codes to fixed messages.
- After login there is no `next` parameter, so deep links (`/dashboard`) are lost.

### P3: cleanup

- **`app/api/meta/*`** (`webhook`, `webhook-logs`, `test-connection`, `_logs.ts`) is dead mock code and is publicly reachable, because the matcher skips `/api/*`. `POST /api/meta/webhook` is unauthenticated with no HMAC check and lets anyone fill the in-memory log; `GET /api/meta/webhook-logs` returns those payloads to anyone; `test-connection` always says `success: true`. Meta's real webhooks go to FastAPI. Delete the folder.
- **`app/api/health/route.ts`**: names "SocialSync" and reports whether `GEMINI_API_KEY` is set, to anyone. Reduce to `{status:'ok'}` if you use it as a Docker/uptime probe.
- **`app/api/amit/page.tsx`** is an empty page at a public URL `/api/amit`. Delete.
- **`middleware.ts.bak`** and **`tsconfig.tsbuildinfo`** are tracked in git. Delete the first; `git rm --cached` the second and add `*.tsbuildinfo` to `.gitignore`.
- **`conversation_example.json`** is tracked and contains real Instagram usernames and IDs of third parties. Remove it from the repo (and consider history).
- `npm run lint` uses `next lint` but neither `eslint` nor `eslint-config-next` is in `package.json`, so it cannot work.
- `Header.tsx` takes `metaStatus` but never uses it; `PageHeader` passes the mock anyway (`:38`). `Header` has a `LOGIN / SIGN UP` branch (`:449-457`) with no handler that cannot be reached.
- `types.ts` has many unused fields (`MerchantSettings`, `ChannelConnection`, `windowExpiresAt`, ...); drop them as you go.
- `Dockerfile` runs as root and has no healthcheck; add `USER node` (or `nextjs`) and a healthcheck against `/api/health`.
- `public/assets/aistudio/` is an empty directory.
- Webhook exclusion (`middleware.ts:11-13`) only works if a proxy (nginx) sends `/api/v1/webhooks/*` straight to FastAPI. If someone hits port 3000 directly (as `docker-compose.yml` publishes), the request passes through `NextResponse.next()`, finds no route and gets a 404, and Meta will mark the webhook as failing. Fine in production behind nginx; a trap on a dev box or during Meta's webhook verification. Whether a middleware rewrite would really break the HMAC (as the comment says) I did not verify; a rewrite proxies the raw body in most cases.

## 3. Things that depend on the backend (please check)

## 5. Quick manual test script (about 10 minutes)

1. Stop the backend, open `/`. Before the fix: reload loop in the Network tab. After: an error message and no loop.
2. Log in with Instagram on a fresh browser. You should land on `/dashboard`, and the dashboard should list only connected channels.
3. Delete the `ns_session` cookie in DevTools while on `/`. The next poll should send you to `/login`.
4. Open a thread with more than a screen of messages. It should be scrolled to the bottom.
5. Click "TAKE OVER", wait 6 s. Status should stay (once the PATCH exists).
6. Type a reply, stop the backend, press Enter twice quickly. The text must stay in the box and only one request must fire.
7. Type Nepali with an IME and press Enter to pick a candidate. It must not send.
8. While logged out, request `/robots.txt`. Expect 200, not a redirect.

## Assumptions

- The product goal is that a tenant whose first login is Instagram sees `/dashboard` first, with `/` free to become a public landing page later. If you prefer the inbox as home, #1 becomes "add a dashboard summary strip on the inbox" and only #2 and the rest still apply.
- `ns_session` is the backend's session cookie name, as the middleware and comments say. I did not read `.env` (it may hold secrets).
- I treated `tsc` results as unknown rather than re-running them, since a run would modify files in the project.
