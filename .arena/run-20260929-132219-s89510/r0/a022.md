# Review and flow check: Instagram login, dashboard, conversations

I read every file in the flow and ran `npx tsc --noEmit --incremental false`, which passes with no errors. I did not run the app against your backend. Findings that depend on FastAPI behaviour I can't see are marked **[backend?]**.

## Verdict

The login-to-inbox path works. Your intended flow does not: the tenant never sees the dashboard first, there is no way to link Instagram or Facebook once logged in, and several screens show fake "connected" data.

The most serious problem is not a cosmetic one. A dead session can put the browser into an endless redirect loop between `/login` and `/` (bug 2).

## Assumptions

- "Dashboard" means `/dashboard`, and "conversations" means the inbox at `/`.
- Instagram OAuth is completed by FastAPI, which sets the `ns_session` cookie and redirects the browser.
- The 5-second polling and the single-tenant-per-cookie model are intentional for this stage.

## Worked example: a new tenant logs in with Instagram

Priya has a shop on Instagram and no WhatsApp or Facebook page linked. I traced what she sees, step by step.

1. **She clicks "Continue with Instagram".** `login/page.tsx:189` sets the loader and follows the `<a href="/api/v1/social-accounts/instagram/login">`. Middleware rewrites it to FastAPI (`middleware.ts:15-17`).
2. **Instagram redirects back to the backend callback.** The backend sets `ns_session` and redirects somewhere **[backend?]**. If it redirects to `/`, or to `/login`, she ends up in the inbox. `middleware.ts:22` sends any logged-in visitor on `/login` to `/`. Nothing in this repo ever sends her to `/dashboard`.
3. **The inbox mounts.** For the first moments she sees "Himalayan Silk & Handicrafts (काठमाडौँ)" as her business name (`App.tsx:25`) and a dead "LOGIN / SIGN UP" button (`Header.tsx:185-192`, no handler is ever passed) until `/tenants/me` answers.
4. **The sidebar loads.** Threads arrive with "No messages yet" previews and `CONF: 0.00` badges. The first thread opens automatically (`App.tsx:76`), but the message pane sits at the top of the history, not the latest message.
5. **She opens Channels.** The Facebook card says "LINKED & ACTIVE" with a page she has never heard of. The Instagram card says "VERIFIED @himalayan_silk_np". The only real card is WhatsApp.
6. **She clicks DASHBOARD.** She gets a page of zeros for WhatsApp and Facebook, with no prompt to connect anything.

Every step after 1 breaks or misleads a first-time user. The ranked list below is what that trace turned up, plus the edge cases behind it.

## Ranked findings

### Critical: blocks the flow or can lock the user out

**1. Login never lands on the dashboard.**
- Locations: `middleware.ts:22` and `login/page.tsx:37` both go to `/`. `/` is the inbox (`app/page.tsx`).
- Options:

| Option | Covers Instagram | Covers email | Cost | Risk |
|---|---|---|---|---|
| A. Middleware `hasSession && isLogin` goes to `/dashboard`, and the email login does `assign('/dashboard')` | only if the callback lands on `/login` | yes | 2 lines | none |
| B. Make `/` redirect to `/dashboard` | yes | yes | 1 line | kills the inbox URL and breaks `/?tab=…` used by `PageHeader.tsx:37` |
| C. Change the backend callback redirect | yes | no | backend change | cannot verify **[backend?]** |

- Do A now, and check what C does today. If the backend redirects to `/`, add `if (hasSession && pathname === '/' && !req.nextUrl.searchParams.has('tab') && req.cookies.get('ns_first') …)` only if you want first-login-only behaviour. Otherwise move the inbox to `/inbox` (see the SEO section), which makes B clean.

```diff
-  if (hasSession && isLogin) return NextResponse.redirect(new URL('/', req.url));
+  if (hasSession && isLogin) return NextResponse.redirect(new URL('/dashboard', req.url));
```
```diff
-      window.location.assign('/'); // full load so middleware sees the new cookie
+      window.location.assign('/dashboard'); // full load so middleware sees the new cookie
```

**2. A dead session can cause an infinite redirect loop, or a stuck blank page.**
- Locations: `App.tsx:54-62`, `PageHeader.tsx:27-31`, `middleware.ts:19-22`.
- Cause: `getMyTenant().catch(handleSignOut)` treats any failure as a dead session. That includes a 500, a proxy error, or the backend restarting during a deploy.
- Failure mode 1, loop: `handleSignOut` calls `logout()` and then goes to `/login`. If the logout call returns 401 or 5xx and does not clear the cookie **[backend?]**, middleware sees the cookie on `/login` and bounces to `/`. `/` calls `/tenants/me`, which fails again, and the cycle repeats. The code comment claims this is handled; it is handled only if logout succeeds.
- Failure mode 2, stuck: if the backend is completely down, `fetch` in `logout()` throws. `window.location.assign` on the next line never runs, so the user stays on a half-rendered inbox with nothing telling them why.
- Fix: distinguish 401 from everything else, and make `/login` reachable even with a stale cookie.

```diff
 // api.ts
-  if (!res.ok) throw new Error('Not authenticated');
+  if (!res.ok) throw Object.assign(new Error('Not authenticated'), { status: res.status });
```
```ts
// App.tsx and PageHeader.tsx
.catch((e) => {
  if (e.status === 401) {
    logout().catch(() => {}).finally(() => window.location.assign('/login?reauth=1'));
  } else {
    setLoadError(e.message); // show a retry banner; do not sign the user out
  }
});
```
```diff
 // middleware.ts
-  if (hasSession && isLogin) return NextResponse.redirect(new URL('/dashboard', req.url));
+  if (hasSession && isLogin && !req.nextUrl.searchParams.has('reauth') && !req.nextUrl.searchParams.has('ig_error'))
+    return NextResponse.redirect(new URL('/dashboard', req.url));
```
- The `ig_error` clause fixes a related bug. If someone with a stale cookie fails Instagram login, the error is currently thrown away because middleware redirects them away from `/login` before the page can read `?ig_error=`.
- The inbox poll needs the same 401 handling: `App.tsx:78` is `.catch(console.error)`, so a session that expires mid-use fails silently every 5 seconds.

**3. No way to link Instagram or Facebook after you are logged in.**
- Instagram can only be started from the login page (`INSTAGRAM_LOGIN_URL`, `api.ts:29`, used only in `login/page.tsx:188`). A logged-in visitor to `/login` is redirected away, and the Channels modal has no Instagram button.
- `ProfileModal.tsx:68` tells the user to "Log in with Instagram again to refresh", but there is no button or link for that.
- Facebook has no API call anywhere (`grep` of `api.ts` finds none). The Facebook card is pure mock (bug 6).
- An email-login tenant therefore has no path to connect Instagram at all.
- Fix: add a real "Connect Instagram" link to `INSTAGRAM_LOGIN_URL` in the Channels modal and the profile modal. It is an API URL, so middleware will not bounce it. Show "Connect Facebook" as disabled with "coming soon" until the backend has an endpoint.

### High: wrong or misleading behaviour

**4. Channels modal shows fake state and can overwrite the real business name.**
- `MetaSettingsModal.tsx:186-189` hardcodes "LINKED & ACTIVE", and `:214-216` hardcodes "VERIFIED". The names and IDs come from `initialMetaStatus` (`mockData.ts:229-247`).
- `MetaSettingsModal.tsx:61`: `useState(businessName)` runs once, when `App` first renders with the fake "Himalayan Silk…" name. The modal never re-syncs. So the "Merchant Business Name" field shows the fake name.
- Clicking "Save Configuration" (`:114-117`) calls `onUpdateBusinessName(bName)`, which replaces the real tenant name in the header with the fake one. Nothing is saved to the backend either way.
- `:105-112` "PING WEBHOOKS" always reports "HTTP 200 OK" after a timer. `:62` and `:401` show a hardcoded verify token and a `socialsync.np` callback URL. If that token is real, it is shipped to every browser **[backend?]**.
- Fix:
  - Drive the Instagram card from `getInstagramProfiles()`, which already exists at `api.ts:149` and is what `ProfileModal` uses.
  - Remove the Facebook card until it is real.
  - Delete the fake ping and the token block, or replace them with the real WhatsApp checks already in `waChecks`.
  - Initialise `bName` from the loaded tenant name and add a `useEffect` to re-sync.
  - Replace the hardcoded default name at `App.tsx:25` with `''`.

**5. The takeover button reverts within 5 seconds.**
- `App.tsx:122-139` only changes local state. `App.tsx:73-75` replaces every thread from the server on each poll, and `api.ts:102` derives `status` from `mode`. The toggle and `escalationReason` are wiped on the next poll.
- The backend appears to have `mode` ('ai' or otherwise). The frontend needs a `PATCH /conversations/{id}` call **[backend?]**. Until then, disable the button, because it currently lies.

**6. The dashboard is an unfinished screen.**
- `dashboard/page.tsx:54-70`: fixed `days=1` (`api.ts:129`), no range selector and no refresh.
- It always renders WhatsApp, Instagram and Facebook rows. Priya sees three lines of zeros with no next step. Add an empty state that links to Channels.
- `:41` labels the INBOX badge with the sum of `handover` over the window. The inbox badge (`App.tsx:103`) counts threads currently in `NEEDS_HUMAN`. Two different numbers share one label. On the dashboard, show nothing on the badge, or fetch the current count.
- Crashes on partial data: `Object.values(data.handover)` at `:41` throws if the backend omits `handover`. There is no `error.tsx`, so this white-screens the whole page. Guard with `data?.handover ?? {}` and `data.top_queries ?? []`.
- A missing channel key renders `undefined`. Default to `?? 0`.
- Duplicate `key={q.text}` at `:62` can warn if two queries are identical after trimming.
- This is the page the user wants as the landing page, so it needs the most polish.

**7. Message pane does not scroll to the latest message.**
- `InboxFeed.tsx:285` renders `thread.messages` in an `overflow-y-auto` div. A grep of `src/` for `scrollIntoView` and `scrollTop` finds nothing.
- Opening a long conversation shows the oldest messages, and a new customer message arriving from the poll appears off-screen.
- Fix: keep a `ref` on the container and set `scrollTop = scrollHeight` when `thread.id` or `thread.messages.length` changes. Also sort by `created_at` on the client in case the backend order isn't guaranteed **[backend?]**.

**8. Sidebar previews are empty for every thread you haven't opened.**
- `SidebarNav.tsx:151` reads `thread.messages`, but messages are only fetched for the active thread (`App.tsx:89-96`). Every other card says "No messages yet" even when it has hundreds.
- Fix: ask the backend to include `last_message_preview` in `/conversations` **[backend?]**.

**11. Simulator and AI-draft features call an endpoint that 404s.**

**13. Filters can hide the open conversation.**

## Cleanup and exposure

- **`app/api/meta/*` is reachable without login.** The middleware matcher excludes anything starting with `api` (`middleware.ts:27`). `GET /api/meta/webhook-logs` returns whatever anyone POSTed to `/api/meta/webhook`, which does no signature check and keeps payloads in memory.
- The same prefix rule makes `/api/health` public. It reports `hasGeminiKey` and says "SocialSync AI".
- Delete `app/api/meta/`, `app/api/amit/page.tsx` (an empty page), `middleware.ts.bak`, and the empty `public/assets/aistudio/`.
- `git rm --cached tsconfig.tsbuildinfo` and add it to `.gitignore`.
- `conversation_example.json` is tracked and contains real Instagram usernames and IDs. Move it out or anonymise it.
- `mockData.ts` exports `initialThreads`, which nothing imports.
- The `lint` script runs `next lint`, but ESLint isn't installed, so it will prompt or fail in CI.
- Webhooks: `middleware.ts:11-13` lets `/api/v1/webhooks/` fall through to Next, which has no such route. That is correct only if nginx routes it to FastAPI first. In `docker-compose.yml` there is no nginx, so a Meta webhook aimed at port 3000 gets a 404 **[backend?]**.

## SEO and Meta review readiness

- **Static files redirect to login.** The old `middleware.ts.bak` matcher excluded files with an extension (`.*\\..*`). The current one doesn't, so `/robots.txt`, `/sitemap.xml`, `/sanchar-mailbox.svg` and OG images redirect a logged-out crawler to `/login`. Restore the exclusion:

```ts
matcher: ['/((?!api/|_next/|favicon.ico|.*\\..*).*)', '/api/v1/:path*'],
```
Note the `api/` with a slash. The current `api` also skips routes like `/apiary` by prefix.

- **Only `/login` is crawlable, and it has no own metadata.** The layout has no `metadataBase` and no OG image. It sets `lang="en"` on pages full of Nepali, and loads fonts with a `<link>` instead of `next/font`.
- **`/` and `/dashboard` are gated.** For SEO you need a public marketing route. Move the inbox to `/inbox`, make `/` a server-rendered landing page, and add `robots.ts` and `sitemap.ts`. Keep `/dashboard` and `/inbox` `noindex`.
- **Terms and privacy are plain `<span>`s** (`login/page.tsx:246-248`). Meta app review needs real URLs for privacy policy, terms and a data-deletion instruction for Instagram and Facebook login.
- **The login page is `select-none`**, so users can't copy the error text. It also reflects `ig_error` text from the query string (`:24`). React escapes it, so it isn't XSS, but anyone can craft a link that shows arbitrary text on your domain. Show a fixed message per known code instead.
