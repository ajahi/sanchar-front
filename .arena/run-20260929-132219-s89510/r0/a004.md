# Flow check: Instagram login -> dashboard -> conversations

I read every file in the flow. I did not run it against your backend. Findings that depend on FastAPI behaviour are marked **[backend]**.

## Verdict

The chain login -> session cookie -> inbox -> messages -> reply is wired to real endpoints and should work. It differs from your intended flow in three ways:

1. A user who logs in lands on the **inbox**, not the dashboard.
2. **Several screens show fake "connected" or "working" state.** They can lead a tenant, or you while testing, to think something works when it doesn't.
3. **Two dev-only features can send fake text to real customers.**

Ranked below, worst first.

## The flow as the code runs it

| Step | What happens | Where |
|---|---|---|
| 1 | `/login` has a plain `<a href="/api/v1/social-accounts/instagram/login">`. Middleware rewrites it to FastAPI, which redirects to Instagram. | `login/page.tsx:225`, `middleware.ts:15` |
| 2 | The backend callback sets the httpOnly `ns_session` cookie and redirects somewhere. **[backend] I can't see where.** On failure it must redirect to `/login?ig_error=...`, and the page shows that. | `login/page.tsx:60-63` |
| 3 | With a cookie, `/login` redirects to `/`. Email login also does `assign('/')`. | `middleware.ts:22`, `login/page.tsx:76` |
| 4 | `/` is the inbox. It calls `/tenants/me` once, then polls `/conversations` every 5s. Messages load only for the open thread. | `App.tsx:54-96` |
| 5 | `/dashboard` is a separate page reached only by the header **DASHBOARD** link. | `Header.tsx:549` |

## Blocking or wrong (fix first)

**1. Login does not land on the dashboard.**
- Both frontend paths go to `/` (`middleware.ts:22`, `login/page.tsx:76`).
- The Instagram callback target is on the backend.
- Frontend fix: change `'/'` to `'/dashboard'` in those two places.
- If the callback redirects to `/`, the tenant still sees the inbox. Two ways to close that:
  - Point the backend callback at `/login`. Middleware then bounces a user with a session to `/dashboard`. This is the cheapest way.
  - Or change the backend callback to `/dashboard`.
- Better long term: make `/` the dashboard and move the inbox to `/inbox`. That also fixes item 9.

**2. Fake "Save" wipes the real business name.**
- `MetaSettingsModal` is always mounted (`App.tsx:425`).
- `useState(businessName)` (`MetaSettingsModal.tsx:61`) runs once, with the mock name "Himalayan Silk & Handicrafts (काठमाडौँ)" from `App.tsx:25`.
- It never picks up the real tenant name that arrives later.
- Open **CHANNELS** and click **Save Configuration**. `onUpdateBusinessName(bName)` then overwrites the header with the mock name.
- Nothing is persisted either way.
- Fix: `useEffect(() => setBName(businessName), [businessName, isOpen])`. Better, remove the field or wire it to a real PATCH.

**3. "AI DRAFT" puts a canned Nepali reply into the send box when the call fails.**
- `/api/v1/ai/reply` doesn't exist yet (`api.ts:41` says it 404s).
- The `catch` at `InboxFeed.tsx:120` writes "Namaste! Hamro store bata hajur ko query review bhairakheko cha..." into the input.
- One click on SEND delivers it to a real Instagram customer.
- The four canned buttons (`InboxFeed.tsx:127-132`) work the same way. They include a fake coupon `VINTAGE10` and a fake tracking link.
- Fix: on error show an inline error and leave the input empty. Hide AI DRAFT and the canned replies until the backend endpoint exists, or gate them behind `NEXT_PUBLIC_DEV_TOOLS`.

**4. Human takeover reverts within 5 seconds.**
- `handleToggleTakeover` (`App.tsx:122`) only edits local state.
- The poll at `App.tsx:73-75` rebuilds every thread from the server `mode`.
- The button appears to work, then flips back. The AI may keep replying.
- **[backend]** It needs something like `PATCH /conversations/{id}` with `{mode}`.
- Until then, disable or hide the button.

**5. Static files and `robots.txt` redirect to `/login` for logged-out visitors.**
- The matcher at `middleware.ts:27` dropped `.*\\..*`. The old `middleware.ts.bak` had it.
- `robots.txt`, `sitemap.xml`, `og:image` and `/public/*` (including `/sanchar-mailbox.svg`) are all redirected.
- This breaks the SEO you mentioned.
- Fix: `matcher: ['/((?!api|_next|favicon.ico|.*\\..*).*)', '/api/v1/:path*']`.
- Check that `/api/v1/*` still matches through the second entry. Since `/api/v1/x` has no dot, either way works.

## Fake state that misleads

**6. Channels modal shows Facebook "LINKED & ACTIVE" and Instagram "VERIFIED" from mock data.**
- Source: `mockData.ts:229`, used at `MetaSettingsModal.tsx:186-228`. The values are "Himalayan Silk" and `@himalayan_silk_np`.
- A tenant with nothing connected sees green badges.
- Only the WhatsApp card is real (`getWhatsAppAccounts`).
- Fix for Instagram: use `getInstagramProfiles()`, which already exists and `ProfileModal` uses it.
- Facebook has no backend call at all. Show "Not connected", not green.
- `PageHeader.tsx:6,38` and `App.tsx:31` also pass the mock status to `Header`. `Header` ignores it (it isn't destructured), so remove the prop.

**7. "PING WEBHOOKS" always returns "HTTP 200 OK".**
- It is a bare `setTimeout` (`MetaSettingsModal.tsx:105-111`).
- The displayed callback URL `https://api.socialsync.np/v1/meta/webhook` and verify token `socialsync_meta_wh_sec_991823` (lines 62, 401) are invented.
- The real webhook is `/api/v1/webhooks/...`, per `middleware.ts:11`.
- Remove this block. The WhatsApp card's three checks are the real ping.

**8. Hard-coded status text.**
- `InboxFeed.tsx:163` and `:429`: "Meta 24h Window: Active", "Customer Service Window: Active • E2E Verified". These are constants.
- `RightInspector.tsx`: "RAG ACTIVE" (~l.31), "ACTIVE CHANNELS" (~l.185), "Meta Webhooks 200 OK" (~l.211).
- `Footer.tsx`: "META GRAPH API v21.0 ACTIVE", and the token usage / latency numbers (`App.tsx:99-100`).
- Instagram DMs do have a real 24-hour reply window, so the false "Active" matters. A send outside it fails, and today it surfaces as `alert()` (`App.tsx:155`).
- Fix: show the window only if the backend gives an expiry (`windowExpiresAt` exists in `types.ts:114` but is never set). Otherwise remove it. Replace `alert` with inline text.

**9. Inbox sidebar: preview and confidence are wrong.**
- The preview reads `thread.messages`, which only the open thread has (`SidebarNav.tsx:151,190`). Every other thread says "No messages yet".
- `CONF: 0.00` (`SidebarNav.tsx:208`) shows on every real thread, because `confidenceScore` is never set from the API.
- Fix: hide the badge when `confidenceScore` is undefined.
- **[backend]** For previews, `/conversations` should return a `last_message` text field.

**10. Dev tools shown in the production UI.**
- The `+ INBOUND` button, `SIMULATE CUSTOMER`, and the RAG sandbox all call the missing `/ai/reply`.
- Simulated threads use ids like `thread-<ts>`. The next poll (5s) deletes them, because `App.tsx:73` rebuilds from the server list.
- `RightInspector`, the Catalog and FAQs modals, and `RightInspector`'s "EDIT ALL (4)" all show mock inventory (Pashmina, singing bowl). Edits are lost on refresh.
- Fix: hide these behind one flag until they are real.

## The dashboard page

- It is not the "all metrics" view you described.
  - It has 4 tiny text blocks: new messages, handled, handover, and top queries. Window is fixed at `days=1` (`api.ts:205`).
  - It has no selector, no refresh, and no conversation list.
- It always lists WhatsApp, Facebook and Instagram (`dashboard/page.tsx:8-12`). A tenant who just signed in with Instagram sees zeros for the other two, with no "connect a channel" prompt.
  - Suggested fix: show only connected channels, or add a call to action linking to Channels.
- Trust in the response: if the backend omits a channel key, `counts[ch]` renders as blank (React drops `undefined`). Use `counts[ch] ?? 0`.
- The header badge on the dashboard (`page.tsx:41`) is the sum of handover counts for the window, but the inbox badge (`App.tsx:103`) counts threads currently `NEEDS_HUMAN`. Two different numbers under the same label.
- The dashboard is reachable from the inbox only through the header link. Add a dashboard <-> inbox link in both directions if the dashboard becomes the landing page.

## Conversations by social media

- The sidebar is one flat list with IG / WA / FB filter chips (`SidebarNav.tsx:71-116`). It is not grouped per channel.
- The chips always show all three channels, connected or not.
- Clicking a thread does load its messages (`App.tsx:89-96`, refetched when `lastMessageAt` changes). This part of your flow works.
- **[backend]** Thread order isn't sorted client-side, and the list is not paginated. Both depend on the API.
- The sidebar still shows a thread if a channel filter is applied and the open thread doesn't match it.

## Auth and session

- Expired sessions are handled at first load only. `getMyTenant` failing calls `handleSignOut` (`App.tsx:61`). The 5s poll just does `console.error` (`App.tsx:78`), so a cookie that dies mid-session leaves a frozen inbox.
  - Fix: if `/conversations` returns 401, sign out.
- Dashboard 401s show a raw "Failed to load dashboard (401)" (`dashboard/page.tsx:34,44`). The header's `getMyTenant` does sign the user out, so this is mostly fine.
- Polling continues in background tabs. Pause on `document.hidden`.
- Middleware only checks that `ns_session` exists (`middleware.ts:19`). That's fine for UX, but the API is the real gate.
- **[backend]** `/api/v1/auth/logout` must clear the cookie even for a dead session, or `/login` bounces back to the app.
- `BACKEND_URL` is read from `process.env` in middleware. The comment says it's runtime. Confirm it in the built image: the container reads it at runtime through `env_file: .env` (`docker-compose.yml`), but `.dockerignore` excludes `.env*`.

## Cleanup and public-facing risks

- `app/api/meta/*` is dead mock code.
  - `test-connection` always succeeds.
  - `webhook` (`route.ts`) is unauthenticated and does no HMAC check. It logs whatever is posted into memory.
  - The middleware matcher excludes `/api/*`, so these routes are public and behind no login.
  - The real webhook is on FastAPI. Delete the folder.
- `app/api/health/route.ts` is public. It names "SocialSync AI" and leaks `hasGeminiKey`. Return `{status:'ok'}` only.
- `app/api/amit/page.tsx` returns `null` and is reachable at `/api/amit`. Delete it.
- Delete `middleware.ts.bak` and untrack `tsconfig.tsbuildinfo`.
- `conversation_example.json` is committed, with real Instagram ids and usernames. Remove it from git.
- `mockData.ts` `initialThreads` is unused (dead). "SocialSync" branding remains in `InboxFeed.tsx:316`, `InventoryModal.tsx:284`, `Footer.tsx:371`. Product name is Sanchar.
- Login page (`login/page.tsx`):
  - "terms of service" and "privacy policy" are `<span>`s (lines 285, 287), not links. Meta app review needs a real privacy policy URL and a data-deletion URL for Instagram/Facebook Login.
  - Marketing claims that aren't true yet: "FREE FOREVER", "GDPR / Nepal Telecomm Ready", "Meta Graph v21.0 Compliant", "ESTD. 1932", "PRICE 50 PAISA".
  - The Instagram button sets `isLoading` (line 228), which puts up a full-screen loader. If the backend answers with an error page, the user leaves the app with no way back except Back. The `pageshow` handler covers only bfcache.
  - Facebook and WhatsApp are listed as features, but there is no login for them. Facebook linking has no UI at all.
  - The heading says "Log in", while the email/password form asks for a "Work email" even though the flow is Instagram-first. Decide whether email login is kept.

## SEO (later)

- Only `/login` is crawlable, and it has no metadata of its own. The whole site shares one title from `layout.tsx`.
- There is no `robots.txt` or sitemap.
- The inbox is `ssr:false` and behind login, which is right for a private app. Add `robots: {index:false}` metadata for it.
- Plan: a public landing at `/`, the inbox at `/inbox`, the dashboard at `/dashboard`. Then also fix item 5.
- Fonts are loaded by a `<link>` in `<head>` (`layout.tsx`). Use `next/font` to avoid render-blocking.

## Suggested order of work

1. Items 1, 2, 3, 5 (about an hour). These change what users see and what can be sent.
2. Items 4, 6, 7, 8, 9: replace mock status with real calls or remove it.
3. Delete dead code and the public mock API routes.
4. Ask the backend for: the callback redirect target, `PATCH` mode, `last_message` in the list, and a 24h window expiry.
