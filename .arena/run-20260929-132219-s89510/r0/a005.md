# Sanchar frontend: review and flow check (Instagram login -> dashboard -> conversations)

## Verdict

The plumbing works. The `/api/v1` proxy, the session cookie check, Instagram login as a plain link, the inbox polling, and the message and attachment rendering are all sound. `npx tsc --noEmit --incremental false` passes (I turned incremental off so it does not rewrite the tracked `tsconfig.tsbuildinfo`). I did not run `next build` or the app against a backend.

Against your intended flow, five things stand out:

1. **Instagram login does not land on the dashboard.** It lands on the inbox (`/`).
2. **A backend hiccup can put a logged-in user into an endless reload loop.** This is the most dangerous bug in the flow.
3. **"Take over as human" does nothing on the server**, so the AI keeps replying to a customer the merchant thinks they took over.
4. **The inbox looks like a demo in many places.** Fake connection status, canned replies with fake coupon codes, and hard-coded "Active" and "200 OK" badges all show for a real tenant. Some of these can be sent to real customers.
5. **Nothing marketing- or Meta-review-related can be public yet.** The middleware redirects every path except `/login`.

Findings marked (B) depend on backend behaviour I cannot see. Line numbers refer to the files as they are now.

## 2. Findings, ranked

### Critical (blocks the flow or can hurt real customers)

**C1. The Instagram login lands on the inbox, not the dashboard.**
- Where: `middleware.ts:22`, `login/page.tsx:37`, and the backend's OAuth callback redirect (B).
- Fix:
```diff
--- middleware.ts
-  if (hasSession && isLogin) return NextResponse.redirect(new URL('/', req.url));
+  if (hasSession && isLogin) return NextResponse.redirect(new URL('/dashboard', req.url));
--- app/login/page.tsx
-      window.location.assign('/'); // full load so middleware sees the new cookie
+      window.location.assign('/dashboard'); // full load so middleware sees the new cookie
```
- Also have FastAPI redirect to `/dashboard` after the Instagram callback.
- If the backend cannot change quickly, an interim fix is to send an authenticated `/` request with `Sec-Fetch-Site: cross-site` to `/dashboard` in the middleware. That is a heuristic and I have not verified it against your callback, so prefer the backend change.
- Cleaner long term: `/` redirects authenticated users to `/dashboard` and the inbox moves to `/inbox` (see S1). Then no login path can land on the inbox by accident.

**C2. Any non-401 failure of `/tenants/me` causes an endless reload loop.**
- Where: `App.tsx:54-62` and `PageHeader.tsx:27-31`. The `.catch(handleSignOut)` runs on any error, including the backend being down or restarting, a network blip, or a 500.
- `handleSignOut` (`App.tsx:47-50`) awaits `logout()`, which hits the same dead backend. The proxy returns 502/500, the cookie is not cleared, and `location.assign('/login')` runs. The middleware sees the cookie and redirects `/login` to `/`, `getMyTenant` fails again, and the cycle repeats with full page loads.
- If the network call itself rejects, `await logout()` throws and `location.assign` never runs, so the user sits on a half-broken page.
- This will happen during every backend deploy or restart in testing.
- Fix: sign out only on a real 401, and show a retry banner otherwise.
```diff
--- src/api.ts
 export async function getMyTenant(): Promise<Tenant> {
   const res = await fetch('/api/v1/tenants/me');
-  if (!res.ok) throw new Error('Not authenticated');
+  if (!res.ok) throw Object.assign(new Error(`Tenant lookup failed (${res.status})`), { status: res.status });
   return res.json();
 }
 export async function logout(): Promise<void> {
-  await fetch('/api/v1/auth/logout', { method: 'POST' });
+  await fetch('/api/v1/auth/logout', { method: 'POST' }).catch(() => {});
 }
--- src/App.tsx (and the same in PageHeader.tsx)
-      .catch(handleSignOut);
+      .catch((e) => (e.status === 401 ? handleSignOut() : setLoadError('Cannot reach the server. Retrying...')));
```
- A 401 that logout cannot clear (cookie is httpOnly, backend down) can still bounce. Have the middleware skip the `/login` to `/` redirect when the URL has `?expired=1`, and use that on the sign-out redirect.

**C3. "Take over as human" is local-only, so the AI keeps auto-replying.**
- Where: `App.tsx:122-139` flips `status` in local state. Nothing tells the backend. The 5-second poll (`App.tsx:67-85`) then overwrites `status` with `mode` (`api.ts:102`), so the toggle reverts.
- The real consequence is worse than a flicker. The merchant sees "HUMAN TAKEOVER ACTIVE" for a few seconds, believes the bot is paused, and the bot keeps answering the customer.
- Also: `escalationReason` is set locally with the text "Manual operator takeover initiated by merchant" and is lost on the next poll.
- Fix (B): add a `PATCH /api/v1/conversations/{id}` with `{mode: 'human' | 'ai'}`, call it in `handleToggleTakeover`, and update state from the response. Until it exists, hide the button. A control that does nothing is worse than none.

**C4. Hard-coded canned replies and fallbacks can be sent to real customers.**
- Where: `InboxFeed.tsx:126-131`. The quick replies include `Coupon code: VINTAGE10`, a fake tracking link `courier.np/track/SS98234`, and a promise of 11 am delivery in Pokhara. One click fills the input and Enter sends it to a real Instagram user.
- `InboxFeed.tsx:120` is worse. When AI draft fails (and `/api/v1/ai/reply` returns 404 today, see `api.ts:41`), the code silently puts "Namaste! Hamro store bata hajur ko query review bhairakheko cha…" into the reply box. The button fails every time, and the fallback looks like a real draft.
- Fix: delete the canned list, or load it per tenant. On AI draft failure show an inline error and leave the input alone. Hide the AI DRAFT button until the endpoint exists.

**C5. The middleware makes every page except `/login` private, so a privacy policy, terms, data-deletion page, landing page and `robots.txt` cannot be public.**
- Where: `middleware.ts:19-21` plus the matcher at `:26-28`.
- The matcher no longer excludes paths with a file extension (the `.bak` did: `.*\\..*`). Any of `/robots.txt`, `/sitemap.xml`, `/privacy`, `/terms`, `/data-deletion`, and anything in `public/` now redirects logged-out visitors, including Meta's reviewer and crawlers, to `/login`.
- Meta app review needs public Privacy Policy and Data Deletion URLs. Building those pages is not enough on its own.
- The login page also shows "terms of service" and "privacy policy" as plain `<span>` elements (`login/page.tsx:246-248`), not links.
- Fix: replace the redirect logic with an allowlist.
```ts
const PUBLIC = ['/login', '/privacy', '/terms', '/data-deletion', '/robots.txt', '/sitemap.xml'];
const isPublic = PUBLIC.includes(pathname) || /\.[a-z0-9]+$/i.test(pathname);
if (!hasSession && !isPublic) return NextResponse.redirect(new URL('/login', req.url));
if (hasSession && pathname === '/login') return NextResponse.redirect(new URL('/dashboard', req.url));
```
- Only `/login` should keep the bounce for signed-in users. Also stop copying `search` into the `/login` redirect for every path. The `ig_error` case only needs it when the target is `/login`.

**H5. The message pane never scrolls to the newest message.**
- `InboxFeed.tsx:284-375` has no scroll ref or effect. Opening a long thread shows the oldest messages, and new messages arrive off-screen. For a chat, this is the core view.
- Fix: a `ref` on the container and `useEffect(() => { ref.current?.scrollTo({ top: ref.current.scrollHeight }); }, [thread?.id, thread?.messages.length]);`.
- Check whether the backend returns messages oldest-first (B). If it is newest-first the pane is also reversed.

**H6. The reply box loses text on failure and sends on IME confirmation.**
- `InboxFeed.tsx:96-100` clears the input before the async send resolves. If the send fails (`App.tsx:155` shows an `alert`), the merchant's typed message is gone. There is no in-flight guard, so a double click sends twice.
- `InboxFeed.tsx:102-106` sends on `Enter` without checking `e.nativeEvent.isComposing`. Typing Nepali through an IME, pressing Enter to confirm a candidate sends the half-typed message. For a Nepali-first product this will hit daily.
- Fix:
```diff
-    if (e.key === 'Enter') {
+    if (e.key === 'Enter' && !e.nativeEvent.isComposing) {
```
  and make `handleSend` await the send, clear the input only on success, and disable the button while sending.

### Medium

If the cookie expires mid-session, the merchant sees a frozen inbox and no redirect. ## 3. Deployment notes

- `middleware.ts:3` falls back to `http://localhost:8000`. In a container, `localhost` is the web container itself, so a missing `BACKEND_URL` gives 500s on every API call without any hint. Fail fast (throw or log) if it is unset in production. `.env.example` sets it to `http://api:8000`, which is right for the `nepsocial` network.
- `docker-compose.yml` needs the external network `nepsocial` to exist beforehand (`docker network create nepsocial`). There is no `HEALTHCHECK`, and the container runs as root; add `USER node`.
- `middleware.ts:11-13` lets `/api/v1/webhooks/*` fall through to Next, which has no such route and returns 404. That is intended only when nginx sends webhooks to FastAPI directly. In local dev without nginx, Meta webhooks cannot reach the backend through this app. Say so in the README or use a tunnel to FastAPI.
- CSRF (B): logout, send and link are cookie-authenticated POSTs with no token. Confirm the backend sets `SameSite=Lax` or stricter on `ns_session`.

## 4. SEO (later, but decide the routes now)

- The app is client-only (`app/page.tsx` uses `ssr:false`) and login-gated, so the only crawlable page is `/login`. That is fine for the app itself.
- Route plan that avoids a second refactor: `/` becomes a public landing page (server-rendered), `/login`, `/privacy`, `/terms`, `/data-deletion` are public, and the authenticated app lives at `/dashboard` and `/inbox` with `robots: { index: false }`.
- `layout.tsx:12` sets `twitter.card = 'summary_large_image'` with no image, and there is no `og:image` or `metadataBase`. Add both or drop the card type. `lang="en"` on a Nepali/English product needs per-page language.
- Fonts are loaded with a render-blocking `<link>` to Google Fonts (`layout.tsx:19-24`). Use `next/font` for speed and privacy.
- `login/page.tsx` is a client component and cannot export `metadata`. Put a small `app/login/layout.tsx` with its own title and description.
- No `robots.txt` or `sitemap.xml` exists. Add them via `app/robots.ts` and `app/sitemap.ts`, and keep them public in the middleware (C5).
