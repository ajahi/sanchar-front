# Sanchar frontend: review and flow check (Instagram login, dashboard, conversations)

## Verdict

The plumbing works. The `/api/v1` proxy, the session-cookie gate, the Instagram login link, conversation polling, message loading, and sending a reply are all wired to real endpoints. `tsc --noEmit --incremental false` passes.

The flow does not match your intent in three ways:

1. A user who logs in with Instagram lands on the inbox, not the dashboard.
2. Much of what the tenant sees is still hard-coded demo data shown as live status.
3. Several paths can send something wrong to a real customer, or log a real user out for no reason.

I read every file listed in the brief. I did not run the app or hit the backend. Findings that depend on backend behaviour are marked **[backend]**, and the section "Verify against the backend" lists what to check.

**Assumptions**
- "Dashboard with all metrics" means `/dashboard`, which uses `GET /api/v1/dashboard`.
- Backend order and sender values are as `api.ts` assumes, unless a finding says otherwise.

## The flow as it runs today

| Step | Intended | Actual | Where |
|---|---|---|---|
| 1. Log in | Instagram, or link other channels | Instagram link works. Email login works. Nothing in the signed-in app lets you link Facebook or add another Instagram account. | `login/page.tsx:186`, `MetaSettingsModal.tsx` |
| 2. After login | Dashboard | Goes to `/`, the inbox | `middleware.ts:22`, `login/page.tsx:37`, backend callback **[backend]** |
| 3. Dashboard | All metrics | `/dashboard` is a separate page, reached from the header. It shows 24 hours of counts only. | `dashboard/page.tsx`, `api.ts:129` |
| 4. Conversations by channel | Listed per social media on the left | One mixed list with All/IG/WA/FB filter buttons and no per-channel counts | `SidebarNav.tsx:71-116` |
| 5. Click a conversation | See its messages | Works, but the message pane has no loading, empty, or error state. It never scrolls to the newest message, and timestamps carry no date. | `App.tsx:88-96`, `InboxFeed.tsx:284` |

## Findings, most severe first

### Critical: wrong or fake content can reach real customers

**1. One-click fake replies to real Instagram customers.**
- `InboxFeed.tsx:126-131` hard-codes quick replies with invented commitments: "10% discount approve bhayo! Coupon code: VINTAGE10", "Tracking link: courier.np/track/SS98234", and a Pokhara delivery promise. Clicking one fills the input, and Enter sends it through the real `sendReply`.
- `InboxFeed.tsx:120` is worse. When AI DRAFT fails, it puts "Namaste! Hamro store bata hajur ko query review bhairakheko cha…" into the input. `/api/v1/ai/reply` returns 404 today (`api.ts:41`), so the fallback fires every time.
- Fix: delete the canned array and the fallback text. On draft failure, show an inline error and leave the input empty. If quick replies are wanted, load them per tenant from the backend.

**2. Simulated messages are injected into real threads.**
- `SIMULATE CUSTOMER` (`InboxFeed.tsx:199-259`, `App.tsx:182-250`) appends a fake customer message and a fake AI answer to the currently open real conversation, locally.
- The 5-second poll only refetches messages when `last_message_at` changes (`App.tsx:88-96`). The fake bubbles therefore stay in a genuine customer's thread until that customer next writes.
- `+ INBOUND` (`App.tsx:253-324`) creates `thread-<timestamp>` threads and makes them active. The messages effect then calls `listMessages('thread-…')`, which fails. Send on such a thread fails too, and the next poll deletes the thread.
- Fix: gate the header `+ INBOUND` button, `SIMULATE CUSTOMER`, `RAGSandboxModal` and `InboundSimulatorModal` behind `NEXT_PUBLIC_DEV_TOOLS === '1'`. Until the backend has `/ai/reply`, these features cannot work anyway.

### High: breaks the described flow

**3. Login lands on the inbox, not the dashboard.**
- Both entry paths go to `/`: `middleware.ts:22` and `login/page.tsx:37`. The Instagram path depends on the backend callback's redirect target **[backend]**.
- Fix:
  ```diff
  # middleware.ts:22
  -if (hasSession && isLogin) return NextResponse.redirect(new URL('/', req.url));
  +if (hasSession && isLogin && !req.nextUrl.searchParams.has('ig_error'))
  +  return NextResponse.redirect(new URL('/dashboard', req.url));
  # login/page.tsx:37
  -window.location.assign('/');
  +window.location.assign('/dashboard');
  ```
  Then make the backend's Instagram callback redirect to `/dashboard`.
- The `ig_error` guard fixes a second bug. Today, a user with a stale `ns_session` cookie whose Instagram login fails is bounced from `/login?ig_error=…` to `/`. The error message is lost, and the session-expiry sign-out then sends them back to a clean `/login`.
- There is no return-to parameter (`middleware.ts:21`). A logged-out deep link such as `/dashboard` always ends at the landing page after login.

**4. Real AI replies show fake metadata, and system messages are mislabelled.**
- `toChatMessage` (`api.ts:83-90`) never sets `confidence`, `source` or `intent`.
- `InboxFeed.tsx:307-333` renders every real AI reply with a green "CONFIDENCE: 0.00" badge and an empty "SOURCE:" badge. Every sidebar card shows "CONF: 0.00" (`SidebarNav.tsx:208`).
- `api.ts:85` maps every sender that is not `customer` or `ai` to `'human'`. A backend `system` message therefore appears as "Human Operator (Merchant) / OPERATOR OVERRIDE SENT VIA GRAPH API".
- Fix: render the confidence and source badges only when the value exists (`conf != null`, `source`). Map `agent` to human, and render `system` as a neutral centred note.

**5. The Take-over toggle does nothing on the server, and the status mapping is lossy.**
- `handleToggleTakeover` (`App.tsx:122-139`) changes local state only. The next poll (`App.tsx:73-75`) replaces it with the server value within 5 seconds. The backend needs a mode update endpoint **[backend]**, and the button should call it.
- `api.ts:102` maps any `mode` other than `'ai'` to `NEEDS_HUMAN`. A deliberate merchant takeover, a paused mode or a closed conversation then shows as a pulsing red "HUMAN ESCALATION REQUIRED / HIGH PRIORITY" banner.
- The `status` field of the conversation (open or closed) is ignored (`api.ts:59-68`).
- Fix: map `mode` to a three-state value (auto, human, needs-human) and use `status` for resolved or closed.

**6. A transient error logs the user out, and a backend outage strands them.**
- `App.tsx:55-62` and `PageHeader.tsx:229-233` call sign-out on any failure of `/tenants/me`. A 502, a backend restart or a network blip destroys the session.
- `signOut` awaits `logout()`. If the backend is down, `fetch` rejects, the redirect never runs, and the page stays on the mock business name "Himalayan Silk…" (`App.tsx:25`).
- Fix: sign out only on 401. On other errors, show a retry banner. Wrap `logout()` in try/finally so the redirect always runs.
- The 5-second poll (`App.tsx:69-80`) has no 401 handling and no backoff. It hammers a down backend every 5 seconds, and it never notices an expired session.

**7. The Channels modal shows the demo tenant as connected.**
- `initialMetaStatus` (`mockData.ts:229-248`) feeds these cards:
  - Facebook: "LINKED & ACTIVE", page "Himalayan Silk & Handicrafts" (`MetaSettingsModal.tsx:186-194`).
  - Instagram: "VERIFIED", handle `@himalayan_silk_np` (`:214-222`). The tenant's real handle is available from `getInstagramProfiles()`, which only `ProfileModal` uses.
  - RightInspector "ACTIVE CHANNELS" lights all three channels and says "Meta Webhooks 200 OK" (`RightInspector.tsx:187-212`).
- A tenant who just logged in with Instagram opens Channels and sees someone else's handle.
- **Business-name overwrite bug:** `useState(businessName)` (`MetaSettingsModal.tsx:61`) captures the mock name. The modal is always mounted (`App.tsx:425`), so the real tenant name arriving later never reaches `bName`. Pressing "Save Configuration" (`:114-117`) then overwrites the real name in the header with "Himalayan Silk…". Save persists nothing either way: no API call, and the language choice is also local only.
- Fix: derive the Facebook and Instagram cards from the API, and show "Not connected" for Facebook until it exists. Sync `bName` with a `useEffect` on `isOpen`, or remove the field. Add an "Add Instagram account" button.
- **PING WEBHOOKS** (`:105-112`) is an 800 ms `setTimeout` that prints "HTTP 200 OK — Inbound Webhooks Verified". The callback URL `api.socialsync.np/v1/meta/webhook` and the verify token `socialsync_meta_wh_sec_991823` (`:62, 401`) match nothing real. Remove them, or fetch them from the backend. Do not ship a secret-looking literal in the client bundle.

**8. The message pane fails silently in ways a user will hit.**
- No auto-scroll to the newest message (`InboxFeed.tsx:284`; grep finds no `scrollIntoView`). A long thread opens at its oldest message. A new inbound message arrives off-screen.
- Fix: add a bottom ref and `useEffect(() => ref.current?.scrollIntoView(), [thread.id, thread.messages.length])`.
- No loading, empty or error state. `listMessages` failures only reach `console.error` (`App.tsx:95`), so a failed load looks like an empty chat.
- Timestamps are `HH:MM` only (`api.ts:80-81, 100`). A thread from last week reads "02:15 PM", and a conversation cannot be told apart from today's. Add a date and day separators.
- `new Date(iso)` misreads a timestamp with no `Z` or offset as local time, which is off by 5:45 in Nepal. It depends on what FastAPI serialises **[backend]**.
- Sidebar previews read `thread.messages`, which is empty for every thread except the open one (`SidebarNav.tsx:151, 190`). Every other thread says "No messages yet", which is false. The conversations endpoint should return `last_message` and `last_message_sender` **[backend]**.

### Medium

**9. Sending edge cases** (`InboxFeed.tsx:96-106`, `App.tsx:154-156`)
- Enter sends even during IME composition. For Devanagari or Romanized-Nepali IME input, the Enter that commits a word sends a half-written message. Use `if (e.key === 'Enter' && !e.nativeEvent.isComposing)`.
- The input is cleared before the send succeeds (`:99`). On failure, such as an expired Meta 24-hour window, the operator's text is gone and an `alert()` appears. Clear the input only after success, and show the error inline.
- The UI always claims "Meta 24h Window: Active" and "Encryption: E2E Verified" (`:163, 433`). Neither is computed. `windowExpiresAt` exists in `types.ts:114` but is never populated. Compute it from the last inbound customer message or remove the claim.

**10. Conversations sidebar**
- Cards are `<div onClick>` (`SidebarNav.tsx:155-158`) with no role, `tabIndex` or key handler. The primary "click a conversation" action cannot be done with a keyboard. Use `<button>`.
- Ordering is whatever the backend returns. Sort by `lastMessageAt` descending on the client.
- For a new Instagram tenant with zero conversations, the centre pane says "Select a conversation from the left feed" while the left says "No threads match the selected filter." (`InboxFeed.tsx:86`, `SidebarNav.tsx:145`). Add a first-run empty state such as "No conversations yet. Send a DM to your Instagram account to test."
- The FB and WA filter buttons show even when those channels are not linked. Show counts per channel and hide or disable the unlinked ones.

**11. Dashboard** (`dashboard/page.tsx`, `api.ts:129`)
- The window is fixed at one day, with no selector or refresh. `days` is already a parameter.
- All three channel rows always show, including unlinked ones, so a new Instagram-only tenant sees a wall of zeros (`:19-24`).
- The response is trusted blindly. `Object.values(data.handover)` at `:41` and `counts[ch]` at `:22` throw or render `undefined` if a key is missing, and there is no `error.tsx` to catch it **[backend]**.
- The header's escalation badge on this page is the 24-hour handover total (`:41`). In the inbox it is the count of currently escalated threads (`App.tsx:103`). One badge carries two meanings.
- Errors show raw text such as "Failed to load dashboard (404)" with no retry.
- The empty state does not tell a new tenant to send a test DM.

**12. Dead and misleading UI controls**
- The header shows an inert "LOGIN / SIGN UP" button (`Header.tsx:185-192`) until `/tenants/me` returns. `onOpenAuthPage` is never passed by `App` or `PageHeader`, so during that window (or an outage) the button does nothing.
- `ProfileModal.tsx:284` says "Log in with Instagram again to refresh." A logged-in user cannot reach `/login`, because `middleware.ts:22` redirects it. They would have to sign out first. Link the button straight to `INSTAGRAM_LOGIN_URL` instead.
- WhatsApp linking exists only when zero numbers are linked (`MetaSettingsModal.tsx:269`). A second number cannot be added.
- The Footer's latency is `latencyMs / 100`, so 120 ms renders as "1.2s" (`Footer.tsx:280`). It should be `/ 1000`. Token usage (412) and latency are hard-coded starting values (`App.tsx:99-100`), and the Footer also prints "(C) 2026 SOCIALSYNC AI".
- `RightInspector.tsx:41, 72` prints `detectedIntent` and `ragSourceDoc` for real threads. Both are undefined, so the fields are blank. The catalog block, delivery rates and "VINTAGE5" (`:93-119`) are static mock data.
- Old-brand text remains: "SocialSync AI (RAG-Enabled)" (`InboxFeed.tsx:316`), "Ask Gemini…" (`:415`), and the health route.

### Middleware, SEO and deployment

**13. The matcher no longer exempts static files** (`middleware.ts:27`).
- The old `.bak` excluded `.*\\..*`; the current matcher does not. A logged-out visitor requesting `/robots.txt`, `/sitemap.xml`, an OG image or `/sanchar-mailbox.svg` gets redirected to `/login`.
- Today no page references those files, and `/favicon.ico` is excluded but does not exist, so the site has no favicon.
- Fix: `matcher: ['/((?!api/|_next/|.*\\..*).*)', '/api/v1/:path*']`. The trailing slash on `api/` also stops it swallowing top-level page names that merely start with "api". Add `/privacy`, `/terms` and `/data-deletion` to the public list (see 14).

**14. Meta review and legal**
- The terms and privacy "links" are `<span>`s (`login/page.tsx:246-248`).
- Meta app review needs a real privacy policy URL and a data-deletion callback or instructions URL for Instagram login.
- Login-page claims that a reviewer or user will read as factual:
  - "FREE FOREVER"
  - "GDPR / Nepal Telecomm Ready" (`:289`)
  - "Meta Graph v21.0 Compliant"
  - "ESTD. 1932" and "PRICE 50 PAISA" (`:71, 128`)
  Remove or substantiate them.
- Also on the login page: the labels have no `htmlFor` (`:212-227`), and both inputs lack `autocomplete`.

**15. SEO**
- Only `/login` is server-rendered and indexable. The inbox is `ssr:false` (`app/page.tsx:8`) behind a login redirect, and `/` redirects crawlers to `/login`.
- A plan:
  - Add a public landing page at `/`.
  - Move the inbox to `/inbox`.
  - Add per-page `metadata`.
  - Add `app/robots.ts` and `app/sitemap.ts`.
  - Mark `/inbox` and `/dashboard` `noindex`.
  - Add a favicon.
  - Load fonts with `next/font` instead of the render-blocking `<link>` in `layout.tsx:19-25`.
- Dashboard and login both render an `<h1>` plus the Header's `<h1>`, so pages have two.

**16. Dead code and hygiene**
- Delete `app/api/meta/*`. `test-connection` always says "success"; `webhook` and `webhook-logs` are unauthenticated and unrelated to the real Meta callback, and the matcher excludes `api`, so they are public.
- Delete `app/api/amit/page.tsx`, which is a public empty page at `/api/amit`.
- `app/api/health/route.ts` reports a Gemini key and the old brand. Keep a health route, but make it minimal.
- Untrack `tsconfig.tsbuildinfo` and `middleware.ts.bak`.
- `conversation_example.json` is a sample containing real-looking Instagram IDs and usernames. Move it out of the repo.
- `"lint": "next lint"` has no ESLint dependency installed.
- `select-none` on the whole login page, inbox, sidebar and Header means users cannot copy handles or phone numbers from the thread header. Safari has historically broken typing into inputs inside `user-select:none` ancestors, so test the login form there.

## Verify against the backend

Nothing below is provable from this repo. Each item changes the fix I recommend.

1. **Instagram callback.**
   - Check the redirect target (`/` or `/dashboard`).
   - Check the `Set-Cookie` flags. A `Secure` cookie on plain HTTP looks like a successful login and then bounces silently.
   - Check how it builds `redirect_uri`. A Next rewrite changes the Host header, so a URL built from the request host would be the internal `api:8000`, not your public origin.
2. **`GET /conversations`.**
   - Check the sort order and whether it paginates.
   - Check the timestamp format (with or without `Z`).
   - Check the possible `mode` and `status` values.
   - Check whether it can return a `last_message`.
3. **`GET /conversations/{id}/messages`.**
   - Check that ordering is oldest first.
   - Check the `sender_type` values, especially `system`.
4. **`GET /dashboard`.**
   - Check that all three channel keys are always present.
   - Check the time zone of the "day".
   - Check whether `days` is clamped.
5. **Missing endpoints.** Is there a `PATCH` for mode, and what does `GET …/instagram/profile` return with no linked account (`[]` or 404)?
6. **Webhook path.**
   - `middleware.ts:11-13` returns `next()` for `/api/v1/webhooks/`. Behind the compose file alone (port 3000, no nginx), Meta's verification GET hits a Next 404. That is fine in production with nginx and blocks local ngrok testing.
   - The comment claims a rewrite breaks the HMAC. I could not confirm that. Test it, because a plain rewrite would remove the need for nginx.
7. **`BACKEND_URL` at runtime.**
   - `.dockerignore` excludes `.env`, and the image build has no `BACKEND_URL`.
   - The value comes from `env_file` at runtime. Confirm on the built container that the proxy reaches `api:8000` and not the `localhost:8000` default.

## Suggested fix order

1. Delete the canned replies, the fallback draft text and the simulators (findings 1 and 2). Ship blocker.
2. Point login at `/dashboard` and add the `ig_error` guard (3).
3. Stop rendering fake confidence, source and channel status. Fix the sender mapping and the business-name overwrite (4, 7).
4. Sign out only on 401, harden `signOut`, add scroll-to-bottom and message/empty/error states (6, 8).
5. Add the mode endpoint, the three-state mapping, IME guard and send-retry (5, 9).
6. Fix the matcher, add legal pages, and prune dead routes (13, 14, 16).
7. Rework the dashboard for connected channels and time windows (11).
