# Sanchar frontend: review and flow check (Instagram login -> dashboard -> conversations)

I read every file on the flow (middleware, login, dashboard, inbox, api client, header, sidebar, feed, inspector, Channels and Profile modals, mock data, `app/api/*`, Docker files). `npx tsc --noEmit --incremental false` passes with no errors. I did not run the app against your backend. Findings that depend on backend behaviour I cannot see are marked **[backend?]**.

## Verdict

The pieces work individually, but the flow you described is not the flow the code implements:

1. **After Instagram login the tenant lands in the inbox (`/`), not the dashboard.** Nothing in the frontend ever sends anyone to `/dashboard`.
2. **A dead or unreachable backend traps the user in an endless redirect loop**, and any failed `/tenants/me` call logs them out.
3. **Several controls claim things that are not true.** "Take over as human" does nothing on the server. The Channels modal shows a fake Facebook page, a fake Instagram handle and a fake "Verified" state. Quick-reply buttons put a fake coupon and a fake tracking link into real customer DMs.
4. **The conversation view opens at the top of the chat**, shows no dates, and labels every AI message "CONFIDENCE: 0.00".
5. **A logged-in tenant has no way to connect (or re-connect) Instagram from inside the app.**

Fixes for the top items are in the patch section at the end.

## 2. Findings, ranked

### P0: breaks the intended flow or traps the user

**1. Landing page is the inbox, not the dashboard.** `middleware.ts:22`, `login/page.tsx:37`, `app/page.tsx`.
Changing only the frontend redirects is not enough, because the Instagram callback lands wherever the backend sends it (probably `/`) **[backend?]**. The robust fix is frontend-only: make `/` redirect to `/dashboard` and move the inbox to `/inbox` (patch A). Whatever URL the backend uses then ends up on the dashboard.

**2. Redirect/reload loop when the session is bad or the backend is down.** `middleware.ts:19-22`, `App.tsx:54-62`, `PageHeader.tsx:27-31`, `api.ts:13-15,23-27`.
- Middleware only checks that the `ns_session` cookie exists.
- `getMyTenant()` throws on any non-OK response, including 502/500 while FastAPI restarts.
- The `.catch(handleSignOut)` then calls `logout()`. `logout()` never checks `res.ok`, so a 401/502 from the backend leaves the httpOnly cookie in place.
- `assign('/login')` -> middleware sees the cookie -> redirects to `/` -> `getMyTenant()` fails again -> repeat.

In development, with Docker restarts, this is easy to hit. Even when logout works, a two-second backend blip signs the tenant out. The comment at `App.tsx:60` shows this loop was already hit once and patched only for the case where the backend clears the cookie.
Fix (patch B): sign out only on 401/403, show a "backend unavailable" state otherwise, and add a Next route `/logout` that deletes the cookie itself, so escaping the loop does not depend on the backend.

### P1: wrong or unsafe behaviour a tenant will hit

**3. "Take over as human" is cosmetic.** `App.tsx:122-139`, `InboxFeed.tsx:177-195,435`.
The toggle changes local state only. The next poll (`App.tsx:73-75`) overwrites `status` from the server's `mode`, so it reverts within 5 s. Worse, the UI says "Auto-pilot suspended" and "HUMAN TAKEOVER ACTIVE" while the AI keeps replying. There is no endpoint in `api.ts` for it. Add `PATCH /conversations/{id}` with `mode` **[backend?]**. Until then, disable the button or label it "not connected yet".

**4. Fake text can be sent to real customers.**
- `InboxFeed.tsx:126-131`: quick replies include "Coupon code: VINTAGE10", "Tracking link: courier.np/track/SS98234", and "10% discount approve bhayo". One click puts them in the input, and Enter sends.
- `InboxFeed.tsx:108-124`: **AI DRAFT** calls `/api/v1/ai/reply`, which 404s (`api.ts:41`). The catch block (`InboxFeed.tsx:120`) then fills the input with "Hamro store bata hajur ko query review bhairakheko cha...". The operator sees a plausible reply, presses SEND, and a real Instagram user receives it.
Hide both behind a dev flag, or leave the input empty and show an inline error.

**5. Channels modal shows fake state, and Save overwrites the real business name.** `MetaSettingsModal.tsx`
- Line 61: `useState(businessName)` runs once, when `App` mounts (the modal is always mounted and returns `null` when closed, line 101). At that moment `businessName` is still the mock `'Himalayan Silk & Handicrafts (काठमाडौँ)'` (`App.tsx:25`). Opening Channels shows the mock name in the field. **Save Configuration** (lines 114-117) calls `onUpdateBusinessName`, so the real tenant name in the header is replaced by the mock one. Nothing is sent to the server either way.
- Lines 175-229: Facebook "LINKED & ACTIVE" (page "Himalayan Silk & Handicrafts") and Instagram "VERIFIED" (`@himalayan_silk_np`) come from `initialMetaStatus` (`mockData.ts:229-248`), even for a tenant who just logged in with a different account. The real handle is available from `getInstagramProfiles()` (`api.ts:149`).
- Lines 105-112 and 401-406: "PING WEBHOOKS" waits 800 ms and prints "HTTP 200 OK - Inbound Webhooks Verified". The callback URL (`api.socialsync.np/v1/meta/webhook`) and verify token are invented. The real webhook path is under `/api/v1/webhooks/` (`middleware.ts:11`).
- The dialect selector (line 162) and `defaultLanguage` are never sent to a backend.
Replace the two cards with data from `getInstagramProfiles()` and an honest "not connected" state for Facebook. Delete the fake ping and webhook block. Remove or wire the name/dialect fields (patch D).

**6. A logged-in tenant cannot connect or re-connect Instagram.** `login/page.tsx:188`, `middleware.ts:20-22`, `ProfileModal.tsx:68`.
The only Instagram button is on `/login`, and `/login` redirects any session holder to `/`. So a tenant who signed up by email cannot add Instagram, and the Profile modal's advice "Log in with Instagram again to refresh" is impossible without signing out first. Add a "Connect Instagram" link to `INSTAGRAM_LOGIN_URL` in the Channels modal and in the Profile modal when `live` is false. What the backend does when the login endpoint is called with a session (link vs create a new tenant) is unknown **[backend?]**.

### P2: conversation and dashboard quality

**7. The chat opens at the top and has no dates.** `InboxFeed.tsx:284`, `api.ts:80-81,100`.
There is no scroll-to-bottom anywhere, so a long thread shows the oldest messages, and new arrivals are out of view. `fmtTime` renders only HH:MM, so a message from 4 September looks like it came today. Sidebar "last seen" has the same problem. Message order is assumed ascending **[backend?]**. Patch E adds scrolling; add a date separator when the day changes.

**8. Every real AI message shows "CONFIDENCE: 0.00" and an empty "SOURCE:".** `InboxFeed.tsx:307-334`, `SidebarNav.tsx:208`, `RightInspector.tsx:41,72`.
`toChatMessage` never sets `confidence` or `source`, so `conf ?? 0` renders 0.00 in a green badge. The sidebar shows "CONF: 0.00" on every thread. The inspector's DETECTED INTENT and KNOWLEDGE BASE SOURCE are blank for real threads. Render these only when the value exists.

**9. Human/agent labelling and static claims.** `api.ts:85`, `InboxFeed.tsx:353-371,163,433`.
- `sender_type` `agent` and `system` both map to `'human'`. System notes appear as "Human Operator (Merchant)" with "OPERATOR OVERRIDE SENT VIA GRAPH API".
- "Meta Customer Service Window: Active - Encryption: E2E Verified" (`InboxFeed.tsx:433`) is a constant. The Instagram 24 h window can be closed, and then sends fail. Compute it from the last customer message time, or remove the text.

**10. Sidebar previews are empty for every thread you have not opened.** `SidebarNav.tsx:151,190`, `api.ts:103`.
Messages load only for the open thread, so other threads say "No messages yet", which is false. Image-only messages show empty quotes. Needs `last_message_preview` from `/conversations` **[backend?]**. Meanwhile show the time only, not a false statement.

**11. Status mapping treats anything that is not `'ai'` as "needs human".** `api.ts:102`.
`c.status` (open/closed) is ignored, and there is no RESOLVED state despite `types.ts:4`. If the backend's default `mode` is anything other than the string `ai` (for example `auto` or `null`), every thread turns red with "HUMAN ESCALATION REQUIRED" **[backend?]**. The banner text at `InboxFeed.tsx:273` also says "AI confidence fell below threshold" for a merchant's own takeover. Map explicitly (`mode === 'human'`) once the enum is confirmed.

**12. Stale active thread.** `App.tsx:76,102`.
`setActiveThreadId(id => id || ...)` never resets. If the selected thread disappears (the simulator's fake thread, a closed conversation), the sidebar highlights nothing, while the centre pane silently falls back to `threads[0]` and sends go there. That is a wrong-recipient risk. One-line fix in patch F.

**13. Dashboard is thin and trusts the response.** `app/dashboard/page.tsx`, `api.ts:129`.
- Fixed `days=1` (`page.tsx:34`), no selector, no refresh, no polling.
- All three channels always render (`page.tsx:19-24`), including channels the tenant never connected: a wall of zeros and no "connect a channel" prompt. `counts[ch]` renders `undefined` if a key is missing.
- Only counts and top queries. The Instagram figures you already fetch for the Profile modal (followers, following, posts) are not on the dashboard. Response time, AI vs human share and open conversations are absent. Whether the backend supplies them is unknown **[backend?]**.
- `PageHeader escalations` (`page.tsx:41`) shows the sum of window handovers next to the INBOX label, while the inbox shows threads currently in NEEDS_HUMAN (`App.tsx:103`). Same badge, two meanings. Drop it on the dashboard.
- A transient error shows a bare red string with no retry (`page.tsx:43-44`). `key={q.text}` collides on duplicate queries. `getMyTenant` is refetched on every navigation between inbox and dashboard, because each page mounts its own header.

**14. Public files and SEO paths redirect to `/login`.** `middleware.ts:27`.
`middleware.ts.bak` excluded paths containing a dot (`.*\\..*`). The current matcher does not, so anything under `public/` and future `robots.txt`, `sitemap.xml` or OG images redirect logged-out visitors (and crawlers) to `/login`. Restore the exclusion (patch C).

### P3: smaller bugs and polish

- **Dead header button.** `Header.tsx:185-192`: while `currentUser` is null (first load, and on the dashboard until `/tenants/me` returns), a "LOGIN / SIGN UP" button renders with no `onClick` (`onOpenAuthPage` is never passed). A signed-in user sees it flash.
- **Hard-coded initials.** `Header.tsx:165` shows "NP" for everybody, because `avatarInitials` is never set.
- **Enter sends mid-composition.** `InboxFeed.tsx:102-106`: Nepali IME users who press Enter to commit a word send the half-typed message. Check `e.nativeEvent.isComposing`.
- **Send loses text on failure.** `InboxFeed.tsx:96-100`: `setInputText('')` runs before the async send finishes, and failure only calls `alert()` (`App.tsx:155`). Also no in-flight guard, so a double Enter sends twice.
- **Simulated messages stick.** `App.tsx:182-206`: "SIMULATE CUSTOMER" appends fake customer and AI messages to a real conversation. The poll keeps existing messages (`App.tsx:74`), so they stay until you switch threads. The earlier review said the next poll wipes them; that is true only for the fake thread from `+ INBOUND`.
- **Hard-coded tenant content.** Footer `TOKEN_USAGE 412/10000`, `LATENCY` (`App.tsx:99-100`, `Footer.tsx:26`), RightInspector catalog, delivery fees and "VINTAGE5" policy (`RightInspector.tsx:93-119`), "RAG ACTIVE", "ACTIVE CHANNELS" stamp and "Meta Webhooks 200 OK" (`:31,182-213`).
- **Old product name.** "SocialSync" in `InboxFeed.tsx:316,415`, `Footer.tsx:26`, `InventoryModal.tsx:284`, `MetaSettingsModal.tsx:62,401`, `app/api/health/route.ts:6`.
- **Layout.** `App.tsx:364` gives the sidebar only 2 of 12 columns on `xl` screens, which is narrow for cards with badges. The inbox is `overflow-hidden h-screen` with `select-none` at the root.
- **`app/loading.tsx`** is a blue, generic spinner, unlike the themed `Loader`, and it flashes on every route change.
- **`?ig_error=` text is shown verbatim** (`login/page.tsx:24`). React escapes it, but anyone can craft a link that puts arbitrary wording in your error box. Show a fixed message per known code.
- **No return-to URL.** Deep links to `/dashboard` while logged out end at `/` after login.
- **Accessibility.** The login labels have no `htmlFor` and the inputs have no `autocomplete`, so password managers do worse.

## 4. SEO and Meta review readiness

- **Indexable surface:** only `/login`, which is server-rendered and correct. `/` and `/dashboard` redirect crawlers there, and `/` is `ssr:false`.
- **Metadata (`layout.tsx:4-13`):** one global title and description. There is no `metadataBase`, no `og:image` (while `twitter.card` is `summary_large_image`), no canonical, and no `robots`/`sitemap`. `login/page.tsx` is a client component, so it cannot export its own metadata; split it into a server page plus a client form when you do SEO. Add `robots: { index: false }` for `/dashboard` and `/inbox`.
- **Fonts:** five Google font families through a render-blocking `<link>` (`layout.tsx:19-25`). Use `next/font` before SEO/performance work.
- **Plan for later:** public marketing page at `/`, with the middleware allowing `/` for logged-out visitors. This is another reason to move the inbox to `/inbox` now (patch A).
- **Meta app review:** the "terms of service" and "privacy policy" on the login page are plain `<span>`s (`login/page.tsx:246,248`). Instagram/Facebook login requires a live privacy policy URL and a data-deletion URL or callback. The page also claims "Meta Graph v21.0 Compliant" and "GDPR / Nepal Telecomm Ready" (`:287-289`) with no policy to back them, which reviewers may notice.
- **Webhooks in development:** `middleware.ts:11` lets `/api/v1/webhooks/*` through to Next itself, so it 404s unless nginx routes it to FastAPI first. Tunnelling a dev URL straight to port 3000 will fail Meta's verification.
- **Deployment:** `BACKEND_URL` is read in middleware at runtime (`middleware.ts:3`), but `.dockerignore` excludes `.env*`, so it comes only from compose `env_file`. Confirm once in the built image that it is not baked in at build time; if it is, every API call goes to `localhost:8000` inside the container. `docker-compose.yml` needs the external `nepsocial` network created first.

## 6. Questions only the backend can answer

1. Where does the Instagram callback redirect after success? (With patch A, `/`, `/inbox` or `/dashboard` all work; `/login?...` also works when the cookie is set.)
2. Does `POST /auth/logout` clear `ns_session` when the session is invalid, and with what `Path`?
3. What are the values of `mode` and `status` on `/conversations`? Is the list sorted, and paginated? Are messages ascending?
4. Is there, or will there be, an endpoint to change a conversation's mode (takeover), and one for `last_message` previews?
5. What does the Instagram login endpoint do when called with an existing session (link, or new tenant)?
6. Does `/dashboard` return all three channel keys always, and what is the maximum `days`?
7. Is a `Host`/`X-Forwarded-Host` used to build the OAuth `redirect_uri`? The rewrite may present the backend's own host.
