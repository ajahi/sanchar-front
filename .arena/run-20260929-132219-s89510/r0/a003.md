# Sanchar frontend: flow check and code review

**Short verdict.** The real plumbing works: Instagram login link, cookie, proxy, conversation list, message pane, reply, dashboard fetch. `npx tsc --noEmit` passes. But the flow you described breaks in five places, and several screens show fake "all green" data that hides those breaks. I read every file listed in the brief; I did not run the app against your backend.

## 1. Intended flow vs. what the code does

| Step you want | What actually happens | Verdict |
|---|---|---|
| Log in with Instagram | `login/page.tsx:188` links to `/api/v1/social-accounts/instagram/login`; middleware rewrites it to FastAPI (`middleware.ts:15-17`) | Works (backend redirect unseen) |
| Land on the dashboard | Middleware sends a logged-in user to `/` (`middleware.ts:22`); email login does `assign('/')` (`login/page.tsx:37`). `/` is the inbox (`app/page.tsx`) | **Wrong page** |
| See all metrics | `/dashboard` only shows 4 small blocks, fixed to 24h (`api.ts:253`) | Thin |
| Conversations per social media on the left | One flat list with filter buttons (`SidebarNav.tsx:272-280`, `396`) | **Not grouped** |
| Click a conversation, see messages | Works: `App.tsx:89-96` fetches messages for the open thread | Works, rough edges (section 3) |
| Link other channels | Only a WhatsApp form exists (`MetaSettingsModal.tsx:269-343`). No Instagram or Facebook connect button anywhere after login | **Missing** |

## 2. High severity (fix first)

**H1. The user does not land on the dashboard.**
Change `middleware.ts:22` and `login/page.tsx:37` to `/dashboard`. The Instagram callback redirect lives in the backend. Check its `Location` header: if it is `/`, change it to `/dashboard`. Nothing on the frontend can tell "just came back from Instagram" apart from a normal visit to `/`, so this one needs the backend.

**H2. A logged-in tenant cannot connect Instagram or Facebook, and cannot re-authorize Instagram.**
- `/login` is blocked for anyone with a cookie (`middleware.ts:22`).
- `INSTAGRAM_LOGIN_URL` is only used on the login page (`login/page.tsx:188`).
- So an email-login tenant, or a WhatsApp-first tenant, has no way to link Instagram.
- `ProfileModal.tsx:509` even tells the user to "Log in with Instagram again", which is impossible while logged in.
- Facebook has no connect flow at all.

Fix: add a "Connect Instagram" `<a href={INSTAGRAM_LOGIN_URL}>` to the Channels modal (and to the profile modal's "didn't respond" hint). Backend-dependent: I cannot see whether that endpoint attaches the account to the current session's tenant or logs in as the account's own tenant. Test it before shipping the button.

**H3. Any error signs the user out, and a backend outage causes an endless reload loop.**
- `App.tsx:54-62` and `PageHeader.tsx:229-233`: if `getMyTenant()` fails for any reason (a 500, a network blip, a restarting backend), the code calls `logout()` then goes to `/login`.
- `logout()` (`api.ts:137-139`) is a fetch through the same proxy. If the backend is down it cannot clear the cookie (or it throws, and the redirect never runs).
- The cookie is still there, so middleware bounces `/login` back to `/` (`middleware.ts:22`), `/` fails again, and the page reloads forever.
- Only a 401 should mean "signed out". Other errors should show "Can't reach server, retrying".
- The 5-second poll (`App.tsx:78`) only does `console.error`. A session that expires later never sends the user to login. `/dashboard` (`dashboard/page.tsx:75`) shows the raw text "Failed to load dashboard (401)" and stays there.

Fix, kept small:
```ts
// api.ts: one wrapper for every call
export async function apiFetch(url: string, init?: RequestInit) {
  const res = await fetch(url, init);
  if (res.status === 401) { await logout().catch(() => {}); location.assign('/login?expired=1'); }
  return res;
}
// logout(): wrap the fetch in try/catch so it never throws
// middleware.ts:22: only bounce when not expired
if (hasSession && isLogin && !req.nextUrl.searchParams.has('expired'))
  return NextResponse.redirect(new URL('/dashboard', req.url));
```
Then in `getMyTenant` catch, sign out only on 401.

**H4. "Save Configuration" overwrites your real business name with the mock name.**
`MetaSettingsModal` is always mounted (`App.tsx:425`), so `useState(businessName)` at `MetaSettingsModal.tsx:61` runs once, at first render, when `businessName` is still the mock default "Himalayan Silk & Handicrafts" (`App.tsx:25`). The tenant name arrives later but the input never updates. Open Channels, press Save, and the header shows the mock name. Nothing is sent to the backend either, so the "save" is fake.
Fix: `useEffect(() => setBName(businessName), [businessName, isOpen])`. Either add a `PATCH /tenants/me` call (needs a backend endpoint) or make the field read-only for now. Also change the initial state at `App.tsx:25` to `''` so the mock name never flashes in the header.

**H5. Fake "connected" and "200 OK" statuses hide real problems.** A tenant with nothing connected sees everything green.
- `MetaSettingsModal.tsx:186-200`: Facebook "LINKED & ACTIVE", page "Himalayan Silk", from `initialMetaStatus` (`mockData.ts:229-248`).
- `MetaSettingsModal.tsx:214-228`: Instagram "VERIFIED", handle `@himalayan_silk_np`. A real endpoint exists (`getInstagramProfiles`), but this card ignores it.
- `MetaSettingsModal.tsx:105-112`: "PING WEBHOOKS" waits 800 ms and prints "HTTP 200 OK — Inbound Webhooks Verified". It calls nothing.
- `MetaSettingsModal.tsx:62,401`: a fake verify token and callback URL `api.socialsync.np/v1/meta/webhook`. If someone copies these into Meta, webhooks fail.
- `RightInspector.tsx:185-211`: "ACTIVE CHANNELS" f/i/w icons and "Meta Webhooks 200 OK" are static.
- `Header.tsx` receives `metaStatus` but never uses it (dead prop).

Fix: drive the Instagram card from `getInstagramProfiles()`, the WhatsApp card is already real, show "Not connected" plus a Connect button for Facebook, delete the fake ping and the fake URL/secret, and derive the inspector's channel icons from the same two real calls.

## 3. Medium severity

**M1. Conversations are not grouped by social media.** `SidebarNav.tsx:396` renders one list. Group `filteredThreads` under Instagram / WhatsApp / Facebook headings with counts. The "ALL / IG / WA / FB" buttons can stay. The header count "N ACTIVE" (`:314`) counts every thread, not active ones.

**M2. The message pane is hard to use.**
- No scroll-to-latest (`InboxFeed.tsx:284`). Opening a long chat shows the oldest messages; new ones arrive off-screen.
- No loading or empty state. On switching threads the pane is blank until the fetch returns (`messages: []` at `api.ts:227`).
- Add a ref at the end of the list and scroll on `thread?.id` and `thread?.messages.length`. The hook must go above the early return at `InboxFeed.tsx:78`.

**M3. Real messages are labelled with fake or empty AI data.**
- Every AI message shows `CONFIDENCE: 0.00` and `SOURCE:` with nothing after it (`InboxFeed.tsx:330,333`). The API never returns these values.
- The label says "SocialSync AI (RAG-Enabled)" (`:316`), an old product name.
- Backend `system` and `agent` messages both become `human` (`api.ts:209`), so they show as "Human Operator (Merchant) / OPERATOR OVERRIDE SENT VIA GRAPH API" (`InboxFeed.tsx:359,370`).
- Sidebar cards show `CONF: 0.00` for every real thread (`SidebarNav.tsx:455`). Live Context shows blank intent and a blank source badge (`RightInspector.tsx:41,72`).
- Fix: render each badge only when its value exists; map `system` to its own style; rename the label to "Sanchar AI".

**M4. "Take over as human" does not stick.** `App.tsx:122-139` only edits local state. The next poll (`App.tsx:73-75`) rebuilds `status` from the server's `mode`, so it flips back within 5 seconds. It needs a backend endpoint (for example `PATCH /conversations/{id}` with `mode`). Until then, hide the button. Also unknown: whether sending a human reply stops the AI from auto-replying on the backend.

**M5. Sending a reply can lose the text.**
- `InboxFeed.tsx:96-100` clears the input before the send finishes. On failure `App.tsx:155` shows `alert()` and the typed text is gone. Make `handleSend` async, clear only on success, and show an inline error.
- `InboxFeed.tsx:433` always says "Meta Customer Service Window: Active • Encryption: E2E Verified", and `:163` "24h Window: Active" (only when a city exists, so never on real data). Instagram only accepts free-form replies within 24 hours of the customer's last message. Compute this from `lastMessageAt` and disable Send when expired (the exact rule for your app's messaging permissions is a backend/Meta detail).

**M6. Sidebar previews show "No messages yet" for every thread you have not opened** (`SidebarNav.tsx:398,437`), because messages load only for the open thread. The conversations endpoint should return `last_message` text. Backend change.

**M7. Dashboard gaps** (`dashboard/page.tsx`, `api.ts:253`)
- Fixed 24 hours, no selector, no refresh (`getDashboard(days = 1)`). Add 1/7/30 buttons.
- Always lists WhatsApp, Facebook and Instagram (`:49-53`). A new Instagram-only tenant sees a wall of zeros and no "Connect WhatsApp" hint. Show connected channels only, with an empty-state link.
- `counts[ch]` (`:63`) prints `undefined` if the backend omits a key. Use `?? 0`.
- The header escalation badge sums the window's `handover` counts (`:82`). The inbox badge counts threads currently in `NEEDS_HUMAN` (`App.tsx:103`). Same label, two different numbers.
- The Instagram numbers you have (followers, following, posts) sit behind the avatar click in `ProfileModal`. For "dashboard with all metrics available", show that card on the dashboard.
- No link from a dashboard number to the conversations behind it.

**M8. Static files redirect to login, which hurts the SEO you plan.** `middleware.ts:27` no longer skips paths with a file extension (`middleware.ts.bak` had `.*\\..*`). Logged-out visitors and crawlers get sent to `/login` for `/robots.txt`, `/sitemap.xml`, og images and anything in `public/`. Use `'/((?!api|_next|favicon.ico|.*\\..*).*)'`.

**M9. Error messages can print `[object Object]`.** `api.ts:134` and `:321` pass FastAPI's `detail` straight to `Error`. On a 422 that is an array. `linkWhatsApp` (`:309`) already handles this; copy that check.

## 4. Low severity: mock code, cleanup, Meta review

**Mock data that looks real (all seen by a real tenant)**
- Store Catalog panel: mock products, hard-coded "Delivery Rs. 150 / Rs. 100" and "VINTAGE5" policy (`RightInspector.tsx:107,117`, `mockData.ts`).
- Footer: `LATENCY` and `TOKEN_USAGE 412/10000` are fake numbers (`App.tsx:99-100`, `Footer.tsx`).
- The Catalog/FAQ modal only edits in-memory state and is lost on reload (`App.tsx:29-30,327-337`).
- `+ INBOUND`, `SIMULATE CUSTOMER`, RAG Sandbox and `AI DRAFT` call `/api/v1/ai/reply`. `api.ts:165` says this 404s until the LLM layer exists. I cannot confirm that against your backend. Simulated threads use ids like `thread-…` and vanish at the next poll. `AI DRAFT` on failure fills the box with a canned Nepglish "we're reviewing" apology (`InboxFeed.tsx:120`) that a user could send to a customer. Put all of these behind a dev flag.
- `Header.tsx:184-192`: the "LOGIN / SIGN UP" button (dead, no handler) shows while the tenant loads. The avatar always reads "NP" (`avatarInitials` is never set).
- `select-none` on the app root and login page stops users copying text.

**Dead or risky files**
- `app/api/meta/*` is a mock webhook and connection test. `test-connection` always returns success. `webhook` has no signature check, and anyone can POST there and read the payloads back through `webhook-logs`. If Meta is ever pointed at this URL it gets a 200 and your customers' messages silently vanish. Delete the folder. `app/api/health` says "SocialSync" and reports a Gemini key (`route.ts:6-7`).
- Delete `app/api/amit/page.tsx` (an empty page that creates a public `/api/amit` route) and `middleware.ts.bak`. Untrack `tsconfig.tsbuildinfo`.
- `conversation_example.json` is tracked and contains real Instagram usernames and IDs. Remove it or anonymise it.
- The webhook exemption (`middleware.ts:11-13`) only means "do not rewrite". Next has no route there, so a webhook sent to the frontend origin returns 404. Meta must point at the backend directly (nginx in production, or a tunnel to FastAPI in testing).

**Meta app review and SEO**
- Terms and privacy on the login page are plain `<span>`s (`login/page.tsx:246-248`). Meta needs a public privacy-policy URL and, for Instagram/Facebook login, a data-deletion URL. Create `/privacy`, `/terms` and `/data-deletion`, and add them to the middleware allow-list. The footer claims "Meta Graph v21.0 Compliant" and "GDPR / Nepal Telecomm Ready" (`:287-289`), which you should not claim before review.
- The app is client-only (`ssr:false`, login-gated), so only `/login` is indexable. That is fine now. Later, put a public landing page at `/` and move the inbox to `/inbox`. That touches `middleware.ts:22`, `PageHeader.tsx:239`, `App.tsx:118` and `login/page.tsx:37`.
- `layout.tsx`: Twitter card is `summary_large_image` but there is no image; no `metadataBase`; Google Fonts are loaded by a `<link>` instead of `next/font`.

## 5. What I could not verify (depends on the backend)
1. Where the Instagram callback redirects (H1).
2. Whether the Instagram login endpoint attaches to the current tenant when a session exists (H2).
3. The array order of `/conversations` and `/messages` (the UI assumes newest thread first, oldest message first).
4. Whether `/api/v1/ai/reply` exists, whether a takeover endpoint exists, and whether `mode` can be values other than `ai` (any non-`ai` value shows as "NEEDS HUMAN", `api.ts:226`).
5. Whether `BACKEND_URL` is read at runtime inside the container (the checked-in `.next` build is old, so I could not confirm).
