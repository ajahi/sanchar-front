# Sanchar frontend: review and flow check (Instagram login -> dashboard -> conversations)

I read every file on the flow (`middleware.ts`, `app/*`, `src/App.tsx`, `src/api.ts`, `Header`, `PageHeader`, `SidebarNav`, `InboxFeed`, `RightInspector`, `MetaSettingsModal`, `ProfileModal`, `mockData.ts`, `app/api/**`, Docker files). `npx tsc --noEmit --incremental false` passes with no errors. Nothing was run against your backend, so anything that depends on backend behaviour is labelled **[backend]**.

## Verdict

The plumbing works: login link, `/api/v1` proxy, cookie check, inbox list, message fetch, send. The real problems are these:

1. After login the user lands in the **inbox, not the dashboard**.
2. Several screens **show fake "connected / verified / AI confidence" data as if it were real**.
3. Two defects can put **fake text in front of a real customer**.
4. A backend blip **logs the user out**.

## How the flow actually runs today

| Step | Intended | Actual | Where |
|---|---|---|---|
| Login | "Continue with Instagram" | Plain `<a>` to `/api/v1/social-accounts/instagram/login`, rewritten to FastAPI. Correct. | `login/page.tsx:186`, `middleware.ts:15-17` |
| Callback | Backend sets `ns_session` and redirects | Unseen **[backend]**. Failures come back as `/login?ig_error=` and are shown. Correct. | `login/page.tsx:21-25` |
| Landing | **Dashboard** | **Inbox `/`**. A user with a cookie who hits `/login` is bounced to `/`, and the email login does `assign('/')`. | `middleware.ts:22`, `login/page.tsx:37` |
| Dashboard | All metrics | Separate page reached by a header pill. Four count blocks over a fixed 24h. | `Header.tsx:91`, `dashboard/page.tsx` |
| Conversations per social media | Left list grouped by channel | One mixed list with All/IG/WA/FB filter buttons. No per-channel counts. | `SidebarNav.tsx:71-116` |
| Click a conversation | Messages appear | Works. Messages are fetched for the open thread only. | `App.tsx:89-96` |

## Findings, ranked

### P0: blocks the intended flow or can hurt a real customer

**1. Login lands on the inbox, not the dashboard.** Two frontend lines, plus the backend callback.
- `middleware.ts:22`: `/` should be `/dashboard`.
- `login/page.tsx:37`: `assign('/')` should be `assign('/dashboard')`.
- **[backend]** The Instagram callback's final redirect is almost certainly `/`. It needs to go to `/dashboard`. I can't see it.

Options considered:

| Option | Backend change? | Keeps `/` free for a public SEO landing? | Diff size | Verdict |
|---|---|---|---|---|
| A. Point the two redirects at `/dashboard` and change the backend callback | 1 line | Yes | 2 lines here | **Choose** |
| B. Move the inbox to `/inbox` and redirect `/` to `/dashboard` for signed-in users | none | Partly | About 8 references (`PageHeader.tsx:37,40`, `App.tsx:118`, ...) | Fallback if the backend can't change this week |
| C. Detect "just came from OAuth" in the frontend | none | Yes | Hacky (referrer or extra cookie) | Reject |

**2. "AI DRAFT" puts a fake Nepglish apology into the reply box when the call fails, and the SEND button will send it.**
- `InboxFeed.tsx:118-121`: on any error it fills the input with "Namaste! Hamro store bata hajur ko query review bhairakheko cha...".
- `/api/v1/ai/reply` returns 404 today (`api.ts:41`), so the button is guaranteed to hit this path. A merchant can send that text to a real Instagram customer.
- Fix: show an inline error and leave the input empty, or hide the button until the endpoint exists.

**3. Quick-reply chips are fabricated business promises, one click from SEND.**
- `InboxFeed.tsx:126-131` includes "10% discount approve bhayo! Coupon code: VINTAGE10", "express delivery ... 11 baje" and a fake tracking link.
- Delete them, or load per-tenant templates from the backend.

**4. Any backend error at page load logs the user out.**
- `api.ts:25` throws "Not authenticated" for any non-OK status (500, 502 and so on).
- `App.tsx:61` and `PageHeader.tsx:30` then call `logout()`, which clears the cookie and redirects to `/login`.
- A backend restart or deploy therefore kicks every open tab out.
- Fix: throw a typed error only for 401 and 403. For other errors, show a retry banner and keep the session.

### P1: real bugs on the intended path

**5. Static files and `/public` redirect to `/login` for signed-out visitors.**
- `middleware.ts:27` matcher is `'/((?!api|_next|favicon.ico).*)'`.
- The old matcher (`middleware.ts.bak`) also excluded `.*\\..*`.
- `robots.txt`, `sitemap.xml`, `/sanchar-mailbox.svg`, og images and any future favicon set all redirect. This directly hurts your SEO plan.
- Fix: `matcher: ['/((?!api|_next|.*\\..*).*)', '/api/v1/:path*']`.

**6. A failed Instagram login can vanish silently if a stale cookie exists.**
- `middleware.ts:22` redirects any `/login?...` request that has a cookie to `/`, dropping `ig_error`.
- The user then reaches the inbox, `getMyTenant` fails, `logout()` runs, and they land on `/login` with no message.
- Fix: skip the bounce when `search` contains `ig_error`, for example `hasSession && isLogin && !search`.

**7. The takeover button doesn't persist.**
- `App.tsx:122-139` only edits local state.
- `api.ts:102` maps `mode === 'ai'` to AUTO_PILOT, so the next 5s poll (`App.tsx:80`) reverts the button.
- It needs a PATCH `/conversations/{id}` endpoint **[backend]** and an API function.

**8. Thread status is derived wrongly.**
- `api.ts:102`: anything whose `mode` isn't exactly `'ai'` is shown as NEEDS HUMAN. A `paused` or `closed` mode is counted as an escalation.
- `ConversationDto.status` (open or closed) is fetched and never used.
- The result is inflated red badges (`App.tsx:103`, `SidebarNav.tsx:133`).
- Confirm the possible `mode` and `status` values **[backend]**, then map explicitly.

**9. The Channels modal shows fake connection data.**
- `MetaSettingsModal.tsx:186-189` always shows Facebook as "LINKED & ACTIVE".
- `MetaSettingsModal.tsx:214-216` always shows Instagram as "VERIFIED".
- Both read `initialMetaStatus` in `mockData.ts:229-248` (Himalayan Silk, `@himalayan_silk_np`, fake IDs).
- Only the WhatsApp card is real.
- Instagram already has a real endpoint (`getInstagramProfiles`, used by `ProfileModal`). Use it here.
- There is **no Facebook connect flow at all**, although the login page advertises Facebook.
- `RightInspector.tsx:183-212` shows an "ACTIVE CHANNELS" stamp with all three channels and "Meta Webhooks 200 OK", both hardcoded.

**10. The modal's Business Name field starts as a hardcoded demo name, and Save can write it back.**
- `MetaSettingsModal.tsx:61`: `useState(businessName)` runs once, at first render.
- `App.tsx:25` defaults `businessName` to "Himalayan Silk & Handicrafts (काठमाडौँ)", and `App.tsx:339-457` keeps the modal mounted.
- So the field holds the demo name even after `getMyTenant` returns the real one.
- Pressing "Save Configuration" (`:114`) then overwrites the header with the demo name.
- Nothing is persisted either way.
- Fix: sync the state when `isOpen` turns true, start `businessName` as `''`, and either call the backend or remove the Save button.

**11. "PING WEBHOOKS" always reports success.**
- `MetaSettingsModal.tsx:105-111` waits 800ms and prints "HTTP 200 OK - Inbound Webhooks Verified for Messenger, Instagram, & WhatsApp".
- It does not call anything.
- The card beside it (`:399-406`) shows a callback URL `https://api.socialsync.np/v1/meta/webhook` and a verify token `socialsync_meta_wh_sec_991823`. Neither matches your real `/api/v1/webhooks/*`.
- A tenant could paste these into Meta.
- Remove the card and the ping, or wire them to the real WhatsApp status data (`waChecks`, already correct).

**12. Real AI messages render with fake metadata.**
- `InboxFeed.tsx:330-333`: every real AI message shows "CONFIDENCE: 0.00" and "SOURCE: " (blank). The backend DTO carries neither, `api.ts:70-78`.
- The label is "SocialSync AI (RAG-Enabled)" (`:316`), which is the old product name.
- `SidebarNav.tsx:208` shows "CONF: 0.00" on every real thread.
- `api.ts:85` maps `sender_type: 'system'` to `'human'`, so system notices render as "Human Operator (Merchant)" with "OPERATOR OVERRIDE SENT VIA GRAPH API" (`InboxFeed.tsx:369`).
- Fix: render the badges only when the value exists, map `system` to its own style, and say "AI".

**13. The message pane doesn't scroll to the newest message.**
- `InboxFeed.tsx:284-375` has no scroll ref or effect.
- A long conversation opens at the top, and messages arriving through the 5s refetch land off-screen.
- Add a ref and `scrollIntoView` on `[thread.id, thread.messages.length]`.

**14. Sending loses your text on failure.**
- `InboxFeed.tsx:99` clears the input before the request finishes.
- On failure, `App.tsx:155` uses a blocking `alert()` and the text is gone.
- Clear the input only after success, and show an inline error.

### P2: dashboard and conversation-list gaps (both partly **[backend]**)

**15. Dashboard vs "all the metrics".**
- `dashboard/page.tsx` shows four blocks (`getDashboard(days=1)`, `api.ts:129`): new messages, top queries, handled and handover, per channel. The window is fixed at 24h with no selector.
- A user who just logged in with Instagram sees WhatsApp and Facebook rows of zeros and no prompt to connect them (`:19-24`). Render only connected channels, and add an empty state linking to Channels.
- The response is trusted as-is (`Counts` reads `counts[ch]`). A missing key prints `undefined`.
- The dashboard header badge is a 24h sum of handover (`:41`). The inbox badge is a count of open NEEDS_HUMAN threads (`App.tsx:103`). Same label, two different numbers.
- Response time, AI-vs-human split, open conversations and unread counts are not requested. If those are the "metrics" you meant, the backend has to expose them.

**16. Left list vs "conversations per social media".**
- It is one list with filter buttons (`SidebarNav.tsx:71-116`), with no per-channel counts on the buttons.
- The list is not sorted client-side (`App.tsx:73-75`); it relies on backend order **[backend]**.
- `unreadCount` and `unread` exist in `types.ts` and are never populated, so there is no unread indicator.
- Previews are empty for every thread you haven't opened (`SidebarNav.tsx:151`, `:190` "No messages yet"), because only the open thread's messages load. Return `last_message` from `/conversations` **[backend]**.
- No pagination on conversations or messages. The polling refetches the whole list every 5s (`App.tsx:80`).

**17. The dead "LOGIN / SIGN UP" button.**
- `Header.tsx:185-192` renders it whenever `currentUser` is null, and `onOpenAuthPage` is never passed.
- It appears for a moment on every load (inbox and dashboard) and does nothing.
- Render nothing instead.

**18. Session expiry mid-session is silent in the inbox.**
- `getMyTenant` runs once (`App.tsx:55`).
- After that, the 5s poll only calls `console.error` (`:78`), and a 401 never sends the user back to `/login`.
- Handle 401 in one shared `fetch` wrapper in `api.ts`, together with finding 4.

### P3: mock and dead code that misleads

  - Hide them behind `process.env.NEXT_PUBLIC_DEV_TOOLS`.
- **Catalog and FAQ.** These are in-memory only (`App.tsx:29-30`, `InventoryModal`). The "RAG Policy Note" and delivery prices in `RightInspector.tsx:105-118` (code VINTAGE5) are hardcoded fiction. "RAG ACTIVE" (`:31`) and the "Language" buttons don't affect anything real.
- **Footer** (`Footer.tsx`). "TOKEN_USAGE 412/10000", "LATENCY 1.2s", "SYSTEM ID: SS-AI-KATHMANDU-01" and "(C) 2026 SOCIALSYNC AI" are constants.
- **Unfounded claims in the UI.**
  - `InboxFeed.tsx:163`: "Meta 24h Window: Active".
  - `InboxFeed.tsx:433`: "Encryption: E2E Verified".
  - `login/page.tsx:92`: "FREE FOREVER".
  - `login/page.tsx:96`: "META GRAPH API v21.0".
  - `login/page.tsx:284-291`: "ESTD. 1932" and "GDPR / Nepal Telecomm Ready".
  - These are risky for Meta app review and for legal reasons. The 24h window value is not computed from anything.
- **`app/api/meta/*`.** All of it is dead mock code, and it is **publicly reachable**, because the middleware matcher skips `api`.
  - `webhook/route.ts` accepts unauthenticated POSTs and does no HMAC check.

- **`app/api/health/route.ts`.** Its name is "SocialSync" and it leaks `hasGeminiKey` publicly. Either return `{status:'ok'}` and wire it into a Docker `healthcheck`, or delete it.
- **Housekeeping.** `app/api/amit/page.tsx` publishes an empty `/api/amit` route. `middleware.ts.bak` and `tsconfig.tsbuildinfo` are tracked in git, so every commit touches the latter.

## Middleware and infrastructure notes

- `middleware.ts:19` only checks that the cookie **exists**. That is fine for routing, since the backend validates it, but it means an expired cookie reaches the inbox.
- `middleware.ts:11` lets `/api/v1/webhooks/*` fall through to Next, which has no route and returns 404. That is correct only if nginx routes webhooks to FastAPI first. `docker-compose.yml` contains no nginx, so local or ngrok webhook testing against port 3000 will 404 **[infra]**.
- `login/page.tsx:36-37` and `PageHeader.tsx:22-25` are correct in using a full page load so the middleware sees the cookie.
- Terms and privacy on the login page (`:246-248`) are `<span>`s, not links. Meta app review needs a real privacy policy URL and a data-deletion URL.

## SEO (for later)

- The whole app is behind login, so only `/login` is indexable. That is fine now.
- `app/layout.tsx` gives every route the same title and description ("Sanchar AI - Omnichannel RAG Dispatch"). Add `robots: {index:false}` metadata on `/dashboard` and the inbox, and give `/login` its own metadata.
- Fonts load through a `<link>` to Google Fonts in `layout.tsx:19-25`. Use `next/font` when you tune performance.
- Before SEO work, decide `/` (public landing) vs `/inbox`. Finding 1 option B gets you there.
