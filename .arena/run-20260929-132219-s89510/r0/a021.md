# Sanchar frontend: review and flow check

I read every file on the login, dashboard and inbox path, plus the middleware, API client, Docker files and `app/api/*`. `npx tsc --noEmit --incremental false` passes. I did not run the app against your backend, so anything that depends on FastAPI is marked **[backend]**.

## Verdict

The real plumbing works: Instagram login link, cookie through the proxy, conversation list, message list, send reply, sign-out. Around it, the flow you described is not what a tenant sees:

| Your intended step | What the code does | Status |
|---|---|---|
| Log in with Instagram | `login/page.tsx:186-194` links to `/api/v1/social-accounts/instagram/login`. Failures come back as `?ig_error` and are shown (`:21-24`). | Works |
| Land on the dashboard | Every frontend exit goes to `/`, the inbox: `middleware.ts:22` and `login/page.tsx:37`. The OAuth callback redirect is in the backend **[backend]**. | **Diverges** |
| Dashboard with all metrics | `/dashboard` shows 4 count blocks for the last 24 hours (`api.ts:129`, `dashboard/page.tsx:54-70`). It has no Instagram account stats, no channel health and no time range. | Thin |
| Conversations per social media on the left | One mixed list with All/IG/WA/FB filter buttons (`SidebarNav.tsx:25-33, 72-116`). No grouping and no counts per channel. | Partial |
| Click a conversation to see its messages | `App.tsx:88-96` fetches the messages. The chat pane never scrolls to the newest message, and AI bubbles show fake metadata. | Works with bugs |

## Findings, most severe first

### 1. Login does not land on the dashboard
Both frontend exits send the user to `/` (the inbox), and the OAuth callback probably does too **[backend]**. Fixing only the two frontend redirects is not enough. The fix that does not depend on the backend is to make `/` a redirect and move the inbox to `/inbox`. This also frees `/` for a public landing page later, which helps your SEO plan.

```diff
--- app/page.tsx
-'use client';
-import dynamic from 'next/dynamic';
-import { Loader } from '../src/components/Loader';
-const App = dynamic(() => import('../src/App'), { ssr: false, loading: () => <Loader /> });
-export default function Page() { return <App />; }
+import { redirect } from 'next/navigation';
+export default function Page() { redirect('/dashboard'); }
```
Move the old body of `app/page.tsx` to a new `app/inbox/page.tsx` (with `'use client'`, and the `../../src/...` paths). Then change these:
- `src/components/PageHeader.tsx:495` → `router.push(tab === 'inbox' ? '/inbox' : \`/inbox?tab=${tab}\`)`
- `src/components/PageHeader.tsx:498` → `router.push('/inbox?tab=inbound')`
- `src/App.tsx:118` → `window.history.replaceState(null, '', '/inbox')`
- `src/components/Header.tsx`: make the logo a `<Link href="/dashboard">`. It is not a link today.

The middleware redirect at `middleware.ts:22` and `login/page.tsx:37` can stay on `/`, because `/` now forwards to the dashboard. Also stop the stale-cookie case from dropping `?ig_error`: change `:22` to `if (hasSession && isLogin && !search) return ...`.

### 2. Session expiry and sign-out are fragile
- **Inbox never re-checks the session.** `getMyTenant` runs once (`App.tsx:54-62`). The 5-second poll (`:69-78`) only calls `console.error` on a 401. The user sees a frozen inbox and is never sent to `/login`. Fix: make `listConversations` (`api.ts:106-110`) throw a marked error on 401 and call `handleSignOut` from the poll's `.catch`.
- **Transient errors log the user out.** `.catch(handleSignOut)` at `App.tsx:61` (and `PageHeader.tsx:488`) fires on any failure, including a 502 or a network blip. If the backend is down, `logout()` (`api.ts:13-15`) also throws. There is no `try/catch`, so the user is stuck on a blank inbox. Fix: only sign out on 401, and wrap `logout()` in `try { … } catch {}` before `location.assign('/login')`.
- **`[object Object]` errors.** `api.ts:10` and `:197` throw `detail` unchecked. FastAPI returns an array on a 422, so the user sees "[object Object]". Reuse the `typeof detail === 'string'` check from `api.ts:185-186`.

### 3. Fake data shown as real, or sent to real customers
This is the largest gap between "testing" and a real tenant seeing the app.
- **Wrong business name.** `App.tsx:25` starts as "Himalayan Silk & Handicrafts". `MetaSettingsModal.tsx:61` copies that into `bName` once at mount, and the modal is always mounted. So "Save Configuration" (`:114-117`) writes the fake name over the real one in the header. It also saves nothing to the server.
- **Fake connection cards.** Facebook shows "LINKED & ACTIVE" and Instagram shows "VERIFIED" from `initialMetaStatus` (`mockData.ts:229-248`; `MetaSettingsModal.tsx:186, 194, 198, 214, 222, 226`). The real Instagram data is available from `getInstagramProfiles` and is not used here. `RightInspector.tsx:183-213` shows a static "ACTIVE CHANNELS / Meta Webhooks 200 OK" panel.
- **Fake ping.** `handleTestPing` (`MetaSettingsModal.tsx:105-112`) waits 800 ms and always prints "HTTP 200 OK — Inbound Webhooks Verified". Remove it. The WhatsApp PING (`:254-260`) is the only honest one.
- **Hard-coded webhook details.** The callback `https://api.socialsync.np/v1/meta/webhook` and the verify token `socialsync_meta_wh_sec_991823` are in the client bundle (`:62, 401-405`). If that token is real, treat it as leaked and rotate it.
- **Canned replies with made-up promises.** `InboxFeed.tsx:126-131` offers one-click replies with "10% discount… VINTAGE10", "express delivery… 11 baje" and "courier.np/track/SS98234". One click and Send posts this to a real Instagram customer. Delete them.
- **Mock catalog and policy panel.** `RightInspector.tsx:92-119` shows pashmina prices, delivery fees and a discount policy to every tenant. `Footer.tsx` and `App.tsx:99-100` show fixed token usage (412) and latency (120 ms). The header says "Omnichannel v21.0".
- **Simulator and sandbox.** "+ INBOUND", "SIMULATE CUSTOMER", "AI DRAFT" and the RAG sandbox call `/api/v1/ai/reply`, which `api.ts:41` says 404s until the LLM layer exists. Threads created by the simulator (`App.tsx:252-324`) vanish at the next poll. On failure, "AI DRAFT" puts a Nepali "we are reviewing" sentence into the reply box (`InboxFeed.tsx:120`). Hide all of these behind `process.env.NEXT_PUBLIC_DEV_TOOLS`.

### 4. Conversation view bugs
- **No scroll to the latest message.** The message area (`InboxFeed.tsx:284-374`) has no ref and no `scrollIntoView`. A long chat opens at the top, and new messages arrive off-screen.
- **Every real AI reply shows "CONFIDENCE: 0.00" and an empty "SOURCE:"** (`:307-333`). The backend `MessageDto` (`api.ts:70-78`) carries neither field. Only show those badges when the values exist. The bubble is also labelled "SocialSync AI (RAG-Enabled)" (`:316`). Rename it to Sanchar.
- **All human bubbles say "OPERATOR OVERRIDE SENT VIA GRAPH API"** (`:369-371`). This includes `system` messages, which `api.ts:85` maps to `human`.
- **A failed send loses the draft.** `handleSend` clears the input before the send finishes (`:96-100`). `App.tsx:155` then shows `alert()`. Await the send, clear only on success, and show the error inline.
- **Sidebar preview is blank except for the open thread.** `SidebarNav.tsx:151, 190` reads `thread.messages`, which is only loaded for the active thread (`App.tsx:88-96`). Every other card says "No messages yet". Every card also shows "CONF: 0.00" (`:208`). Ask the backend for a `last_message` preview on `/conversations` **[backend]**, and hide CONF when undefined.
- **Sidebar counts.** "N ACTIVE" is just `threads.length` (`:67`). The active thread can be filtered out of the list but still open in the pane (`App.tsx:102`).
- **Takeover does not persist.** `handleToggleTakeover` (`App.tsx:122-139`) changes local state only. The next poll resets `status` from `mode` (`api.ts:102`), so the toggle reverts within 5 seconds. That line also maps any `mode` other than `"ai"` to NEEDS_HUMAN, so unknown modes inflate the escalation badge. Needs a PATCH endpoint **[backend]**.
- **Not keyboard-accessible.** Thread cards are `<div onClick>` (`SidebarNav.tsx:155-158`). Use `<button>`.

To get "conversations per social media" as you described, group `filteredThreads` by `channel` under three headings with counts. That is roughly 15 lines in `SidebarNav.tsx`.

### 5. Dashboard
- Fixed at `days=1` (`dashboard/page.tsx:34`), with no selector or retry after an error.
- Always renders WhatsApp, Instagram and Facebook rows (`:8-12`, `:19-24`). A tenant who just signed in with Instagram sees zeros for two channels and no prompt to connect them. Show connected channels only, plus a "Connect a channel" link.
- Nothing is shown from the data you already fetch elsewhere: Instagram followers/posts (`getInstagramProfiles`, shown only in the profile modal) and WhatsApp quality and webhook health (`getWhatsAppAccounts`). Add these as tiles if "all the metrics" is the goal.
- The header badge here is the sum of `handover` over the window (`:41`). The inbox badge counts threads currently needing a human (`App.tsx:103`). They are two different numbers under one label.
- The response shape is trusted. If a channel key is missing, `counts[ch]` renders as blank. `key={q.text}` (`:62`) breaks on duplicate queries.

### 6. Routes that bypass login, and routes login blocks
- **Open to anyone.** The matcher (`middleware.ts:27`) skips everything starting with `api`. So `/api/meta/webhook-logs` (returns logged payloads), `/api/meta/webhook`, `/api/meta/test-connection`, `/api/health` (reveals whether a Gemini key is set) and the empty page `/api/amit` are all public. The `webhook` route accepts any POST with no signature check and returns 200. If Meta is ever pointed at it, events are dropped silently. Delete `app/api/meta/`, `app/api/amit/` and `app/api/health/` (or make health return only `{status:'ok'}`).
- **Blocked for the public.** The old matcher in `middleware.ts.bak` excluded `.*\\..*`. The current one does not, so any file you add to `public/` (`robots.txt`, `sitemap.xml`, favicon, og image) redirects anonymous visitors, including Googlebot, to `/login`. Nothing in `public/` is referenced today, so nothing is broken yet.
- **Meta app review.** It needs a public privacy policy URL and a data-deletion URL. Terms and privacy on the login page are plain `<span>`s (`login/page.tsx:246-248`). Any new `/privacy`, `/terms` and `/data-deletion` page would also be redirected to `/login`. Fix the matcher and the check together:

```diff
-  matcher: ['/((?!api|_next|favicon.ico).*)', '/api/v1/:path*'],
+  matcher: ['/((?!api/(?!v1)|_next|.*\\..*).*)', '/api/v1/:path*'],
```
```diff
+const PUBLIC = ['/login', '/privacy', '/terms', '/data-deletion'];
-  const isLogin = pathname === '/login';
-  if (!hasSession && !isLogin) return ...
+  const isLogin = pathname === '/login';
+  if (!hasSession && !PUBLIC.includes(pathname)) return ...
```
This also puts `/api/*` non-v1 routes behind the check until you delete them.

### 7. Channels linking
- Only Instagram (login) and WhatsApp (manual IDs) can be linked. There is no Facebook connect action at all, although the UI shows Facebook as active.
- The WhatsApp form appears only when there are zero linked numbers (`MetaSettingsModal.tsx:269`), so a second number cannot be added.
- There is no "Connect / reconnect Instagram" button in the modal. The only path is logging out and in.
- `ProfileModal` shows "No Instagram account connected" to a WhatsApp-only tenant, and the header avatar always reads "NP" (`Header.tsx:165`, `avatarInitials` is never set).

### 8. Login page copy and SEO
- Unsupported claims: "FREE FOREVER FOR CORE FEATURES" (`:92`), "GDPR / Nepal Telecomm Ready" and "Meta Graph v21.0 Compliant" (`:287-289`), plus decorative "ESTD. 1932" and "Sulphur-Free". Remove them before Meta review.
- Email/password fields are labelled "signing up" (`:245`), but no sign-up or reset endpoint exists. Copy at `:264` says Instagram creates the workspace.
- `app/layout.tsx:8-13`: one global title and description for every route, no `metadataBase`, and `twitter: summary_large_image` with no image. Fonts are loaded with a `<link>` (`:19-24`) instead of `next/font`. When you build the public pages, give each its own `metadata`. Keep `/dashboard` and `/inbox` out of the index with `robots: { index: false }`.
- `/` is `ssr:false`, so a crawler that gets past the login redirect would see only a spinner. Fine for a private app, but public pages must not use that pattern.

### 9. Housekeeping
- Untracked or leftover files that are tracked in git: `middleware.ts.bak`, `tsconfig.tsbuildinfo` (add it to `.gitignore`), `conversation_example.json` (real Instagram usernames and IDs), `public/sanchar-mailbox.svg` (unused).
- `.dockerignore` excludes `.env*`, which is right. Compose needs `.env` with `BACKEND_URL` at runtime. If it is missing, the default `http://localhost:8000` (`middleware.ts:3`) points at the container itself and every API call fails.
- **[unverified]** Middleware builds redirects from `req.url` (`:21-22`). With `HOSTNAME=0.0.0.0` in the Dockerfile, check that nginx forwards `Host`, or the redirect may point at `0.0.0.0:3000`.
- `middleware.ts:12` returns `next()` for `/api/v1/webhooks/`. That path has no Next route, so it only works if nginx routes it straight to FastAPI, as the comment says.
