Scope: `C:\Users\Acer\Documents\development\next-app`. I read every file in the flow (middleware, login, dashboard, inbox `App.tsx`, `api.ts`, all components, `mockData.ts`, `app/api/**`, Dockerfile, compose, `.bak`). `npx tsc --noEmit` passes, so everything below is behaviour, not type errors. I did not run it against your backend. Anything that depends on FastAPI is tagged **[backend]** and collected in section 6.

## 1. One login, traced end to end

Take a tenant, Sita, who owns `@sita_shop` on Instagram and has never used Sanchar. Here is what the code does for her.

| # | What happens | Code | Matches intent? |
|---|---|---|---|
| 1 | She opens `/`. No `ns_session` cookie, so she is redirected to `/login`. | `middleware.ts:21` | Yes |
| 2 | She clicks "Continue with Instagram". A plain `<a>` goes to `/api/v1/social-accounts/instagram/login`. The middleware rewrites it to FastAPI, which redirects to instagram.com. | `login/page.tsx:188`, `middleware.ts:15-17`, `api.ts:29` | Yes |
| 3 | Instagram sends her back to the backend callback, which sets the httpOnly cookie and redirects somewhere. A failure comes back as `/login?ig_error=...`, and the `?` query survives the redirect. | `middleware.ts:21`, `login/page.tsx:22-27` | Yes **[backend]** |
| 4 | With the cookie set, `/login` redirects to `/`. The email login also ends at `/`. | `middleware.ts:22`, `login/page.tsx:37` | **No. `/` is the inbox, not the dashboard.** |
| 5 | The inbox loads as a client-only bundle. It reads `/tenants/me`, then `/conversations`. Sita has no conversations yet. | `app/page.tsx:8`, `App.tsx:54-85` | Partly |
| 6 | She sees "No threads match the selected filter" on the left, "No Thread Selected" in the centre, a Pashmina catalogue on the right and three green "ACTIVE CHANNELS". She has connected only Instagram. | `SidebarNav.tsx:146`, `InboxFeed.tsx:85`, `RightInspector.tsx:185-211` | **No** |
| 7 | She finds the small DASHBOARD pill and clicks it. She sees `Instagram 0`, `WhatsApp 0`, `Facebook 0`, for 24 hours only. | `Header.tsx:91`, `dashboard/page.tsx:19-24`, `api.ts:129` | Partly |

Verdict: the plumbing works (login, cookie, proxy, polling, message fetch, send). The flow diverges in three places: where she lands, what the empty and connected states say, and what "all metrics" contains. Section 5 also shows that several screens present invented data as real state.

## 2. Ranked findings

### Blocks or contradicts the intended flow

**H1. Login lands on the inbox, not the dashboard.**
There are three places to change, plus the backend.
- `middleware.ts:22`: `new URL('/', req.url)` should be `'/dashboard'`.
- `login/page.tsx:37`: `location.assign('/')` should be `'/dashboard'`.
- The backend OAuth callback's final redirect. It is not in this repo, so check it. If it redirects to `/`, fix it there. **[backend]**

Two related points:
- `Header.tsx` has a real `Link` to `/dashboard` but the INBOX pill goes to `/`. Once the landing moves, "Inbox" stays reachable in one click.
- Do not solve this by making `/` render the dashboard. That breaks `/?tab=…` (`App.tsx:114-119`, `PageHeader.tsx:37`).

**H2. Every future public page is blocked by the middleware, including the Meta-review pages.**
`middleware.ts:19-21` treats only `/login` as public. A `/privacy`, `/terms`, `/data-deletion` or a marketing landing page would redirect a logged-out visitor, or a Meta reviewer, or Googlebot, to `/login`. This is the real blocker behind "SEO later" and Meta app review. The terms and privacy text on the login page are `<span>`s (`login/page.tsx:246,248`), so nothing exists to link to yet.
Fix: add an allow-list.
```ts
const PUBLIC = ['/login', '/privacy', '/terms', '/data-deletion'];
const isPublic = PUBLIC.includes(pathname);   // + '/' if you build a landing page
if (!hasSession && !isPublic) return NextResponse.redirect(new URL('/login' + search, req.url));
if (hasSession && pathname === '/login') return NextResponse.redirect(new URL('/dashboard', req.url));
```

**H3. The matcher regressed from the old `middleware.ts.bak`, so files with an extension redirect to login.**
The `.bak` matcher ended `…|favicon.ico|.*\\..*`. The current `middleware.ts:27` dropped `.*\\..*`. Today nothing in the code references `/public` files, so nothing breaks yet. As soon as you add an OG image, `robots.txt`, `sitemap.xml`, a manifest or `public/sanchar-mailbox.svg`, logged-out crawlers get a 307 to `/login`.
Fix, using an allow-list rather than "any dot":
```ts
matcher: ['/((?!_next/|api/|favicon\\.ico|robots\\.txt|sitemap\\.xml|.*\\.(?:svg|png|jpe?g|webp|ico|webmanifest)$).*)', '/api/v1/:path*'],
```
Note: `api` (without a slash) in the current pattern also skips any page whose name starts with "api". Use `api/`.

**H4. The left column does not list conversations "per social media".**
`SidebarNav.tsx:64-140` renders one mixed, time-ordered list. A four-button filter (ALL/IG/WA/FB, default ALL) sits above it. IG/WA/FB filters show for channels the tenant never connected, and there are no per-channel counts. The header "N ACTIVE" (`:67`) counts all threads.
Change: group under IG / WhatsApp / Facebook headings with counts, or show tabs only for connected channels and default to the one that has threads. The data is already there (`thread.channel`).

**H5. A first-time tenant sees a broken-looking, misleading empty state.**
- `SidebarNav.tsx:146` says "No threads match the selected filter". With zero conversations it should say "No conversations yet. Send a DM to @your_handle to test," and link to Channels.
- `InboxFeed.tsx:85` says "Select a conversation from the left" when there is nothing to select.
- The dashboard shows zeros for two channels she never connected (`dashboard/page.tsx:19-24`).
- The Channels modal claims Facebook and Instagram are "LINKED & ACTIVE" and "VERIFIED" (see M3).
The right pane reads `getInstagramProfiles()` and `getWhatsAppAccounts()` only inside modals. Load them once and drive every "connected" indicator from that.

### Real bugs

**M1. Clicking "Save Configuration" overwrites the real business name with a mock name.**
`App.tsx:25` initialises `businessName` to `'Himalayan Silk & Handicrafts (काठमाडौँ)'`. `MetaSettingsModal.tsx:61` does `useState(businessName)`. The modal is always mounted, and returns `null` after its hooks (`:101`). So `bName` is captured once at mount with the mock value and never updates when `/tenants/me` returns the real name. Open Channels and press Save, without typing anything, and `onUpdateBusinessName('Himalayan Silk…')` (`:114-117`) replaces the header name. Nothing is saved to the backend either.
Fix: initialise `businessName` to `''`; give the modal `key={businessName}` or `useEffect(() => setBName(businessName), [businessName, isOpen])`; and either PATCH the tenant or remove the field.

**M2. Human takeover reverts within 5 seconds.**
`App.tsx:122-139` flips a local status only. The 5-second poll (`:67-85`) rebuilds every thread from the server's `mode` (`api.ts:102`). So "TAKE OVER AS HUMAN" and "RESOLVE & RE-ENABLE AI" appear to work, then undo themselves. It needs a backend PATCH such as `/conversations/{id}` with `{mode}` **[backend]**. Until then, disable the buttons or say "demo only".
Related: `api.ts:102` collapses everything that is not `mode==='ai'` into `NEEDS_HUMAN`, and ignores `c.status`. "Resolved" or "closed" conversations are counted as escalations in the badge (`App.tsx:103`, `SidebarNav.tsx:66`).

**M3. Fake connection state inside the real Channels modal.**
- `MetaSettingsModal.tsx:175-229`: Facebook and Instagram cards read `initialMetaStatus` (`mockData.ts:229-248`: "Himalayan Silk", `@himalayan_silk_np`). Their badges "LINKED & ACTIVE" and "VERIFIED" are literals (`:186-188`, `:214-216`).
- Only the WhatsApp card is live (`getWhatsAppAccounts`, `:70-77`).
- There is no "Connect Instagram" or "Connect Facebook" action in the modal. The only way to link Instagram is to sign in again. The Instagram card should use `getInstagramProfiles()` (`api.ts:149`), the way `ProfileModal` does.
- `PageHeader.tsx:38` passes `initialMetaStatus` into `Header`, which never uses it (`Header.tsx` does not destructure `metaStatus`). Drop the prop.

**M4. Fake webhook diagnostics in the Channels modal.**
- "PING WEBHOOKS" (`:105-112`) is a `setTimeout` that prints "HTTP 200 OK — Inbound Webhooks Verified for Messenger, Instagram, & WhatsApp". It tests nothing.
- The displayed callback URL `https://api.socialsync.np/v1/meta/webhook` and verify token `socialsync_meta_wh_sec_991823` (`:62`, `:401`) match neither your real path (`/api/v1/webhooks/…`, `middleware.ts:11`) nor the Sanchar name. If a tenant or teammate pastes these into Meta, delivery fails silently.
- Remove the block, or show the real values from the backend. The WhatsApp PING (`:254-260`) is the real check; keep that.

**M5. Real messages render with fake AI metadata and wrong sender labels.**
- `api.ts:85` maps `agent` and `system` to `'human'`. Every system note is shown as "Human Operator (Merchant)" with "OPERATOR OVERRIDE SENT VIA GRAPH API" (`InboxFeed.tsx:370`).
- Any real AI message shows `CONFIDENCE: 0.00` and `SOURCE:` empty (`InboxFeed.tsx:330,333`), because the API DTO has no confidence or source. Only render these badges when the value exists.
- `SidebarNav.tsx:208` shows `CONF: 0.00` on every real thread (`confidenceScore` is never set). Hide it when undefined.
- The AI label reads "SocialSync AI (RAG-Enabled)" (`InboxFeed.tsx:316`).

**M6. Opening a conversation does not scroll to the latest message.**
The message pane (`InboxFeed.tsx:284`) has no ref and no `scrollIntoView` (grep confirms none). A long thread opens at the oldest message and stays there when new ones arrive. Add a bottom sentinel and scroll when `thread.id` or `messages.length` changes. Messages also carry only `HH:MM` (`api.ts:80-81`), so a conversation spanning days shows ambiguous times. Add a date separator.

**M7. Messages fail silently, and the send box loses your text.**
- `App.tsx:88-96` logs a message-load error to the console. The pane just stays empty; a failure looks the same as "no messages".
- `InboxFeed.tsx:99` clears the input before the send resolves. On failure, `App.tsx:155` shows `alert()` and the draft is gone. Clear only on success and show the error inline.
- `InboxFeed.tsx:103`: `Enter` sends even while a Devanagari IME is composing. Guard with `!e.nativeEvent.isComposing`. This matters for Nepali typing.
- Sidebar previews read `thread.messages` (`SidebarNav.tsx:190`), which is empty for every thread except the open one, so previews say "No messages yet". Ask the backend for `last_message_preview` on `/conversations` **[backend]**.

**M8. Any hiccup logs the tenant out; expired sessions are only caught once.**
- `api.ts:25` throws for every non-OK status. `App.tsx:61` and `PageHeader.tsx:30` treat any throw as "dead session" and sign out, including a network blip or a 500. Only sign out on 401 (throw a typed error).
- The inbox checks the session once at mount. If the cookie expires later, the 5-second poll (`App.tsx:78`) only calls `console.error`, forever. The poll also keeps running in hidden tabs.
- `handleSignOut` (`App.tsx:47-50`) awaits `logout()` first. If that request fails, the redirect never happens. Wrap it in `try/finally`. **[backend]** whether logout clears the cookie when the session is already invalid; if not, `/login` and `/` bounce forever (`middleware.ts:22` versus `App.tsx:61`).

**M9. Poll drops locally created state.**
The poll rebuilds threads from the server (`App.tsx:73-75`). Any thread created by "+ INBOUND" or "SIMULATE CUSTOMER" disappears within 5 seconds, and its `askAi` call 404s (`api.ts:41`). This is one more reason to hide simulator features behind a dev flag.

### Dashboard specifics (`app/dashboard/page.tsx`, `api.ts:118-133`)

- Fixed window: `getDashboard()` is called with the default `days=1` (`:34`). There is no 7/30-day selector, no refresh, no auto-update. The "all metrics" the tenant expects is four blocks: new messages, top queries, handled, handover, all as per-channel counts.
- It always renders all three channels (`:19-24`). Instagram-only tenants get zero rows for the rest. Show connected channels only, with a "Connect WhatsApp" prompt.
- Missing channel keys render `undefined` (`counts[ch]` at `:22`). Use `?? 0`.
- The INBOX badge on the dashboard is the sum of handover counts over the window (`:41`). In the inbox it counts threads currently in `NEEDS_HUMAN` (`App.tsx:103`). Two different numbers under one label. Pick one.
- `key={q.text}` (`:62`) collides if the backend ever returns duplicates. Use the index.
- On failure it shows a bare "Failed to load dashboard (500)" (`:44`). Add a retry.

### Security and hygiene

**S1. Unauthenticated dev routes are live in the production build.**
`middleware.ts:27` skips `api`, so `app/api/**` bypasses the session check entirely:
- `POST /api/meta/webhook` accepts any JSON with no HMAC check and stores the payload in memory (`app/api/meta/webhook/route.ts`).
- `GET /api/meta/webhook-logs` returns those payloads to anyone.
- `/api/meta/test-connection` always returns success.
- `/api/health` returns "SocialSync AI Omnichannel Platform" and whether `GEMINI_API_KEY` is set.
- `app/api/amit/page.tsx` creates a blank public route `/api/amit`.
Meta does not post to these (it goes to FastAPI), so the only traffic is arbitrary. Delete `app/api/meta/**` and `app/api/amit/`; keep `/api/health` only if you need a container health check, and make it stop mentioning Gemini and SocialSync.

**S2. Repo hygiene.**
- `git ls-files` shows `middleware.ts.bak`, `tsconfig.tsbuildinfo` and `conversation_example.json` tracked. The last holds real Instagram usernames and IDs from a live test. Remove them and add `*.tsbuildinfo` and `*.bak` to `.gitignore`.
- `.env` files are correctly ignored and only `.env.example` is tracked.

**S3. Error text.** `api.ts:10` and `:197` use `detail` as the error message. FastAPI 422 responses return `detail` as an array, which becomes "[object Object]". `linkWhatsApp` (`:184-186`) already handles this; copy that.

**S4. Small UI defects.**
- `Footer.tsx:24`: `(latencyMs / 100).toFixed(1)s`, so 120 ms shows as "1.2s".
- `Footer.tsx:25-26`, `App.tsx:99-100`: "TOKEN_USAGE 412/10000" and "LATENCY" are constants, and the copyright line still says SOCIALSYNC AI.
- `Header.tsx:187` (LOGIN / SIGN UP) is a dead button (`onOpenAuthPage` is never passed). It flashes on the dashboard while the tenant loads. Render nothing while loading.
- `Header.tsx:165` hardcodes "NP" as the avatar.
- `InboxFeed.tsx:163` and `:433` claim "Meta 24h Window: Active" and "Encryption: E2E Verified" as fixed text. Compute the window from the last customer message, or remove it.
- `RightInspector.tsx:31,41,72`: "RAG ACTIVE", and blank intent and source for real threads (`detectedIntent` and `ragSourceDoc` are undefined). Lines 92-119 show a fake Pashmina catalogue with Rs. prices and a "VINTAGE5" discount note.
- `app/loading.tsx` is a blue Tailwind spinner from a template. It flashes when navigating between `/` and `/dashboard`. Reuse `<Loader/>`.
- `login/page.tsx:212,226`: `<label>` has no `htmlFor`, so the inputs are not labelled for screen readers.
- `login/page.tsx:264` says "New merchant? Connect with Instagram" but Facebook and WhatsApp are never offered on the login page.

## 4. SEO (later, but plan it now)

- Everything except `/login` needs a session, so today only `/login` is indexable. `/` is an app shell loaded with `dynamic(..., {ssr:false})` (`app/page.tsx:8`), so there is nothing to index there anyway. This is fine for an authenticated inbox.
- For SEO, give the app real public routes: `/` (landing), `/privacy`, `/terms`, `/data-deletion`, and move the inbox to `/inbox` (then `/` stops redirecting crawlers, and H1 and H2 above are the prerequisite).
- `app/layout.tsx`: one global title and description for every page; no `metadataBase`, canonical, `robots`, OG image or `twitter:image`, so `summary_large_image` has no image. `lang="en"` while the copy is Nepali and Devanagari. Fonts are loaded with a hand-written `<link>` (`layout.tsx`); `next/font` avoids the render-blocking request. Add `app/robots.ts` and `app/sitemap.ts`, and `noindex` for `/dashboard` and the inbox.
- The login page hero contains print-shop jokes ("ESTD. 1932", "PRICE 50 PAISA", "Meta Graph v21.0 Compliant", "GDPR / Nepal Telecomm Ready"). Compliance claims you cannot back up are a risk in Meta review. Remove them before submitting.

## 5. Infra note

`Dockerfile` and `docker-compose.yml` are sound for a standalone Next build with runtime `BACKEND_URL`. Two checks: the compose file has no healthcheck (use `/api/health` after cleaning it), and the `/api/v1/webhooks/` pass-through (`middleware.ts:11-13`) returns a Next 404 if nginx is not in front. That is correct in production and confusing on a laptop.

## 6. Depends on the backend, which I could not see

1. Where the Instagram callback redirects (H1). Whether it redirects with an absolute URL built from the internal host (`http://api:8000`) rather than the public origin, which would leave the user on an internal address.
2. Cookie attributes for `ns_session`. A `Secure` cookie is dropped over plain `http://localhost` and the user bounces back to `/login`. The Instagram redirect URI registered in Meta must be the public frontend origin.
3. Whether `/auth/logout` clears the cookie when the session is already invalid (M8).
4. Whether `/conversations` returns newest first, and `/messages` returns oldest first. The UI assumes both. Also whether either is paginated.
5. The value set of `mode` and `status` (M2).
6. A PATCH endpoint for takeover, a last-message preview field, and confidence and source on AI messages.
7. Whether `/dashboard` includes only connected channels.
