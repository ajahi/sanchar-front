# Sanchar frontend: flow check and code review

I read every file on the flow (`middleware.ts`, `app/*`, `src/App.tsx`, `src/api.ts` and the components) and ran `npx tsc --noEmit --incremental false`. It reports no errors. Nothing was run against your backend. Findings that depend on it say so.

## Verdict

The pipe works: Instagram login, then the inbox, then the messages of a thread are all real API calls. It does not match your intended flow in three ways.

1. A successful login lands on the inbox, not the dashboard.
2. Most of the "connection" UI is hardcoded mock data that shows green for a tenant who has connected nothing.
3. Any transient error signs the user out.

## Flow as coded

| Step | What happens | Matches intent? |
|---|---|---|
| Click "Continue with Instagram" | `login/page.tsx:188` links to `/api/v1/social-accounts/instagram/login`. `middleware.ts:15` proxies it to FastAPI. | Yes |
| Instagram callback | The backend sets `ns_session`. Errors return as `/login?ig_error=` (`login/page.tsx:22-23`). `middleware.ts:21` keeps the query string. | Yes. The redirect target is backend-side and I can't see it. |
| Landing | A session on `/login` goes to `/` (`middleware.ts:22`). Email login does `assign('/')` (`login/page.tsx:37`). `/` is the inbox. | **No** |
| Dashboard | Reached only through a header link (`Header.tsx:~118`) to `app/dashboard/page.tsx`. It shows counts for 1 day. | Partly |
| Conversations on the left | `SidebarNav` shows a flat list with IG/WA/FB filter chips. | Roughly. It is filtered, not grouped per channel. |
| Click a conversation | `App.tsx:89-96` fetches `/conversations/{id}/messages` and `InboxFeed` renders it. | Yes |

## Findings, ranked

### High: blocks or breaks the flow

**H1. Login lands on the inbox, not the dashboard.**
- Change `middleware.ts:22` and `login/page.tsx:37` to `/dashboard`.
- The Instagram callback redirect in FastAPI must also point to `/dashboard`. This one is backend-side.
- In `PageHeader.tsx:~256`, keep INBOX pointing at `/`.
- Depends on backend: the callback must redirect to your Next origin, not to the API host. If `redirect_uri` is the API's own domain, `ns_session` is set on the wrong domain. Middleware then never sees it and the user bounces back to `/login`. Check the cookie domain in the browser after a real login.

**H2. Any error in `getMyTenant` signs the user out, and a failed logout leaves them stuck.**
- Where: `App.tsx:54-61` and `PageHeader.tsx:22-30` use `.catch(handleSignOut)`.
- `getMyTenant` (`api.ts:23-27`) throws on any non-2xx or network error. A backend restart or a 500 therefore calls `logout()` and redirects.
- If the backend is unreachable, `logout()` rejects at `App.tsx:48`. `window.location.assign` never runs and the rejection is unhandled. The user sits on an empty inbox that still shows "Himalayan Silk" (see H3).
- If logout answers without clearing the cookie, `/login` redirects back to `/` and the two loop.
- Fix: make `getMyTenant` throw a typed error on 401 only. Sign out on that alone. Show a retry banner otherwise. Wrap `logout()` in try/finally so the redirect always runs.

**H3. The UI shows a fake tenant before the real one loads, and Save overwrites the real name.**
- `App.tsx:25` starts `businessName` as "Himalayan Silk & Handicrafts (काठमाडौँ)".
- `MetaSettingsModal.tsx:61` copies that into `bName` once. The modal is always mounted, so it never re-syncs when `getMyTenant` sets the real name.
- "Save Configuration" (`:114`) then writes the mock name over the real one. It is local state only, so nothing is saved to the backend either.
- Fix: start `businessName` as `''`. Sync `bName` in a `useEffect` on `[businessName, isOpen]`. Either persist the name through an endpoint or remove the field.

**H4. Channels shows connections that don't exist, and there is no way to connect Instagram or Facebook from it.**
- Hardcoded green states:
  - Facebook "LINKED & ACTIVE" (`MetaSettingsModal.tsx:187`).
  - Instagram "VERIFIED" (`:215`).
  - Both read `initialMetaStatus` in `mockData.ts:229`.
  - The RightInspector "ACTIVE CHANNELS" stamp and "Meta Webhooks 200 OK" (`RightInspector.tsx:185-211`).
- "PING WEBHOOKS" is a `setTimeout` that prints "HTTP 200 OK — Inbound Webhooks Verified" (`MetaSettingsModal.tsx:107-111`).
- The callback URL and verify token shown (`:401`, `:62`) are fake (`socialsync.np`).
- Only the WhatsApp card is real, through `getWhatsAppAccounts`.
- There is no Facebook connect path anywhere. Instagram is connectable only from `/login`.
- Fix:
  - Drive the Instagram card from `getInstagramProfiles()` (`api.ts:149`).
  - Show "Not connected" plus a connect link (`INSTAGRAM_LOGIN_URL`) when the list is empty.
  - Hide Facebook until a backend endpoint exists.
  - Delete the fake ping, URL and token, or fetch the real ones.
  - Delete the stamp, or derive it from real account lists.

**H5. Human takeover does not persist.**
- `handleToggleTakeover` (`App.tsx:122-139`) changes local state only.
- The 5-second poll (`:73-75`) spreads `fresh` over each thread. The server's `mode` overwrites `status`, so the toggle reverts within 5 seconds. The button implies AI replies are paused, which is not true.
- Fix: add a backend `PATCH /conversations/{id}` for `mode` and call it. Until it exists, hide the button.
- Depends on backend: I can't see whether one exists.

### Medium: real defects

**M1. Dashboard is thin and misleading for a new tenant** (`app/dashboard/page.tsx`).
- `getDashboard()` is called once with `days=1` (`api.ts:129`). There is no range selector or refresh.
- `Counts` always lists WhatsApp, Facebook and Instagram (`:5-9`, `:16-24`). An Instagram-only tenant sees zeros for two channels and no "connect WhatsApp" prompt.
- If the backend omits a key, the cell renders `undefined`. Default with `?? 0`.
- The header badge is the sum of handovers over the window (`:~40`). The inbox badge counts threads currently `NEEDS_HUMAN` (`App.tsx:103`). Same label, different numbers.
- There is no metric for the connected Instagram account (followers, media). `ProfileModal.tsx` already has these.
- "All metrics" depends on what `/dashboard` returns.

**M2. Sidebar previews and confidence are wrong for almost every thread.**
- `SidebarNav.tsx:151` reads `thread.messages`, which are loaded only for the open thread (`App.tsx:89`). Every other thread shows "No messages yet".
- `:208` prints `CONF: 0.00` on every real thread, because `confidenceScore` is never set from the API.
- Fix: have the list endpoint return `last_message_text`. Hide `CONF` when the value is undefined.

**M3. Sending a reply loses the text on failure.**
- `InboxFeed.tsx:99` clears the input before the send resolves. On failure `App.tsx:155` shows `alert()` and the typed text is gone.
- Fix: clear the input only on success, disable the button while sending, and show an inline error.
- `handleKeyDown` (`:102-106`) sends on Enter even during IME composition. Nepali Devanagari input commits with Enter, so it can send half-typed text. Add `if (e.nativeEvent.isComposing) return;`.

**M4. Message pane has no scroll-to-bottom and no empty or loading state.**
- A grep for `scroll` in `src/` finds nothing. New messages appear below the fold.
- Fetch errors are `console.error` only (`App.tsx:95`), so a failed load shows a blank pane.
- Timestamps are `HH:MM` only (`api.ts:80-81`), so a thread spanning days is ambiguous.
- Threads are shown in server order. Sort by `lastMessageAt`.

**M5. The poll ignores auth loss and runs on hidden tabs.**
- `App.tsx:67-85` polls every 5s and swallows errors. If the cookie expires, the user sees a frozen list and is never sent to `/login`.
- Fix: stop or redirect on 401, and skip polling when `document.hidden`.

**M6. Message labels are hardcoded and inaccurate.**
- `api.ts:85` maps `system` and `agent` senders to `human`.
- `InboxFeed.tsx:359` labels those "Human Operator (Merchant)". `:370` adds "OPERATOR OVERRIDE SENT VIA GRAPH API" even for messages that were not sent.
- `:433` says "Meta Customer Service Window: Active • Encryption: E2E Verified". Both are static and unverified.
- `:163` shows "Meta 24h Window: Active", but only when `customerCity` exists, which the API never sets.
- Compute the 24h window from the last customer message, or remove the claim.

**M7. Simulator, RAG sandbox and AI draft are mock or dead code on the live inbox.**
- All call `askAi` to `/api/v1/ai/reply`, which `api.ts:41` says returns 404. Callers: `App.tsx:211`, `:291`, `InboxFeed.tsx:114`, `RAGSandboxModal.tsx:37`.
- "+ INBOUND" and "SIMULATE CUSTOMER" add fake threads and messages, and the next poll wipes them.
- The AI DRAFT failure path inserts a hardcoded Nepglish apology into the reply box (`InboxFeed.tsx:120`). It looks like a real draft.
- Catalog and FAQ (`mockData.ts`) are demo data. Token usage 412 and latency 120 ms in the footer are constants.
- Hide all of these behind `NODE_ENV !== 'production'` or a flag.

**M8. `middleware.ts` no longer excludes static files.**
- The matcher (`:27`) lacks the `.*\\..*` exclusion that `middleware.ts.bak` had.
- A logged-out visitor requesting `/robots.txt`, `/sitemap.xml`, `/sanchar-mailbox.svg` or an og image is redirected to `/login`. That breaks SEO assets.
- Restore `.*\\..*` in the negative lookahead.

**M9. Webhook path handling depends on infrastructure outside this repo.**
- `middleware.ts:11` returns `NextResponse.next()` for `/api/v1/webhooks/*`. Next has no such route, so the request 404s.
- `docker-compose.yml` publishes only `web:3000` and has no nginx. If Meta's callback URL points at port 3000 (ngrok in testing, or a deploy without the proxy), verification fails with a 404. Point Meta at the FastAPI host.
- The stated reason (Next breaks the HMAC) is not verified here, so treat it as a claim.

### Low: cleanup and SEO

- **Public mock API.** `app/api/meta/*` is excluded from middleware by the `api` prefix (`middleware.ts:27`).
  - `webhook` (POST) and `webhook-logs` (GET) are public and unauthenticated. They keep 50 arbitrary payloads in memory, and anyone can read them.
  - `test-connection` always reports success.
  - Delete the folder. `app/api/health/route.ts` names "SocialSync" and checks `GEMINI_API_KEY`. Reduce it to `{status:'ok'}` (Docker healthcheck) or delete it.
- **Junk files.**
  - `app/api/amit/page.tsx` publishes a route `/api/amit` that renders `null`.
  - `middleware.ts.bak` and `tsconfig.tsbuildinfo` are tracked.
  - `conversation_example.json` is tracked and holds real Instagram usernames and IDs. Sanitise or untrack it.
  - Dead prop `metaStatus` is still passed to `Header` (unused in `Header.tsx`).
  - A dead "LOGIN / SIGN UP" button in `Header.tsx:187` has no handler.
- **Old branding.** "SocialSync" remains in `InboxFeed.tsx:316`, `Footer.tsx`, `InventoryModal.tsx:284` and the health route. "Gemini" appears in the AI DRAFT tooltip (`InboxFeed.tsx:415`).
- **Meta app review.** On the login page, "terms of service" and "privacy policy" are plain `<span>`s (`login/page.tsx:246,248`). Meta requires a real privacy-policy URL, and a data-deletion URL for Instagram and Facebook login. Make them `<Link>`s to real pages.
- **Login copy.**
  - The email form has no sign-up or reset path. Only Instagram creates a workspace (`login/page.tsx:~262`).
  - The login page carries decorative print-shop copy such as "ESTD. 1932" and "PRICE 50 PAISA". Trim it for reviewers.
  - The whole page has `select-none`. Drop it.
- **SEO.**
  - Only `/login` is indexable: `/` is `ssr:false` and gated, so crawlers get a redirect. This is fine for now.
  - When you want SEO, make `/` a public landing page and move the inbox to `/inbox`. Add `robots.txt`, a sitemap, `metadataBase`, an og image and a per-page `title` in `layout.tsx`. Add `robots: noindex` on `/dashboard` and `/inbox`.
  - The `BACKEND_URL` fallback `http://localhost:8000` (`middleware.ts:3`) hides a missing env var in production. Fail loudly instead.

## Suggested order

1. H1 and H2 first: the landing page, then sign-out only on 401.
2. H3 and H4: remove the fake identity and fake statuses.
3. H5, M2 and M3: takeover persistence, sidebar previews, and sending without losing text.
4. M8 and M9 before any SEO or Meta review work.
5. Everything else is cleanup.

## Assumptions

- "Dashboard" means `/dashboard`. "Conversations per social media" is satisfied by a filterable list.
- Backend behaviour is unverified: the callback redirect and cookie domain, the `/logout` behaviour when unauthenticated, the presence of a `mode` PATCH, and the shape of `/dashboard` and `/conversations`.
