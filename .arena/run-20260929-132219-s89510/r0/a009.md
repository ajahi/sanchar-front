# Sanchar frontend: review and flow check (Instagram login -> dashboard -> conversations)

Scope: every file in the task's key-file list, plus `MetaSettingsModal`, `InboxFeed`, `RightInspector`, `Footer`, `ProfileModal`, `InventoryModal`, `RAGSandboxModal`, `InboundSimulatorModal`, `types.ts` and `app/api/**`. I ran `npx tsc --noEmit --incremental false` and it exits clean. Nothing was modified and I did not run the app. I did not open `.env` or `.env.bak`. The backend source is not available. Findings that depend on it are marked **[backend]** and collected in section 3 with a command to settle each one.

## 1. Verdict

The plumbing is sound. The `/api/v1` rewrite, the `ns_session` cookie gate, the Instagram button and the read-only inbox (list, open, read, send) are wired to real endpoints. The flow you described breaks in four places:

1. **Login does not end on the dashboard.** Both frontend paths end on the inbox (`/`). Whether the Instagram path is different depends on a backend redirect I cannot see.
2. **The UI shows another merchant's data as if it were the tenant's.** After a real Instagram login, the Channels modal says `@himalayan_silk_np` is "VERIFIED" and a Facebook page is "LINKED & ACTIVE". These are hard-coded.
3. **Every real AI message shows `CONFIDENCE: 0.00` and an empty `SOURCE:`.**
4. **The operator controls can hurt you.** "Take over" does nothing server-side. Canned replies and the AI-draft fallback paste fake coupon and tracking text into a box that sends to real Instagram users.

**B3. Real AI messages render `CONFIDENCE: 0.00` and `SOURCE:` with nothing after it.** `InboxFeed.tsx:307-334`. `MessageDto` (`api.ts:70-78`) carries no confidence or source, so both are `undefined`. `(conf ?? 0).toFixed(2)` prints `0.00` in a green badge on every auto-reply, which is your core product path. **B4. "Take over as human" does not take over.** `App.tsx:122-139` only edits React state. The 5-second poll rebuilds every thread from `mode` (`api.ts:102`), so the button reverts within 5 s. Meanwhile the banner says "Auto-pilot suspended" (`InboxFeed.tsx:435`), and the AI keeps replying to the customer. This misleads a merchant who believes they have paused the bot.

- Needs a backend endpoint **[backend]**, for example `PATCH /api/v1/conversations/{id}` with `{mode:'human'|'ai'}`. I found no such call in `api.ts`.
- Until it exists, disable both buttons (`InboxFeed.tsx:177-194`).
- Once it exists: update optimistically, call the endpoint, and roll back on error.

**B5. Operator send box can send fake or partial content to real customers.** `sendReply` is real (`api.ts:191`), so these matter.

- `InboxFeed.tsx:126-131`: four one-click canned replies contain invented facts (`Coupon code: VINTAGE10`, `courier.np/track/SS98234`, a promised "10% discount approve bhayo"). One click fills the box and Send transmits it.
- `InboxFeed.tsx:118-121`: `/api/v1/ai/reply` returns 404 today (`api.ts:41`), so AI DRAFT always lands in the catch. The catch **writes an apology paragraph into the message box** as if it were a draft. Replace it with an inline error.
- `InboxFeed.tsx:96-100` and `App.tsx:142-158`: `handleSend` clears the input before the request finishes. A failed send (for example Instagram's 24-hour window, or a 401) loses the typed text and pops `alert()` (`App.tsx:155`). There is also no in-flight guard, so Enter twice sends twice. Await `onSendMessage`, clear only on success, and disable Send while pending.
- `InboxFeed.tsx:102-106`: Enter sends even during IME composition. Devanagari and Romanized-Nepali input methods use Enter to commit a candidate, so this can send half-typed text. Use `if (e.key === 'Enter' && !e.nativeEvent.isComposing)`.

### High

**H1. Any `/tenants/me` failure logs the user out, and a failed logout leaves them stuck.** `api.ts:23-27` throws "Not authenticated" for any non-2xx, including 500, 502 and a backend restart. `App.tsx:61` and `PageHeader.tsx:30` both treat that as a dead session, call `logout()` and redirect to `/login`. In development, restarting FastAPI logs you out. If `logout()` itself rejects (backend down, so the fetch throws), `handleSignOut` throws with no catch. The user stays on a page whose header shows a dead "LOGIN / SIGN UP" button. Fix in one place:

```ts
// api.ts: one wrapper for every call
async function api(url: string, init?: RequestInit) {
  const res = await fetch(url, init);
  if (res.status === 401) {
    await fetch('/api/v1/auth/logout', { method: 'POST' }).catch(() => {});
    window.location.assign('/login');
    throw new Error('Session expired');
  }
  return res;
}
```

Route every `fetch` in `api.ts` through it. The rest is then simple:
- `getMyTenant` throws a plain error for non-401.
- The `.catch(handleSignOut)` at `App.tsx:61` and `PageHeader.tsx:30` becomes "show an inline error".
- The 5-second poll (`App.tsx:67-85`) and the dashboard fetch (`dashboard/page.tsx:34`) pick up 401 handling automatically. Today they only `console.error` or print a raw message (`dashboard/page.tsx:44`).

**H2. Header shows a fake tenant and a dead login button during load.** `App.tsx:25` initializes `businessName` to `'Himalayan Silk & Handicrafts (काठमाडौँ)'`. Until `getMyTenant` returns, the header brand line is that string, and `currentUser` is `null`, so `Header.tsx:185-192` renders "LOGIN / SIGN UP" with `onClick={undefined}`. Initialize to `''`. In `Header`, render nothing (or a skeleton) when `currentUser` is null, and delete `onOpenAuthPage`. Also `Header.tsx:165` shows initials `'NP'` for every user, because nothing sets `avatarInitials`. Derive them from `ownerName`.

**H3. "Save Configuration" overwrites the real business name with the mock one.** `MetaSettingsModal.tsx:61` does `useState(businessName)`. The modal is mounted from the first render (`App.tsx:425`), before the tenant loads, so `bName` is frozen at the mock default. `:114-117` then calls `onUpdateBusinessName(bName)`. Open Channels, press Save without typing, and the header changes to "Himalayan Silk…". The save is also local-only. Remove the merchant-name and language form, or wire it to a backend call, and add a `useEffect` that resets `bName` when `businessName` changes.

**H4. Meta webhooks 404 if the tunnel points at Next.** `middleware.ts:11-13` returns `NextResponse.next()` for `/api/v1/webhooks/`. No Next route exists there, so Next answers 404. The comment says nginx sends these straight to FastAPI. That is true in production, but in dev, `next dev` on :3000 behind ngrok has no nginx. Meta's verification GET and every Instagram DM would 404 and the inbox would stay empty. Point the dev tunnel's `/api/v1/webhooks/*` at FastAPI :8000 directly, or add a dev-only proxy. Confirm the production nginx rule before app review.

**H5. Conversation list is flat, and rows lack what an inbox needs.** `SidebarNav.tsx:150-208`:
- **Not per social media.** Chips filter (`:72-115`) but there is no grouping or per-channel counts. `{threads.length} ACTIVE` at `:66` counts every thread.
- **Preview.** `lastMsg` comes from `thread.messages`, which is filled only for the open thread (`App.tsx:88-96`). Every other row says "No messages yet" (`:189-191`), including rows that have messages. Return a `last_message` preview from `/conversations` **[backend]**.
- **Ordering.** No client sort by `lastMessageAt`, so order is whatever the backend sends **[backend]**.
- **No date.** `fmtTime` (`api.ts:80-81`) shows only HH:MM, so a message from last week and one from today look the same.
- **Unread.** `unreadCount` is never populated.
- **Keyboard.** Rows are `div onClick` (`:155-159`) with no `role`, `tabIndex` or key handler, so conversations cannot be opened from the keyboard. Use `<button>`.

Cheap improvement: `const byChannel = Object.groupBy(threads, t => t.channel)` with a heading and count per group.

**H6. Dashboard is thin and cannot show an empty or partial account.** `dashboard/page.tsx`:
- `getDashboard()` is called once with `days=1` (`:34`; `api.ts:129`), with no selector or refresh. It shows three per-channel count tables and a top-queries list.
- `Counts` iterates all three channels (`:19-24`). A tenant who just logged in with Instagram sees WhatsApp 0 and Facebook 0, and no prompt to connect them. Use `getInstagramProfiles()` and `getWhatsAppAccounts()` (already in `api.ts`) with `Promise.allSettled`, and show only connected channels plus a "Connect WhatsApp" link to Channels.
- `:41`: `Object.values(data.handover)` throws if the backend omits `handover`. A missing channel key would render a blank cell, not the word "undefined".
- The INBOX badge on the dashboard header is the sum of `handover` over the window. On the inbox the same badge counts threads currently in `NEEDS_HUMAN` (`App.tsx:103`). Same label, two meanings.
- Add a `days` selector (1, 7, 30) and `role="status"` states.

## 3. Backend-dependent checks (run these, they settle the open questions)

Start the stack (`npm run dev`, FastAPI on :8000) and use a real logged-in cookie value in `$C`.

1. **Where does the Instagram callback send the user, and to which host?**
   `curl -si "http://localhost:3000/api/v1/social-accounts/instagram/login" | grep -i '^location'`
   Expect a redirect to `instagram.com/oauth/authorize` with a `redirect_uri`. That `redirect_uri` must be the **public frontend origin** (for example `https://app.example.com/api/v1/social-accounts/instagram/callback`), not `http://api:8000`. Because the request arrives via the rewrite, a backend that builds URLs from the request host can leak the internal name. After completing a real login, read the callback response with browser dev tools (Network tab, "Preserve log") and confirm: `Location: /dashboard` (or an absolute public URL, never `api:8000`), and a `Set-Cookie: ns_session=…; HttpOnly; Secure; SameSite=Lax; Path=/`.
2. **Does logout clear a dead cookie?** `curl -si -X POST -b "ns_session=bogus" http://localhost:3000/api/v1/auth/logout`. It must return `Set-Cookie: ns_session=; Max-Age=0` even for an invalid session. Otherwise middleware bounces `/login` to `/` and the app bounces back, which is an endless reload loop (the failure `App.tsx:60` mentions).
3. **Endpoint shapes.**
   `curl -s -b "ns_session=$C" localhost:3000/api/v1/conversations | head -c 600`. Check the list is sorted newest-first and whether `last_message` exists.
   `curl -s -b "ns_session=$C" "localhost:3000/api/v1/dashboard?days=1"`. Check that `whatsapp`, `instagram` and `facebook` keys are always present in all three count objects.
4. **Timestamps carry a zone.** In the `/conversations/{id}/messages` output, `created_at` must end in `Z` or `+00:00`. If not, fix it in the backend (`AwareDatetime` or a serializer).
5. **`PATCH` for mode, `last_message`, `/ai/reply`, Facebook link endpoint, unread counts.** None appear in `api.ts`. Confirm which exist before building the UI for them.
6. **Instagram send limits.** Instagram allows a standard reply only within 24 hours of the customer's last message. Check that the backend returns a readable `detail` string for that error, because the UI shows it verbatim.

## 5. SEO and Meta review readiness

- **What is crawlable today:** only `/login`, which is a client component, so it cannot export `metadata`. It shares the layout-wide title and description (`app/layout.tsx:4-13`). `/` and `/dashboard` are client-only behind the login redirect (`ssr:false` at `app/page.tsx:8`), and that is right for a private app. Add `robots: { index: false, follow: false }` to the app pages and keep them out of any sitemap.

  1. Make `/` a server component with real copy, and move the inbox to `/inbox` (then update `app/page.tsx`, `middleware.ts:19-22`, `PageHeader.tsx:37,40` and `App.tsx:114-119`).

  4. Make sure the matcher exclusion from M1 is in place so crawlers can fetch these.
  5. Replace the five Google Fonts `<link>` tags (`layout.tsx:19-24`) with `next/font` to stop render-blocking third-party CSS.
- **Meta app review:**
  - Real Terms and Privacy pages, and their URLs in the app settings.
  - A data-deletion callback or instructions URL (required for Instagram and Facebook login).
  - Remove the false compliance strings above.
  - The reviewer needs a working path: Instagram login -> dashboard -> conversation -> reply. That is the reason to do B1 to B5 first.
