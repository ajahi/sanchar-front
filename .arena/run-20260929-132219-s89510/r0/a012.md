# Sanchar frontend: review and flow check (Instagram login -> dashboard -> conversations)

## Verdict

The plumbing is sound. The `/api/v1` proxy, the httpOnly session cookie, the Instagram login link, the conversation and message fetching and the send-reply path are all wired and typecheck cleanly. `npx tsc --noEmit --incremental false` reports 0 errors. I ran it with `--incremental false` so it wrote nothing.

The flow as intended does not happen, for three reasons.

1. **Wrong landing page.** Nothing lands the user on the dashboard. Every entry path ends on the inbox (`/`).
2. **Disconnected Instagram account.** Once you are logged in there is no way to connect or refresh an Instagram account. The only Instagram login button is on `/login`, and the middleware bounces logged-in users away from `/login`.
3. **Fake data on screen.** Large parts of the screen show hard-coded demo data as if it were live. This includes "Himalayan Silk" connected-channel cards, a "200 OK" webhook badge, an AI confidence of 0.00 and a name field that saves the wrong business name.

Backend behaviour I could not see is marked **[backend]**. Those items need a check on your side and I do not claim them as bugs.

## Assumptions

- The backend sets `ns_session` on the Instagram callback and then redirects the browser somewhere. That destination is **[backend]**.
- nginx (or similar) sits in front in production and sends `/api/v1/webhooks/*` straight to FastAPI. `middleware.ts:6-7` says so.
- "Dashboard" means `/dashboard` (`app/dashboard/page.tsx`). "Inbox" means `/` (`src/App.tsx`).
- I read every file in scope except `InventoryModal`, `RAGSandboxModal` and `InboundSimulatorModal`. I only checked what they call.

## Findings, ranked

### P0: blocks or misleads the core flow

**P0-1. A logged-in tenant cannot connect or re-connect Instagram.**
- The only Instagram login link is on `/login` (`login/page.tsx:188`).
- `middleware.ts:22` redirects any request to `/login` that carries a session cookie to `/`.
- `ProfileModal.tsx:68` tells the user "Log in with Instagram again to refresh". That is impossible through the UI.
- The Channels modal has cards for Facebook and Instagram but no Connect button for either. Only WhatsApp has a link form (`MetaSettingsModal.tsx:269-343`).
- "Link other channels" in your flow is therefore only half built. WhatsApp is manual (paste two IDs). Instagram works only on first login. Facebook is missing entirely.
- Fix: put an `<a href={INSTAGRAM_LOGIN_URL}>Connect / reconnect Instagram</a>` in `ProfileModal` and in the Instagram card. Nothing in the middleware blocks `/api/v1/...`, so the link works while logged in.
- **[backend]** The login endpoint must also accept an already-authenticated tenant and attach the new account to that tenant, not create a second one.

**P0-2. Hard-coded demo data is shown as live connection status.** The user sees a healthy, connected state for accounts they never connected.
- `App.tsx:31` seeds `metaStatus` from `mockData.ts:229-248`. That is "Himalayan Silk", a fake page ID, `@himalayan_silk_np` and a fake WhatsApp number. `PageHeader.tsx:38` does the same.
- `MetaSettingsModal.tsx:187` prints "LINKED & ACTIVE" for Facebook unconditionally. `:215` prints "VERIFIED" for Instagram. `:194-226` show the mock page and handle. A real Instagram profile endpoint already exists (`api.ts` `getInstagramProfiles`, used by `ProfileModal`) but is not used here.
- `RightInspector.tsx:185-211` shows an "ACTIVE CHANNELS" badge with all three icons and "Meta Webhooks 200 OK". These are static.
- `MetaSettingsModal.tsx:105-112` "PING WEBHOOKS" waits 800 ms in a `setTimeout` and prints "HTTP 200 OK - Inbound Webhooks Verified for Messenger, Instagram, & WhatsApp". It calls nothing.
- `MetaSettingsModal.tsx:401` shows a fake callback URL (`api.socialsync.np/v1/meta/webhook`). `:62` puts a fake-looking verify token, `socialsync_meta_wh_sec_991823`, into the client bundle. If that ever matches a real token, it is leaked to every visitor.
- Fix: delete `initialMetaStatus`. Drive the Instagram card from `getInstagramProfiles()`. Drive the WhatsApp card from `getWhatsAppAccounts()`, which is already real. Render Facebook as "Not available yet". Remove the fake ping and the callback and token block. Show the real webhook URL only if the backend exposes it.

**P0-3. "Save Configuration" overwrites the tenant name with the demo name.**
- `App.tsx:25` initialises `businessName` to `'Himalayan Silk & Handicrafts (काठमाडौँ)'`.
- `MetaSettingsModal.tsx:61` does `useState(businessName)`. The modal is mounted from the start and only returns `null` when closed (`:101`), so `bName` captures that demo string once and never updates after `getMyTenant` returns the real name (`App.tsx:57`).
- Open Channels and the field shows "Himalayan Silk...". Click Save and `handleSave` (`:114-117`) pushes it into the header. The change is not sent to the backend either, so a reload discards it.
- Fix:
```diff
--- a/src/App.tsx
-  const [businessName, setBusinessName] = useState('Himalayan Silk & Handicrafts (काठमाडौँ)');
+  const [businessName, setBusinessName] = useState('');
--- a/src/components/MetaSettingsModal.tsx
   const [bName, setBName] = useState(businessName);
+  useEffect(() => setBName(businessName), [businessName, isOpen]);   // place above the `if (!isOpen) return null`
```
  Either persist the name (**[backend]** needs a `PATCH /tenants/me`) or make the field read-only.

### P1: real bugs or the intended flow diverging

**P1-1. Login lands on the inbox, not the dashboard.** The two frontend places are `middleware.ts:22` and `login/page.tsx:37`. The third, the OAuth callback redirect, is **[backend]**.
- Options:
  - (a) Change the two frontend places to `/dashboard`, and have the backend redirect there. This is the smallest change.
  - (b) Move the inbox to `/inbox` and make the dashboard `/`. Then any backend redirect to `/` already works, but you also edit `PageHeader.tsx:22,24`, `App.tsx:118` and `Header`.
- I recommend (a) for now, because you are still in testing and it touches three lines. It gives up robustness: if the backend redirect is ever set back to `/`, the user silently lands on the inbox again. (b) fixes that, at the cost of a larger refactor. It also frees `/` for the public landing page you want for SEO, so choose (b) when you start the SEO work.
```diff
--- a/middleware.ts
-  if (hasSession && isLogin) return NextResponse.redirect(new URL('/', req.url));
+  if (hasSession && isLogin) return NextResponse.redirect(new URL('/dashboard', req.url));
--- a/app/login/page.tsx
-      window.location.assign('/'); // full load so middleware sees the new cookie
+      window.location.assign('/dashboard'); // full load so middleware sees the new cookie
```

**P1-2. Any error signs the user out, and a backend outage strands them.**
- `getMyTenant` throws `'Not authenticated'` for every non-2xx (`api.ts:25`). `App.tsx:61` and `PageHeader.tsx:30` treat every failure as a dead session and call `logout()`.
- On a transient 500 or 502, for example while the backend restarts, the user is logged out.
- If the backend is fully down, `logout()` (`App.tsx:47-50`) throws before `window.location.assign('/login')`, and the user is stuck on a blank inbox with no message.
- Fix: throw a typed error only on 401 and sign out only for that. Wrap `logout()` in `try/finally`, and show a "backend unreachable" banner for other errors.
```ts
// api.ts
export class AuthError extends Error {}
if (res.status === 401) throw new AuthError('Not authenticated');
if (!res.ok) throw new Error(`Tenant lookup failed (${res.status})`);
// App.tsx / PageHeader.tsx
.catch((e) => { if (e instanceof AuthError) handleSignOut(); else setBanner(e.message); });
// handleSignOut
try { await logout(); } finally { window.location.assign('/login'); }
```
- **[backend]** If `/auth/logout` needs a valid session and does not clear the cookie on 401, the reload loop that `App.tsx:60` warns about can return. Confirm that logout clears the cookie unconditionally.

**P1-3. Static files and SEO files redirect to `/login` for logged-out visitors.**
- The matcher at `middleware.ts:27` no longer excludes paths with a file extension (`middleware.ts.bak` did).
- `robots.txt`, `sitemap.xml`, `/sanchar-mailbox.svg`, Open Graph images and anything else in `public/` therefore get a 307 to `/login`. Crawlers and link-preview bots never see them. The repo also has no `favicon.ico`.
- Fix: `matcher: ['/((?!api|_next|favicon\\.ico|.*\\..*).*)', '/api/v1/:path*']`.

**P1-4. Every non-open conversation card in the left list says "No messages yet".**
- Messages are fetched only for the open thread (`App.tsx:88-96`). The list endpoint returns no last-message text (`api.ts:60-70`, `ConversationDto`).
- `SidebarNav.tsx:151,190` therefore renders `"No messages yet"` for every other card, including conversations that are full.
- Fix: **[backend]** add `last_message_text` and `unread_count` to `GET /conversations`. On the frontend, show nothing rather than a false statement until that exists.

**P1-5. AI messages always show "CONFIDENCE: 0.00" and an empty "SOURCE:".**
- The API maps no confidence or source (`api.ts:84-91`). `InboxFeed.tsx:330` prints `(conf ?? 0).toFixed(2)` and `:333` prints `SOURCE: {source}` with nothing after it.
- The sidebar has the same problem on every card (`SidebarNav.tsx:208`, "CONF: 0.00"), and the "Live Context" panel shows empty intent and source (`RightInspector.tsx`).
- Fix: render each badge only when the value exists (`conf != null && ...`), and hide "CONF" in the sidebar when it is undefined.

**P1-6. "Take over as human" does not stick.**
- `handleToggleTakeover` (`App.tsx:122-139`) changes only local state.
- The 5 s poll (`App.tsx:69-80`) rebuilds every thread from the server `mode` (`api.ts:102`), so the toggle reverts within 5 seconds. The "TAKE OVER" and "RESOLVE" buttons and the "Auto-pilot suspended" label are therefore false.
- Fix: **[backend]** add an endpoint such as `PATCH /conversations/{id}` with `{mode}`. Call it, and only then update the state. Until it exists, hide the buttons.
- Also, `api.ts:102` maps any mode other than `'ai'` to NEEDS_HUMAN, so a resolved or closed status would show as an escalation. `c.status` is ignored.

**P1-7. Two different numbers share the "escalations" badge.**
- On `/dashboard` the header badge is the sum of `handover` counts for the day (`dashboard/page.tsx:41`).
- In the inbox it is the count of threads currently in NEEDS_HUMAN (`App.tsx:103`).
- The same red badge means different things depending on the page. Use one definition, or label the dashboard figure "Handovers (24 h)".

### P2: correctness and clarity

- **No scroll to the newest message.** The messages pane (`InboxFeed.tsx:283`) is a plain `overflow-y-auto` and there is no scroll handling anywhere in `src/`. A long conversation opens at the oldest message, and new messages arrive below the fold. Add a ref, and scroll to the bottom in an effect when `thread.id` or `thread.messages.length` changes. Place the hook above the `if (!thread) return` at `:204`.
- **System messages are labelled as operator messages.** `api.ts:85` maps every non-customer, non-AI sender, including `system`, to `'human'`. `InboxFeed.tsx:370` then stamps them "OPERATOR OVERRIDE SENT VIA GRAPH API". Keep `system` as its own type.
- **Leftover product name in the UI.** `InboxFeed.tsx:316` shows "SocialSync AI (RAG-Enabled)" and `Footer.tsx:26` shows "SOCIALSYNC AI". `InboxFeed.tsx:415` mentions Gemini. Rename these to Sanchar.
- **False claims in the reply bar.** `InboxFeed.tsx:433` says "Meta Customer Service Window: Active . Encryption: E2E Verified". The window is not computed and Instagram DMs are not E2E. A send outside Meta's 24 h window will fail at the `alert()` (`App.tsx:155`). Compute the window from the last customer message, or remove the line.
- **Composer loses text on failure.** `InboxFeed.tsx:99` clears the input before the send finishes, so a failed send (shown only through `alert()`) loses what the user typed. Clear it after success and show an inline error.
- **Dead "LOGIN / SIGN UP" button.** While `currentUser` is still null, `Header.tsx:187` renders a button whose `onOpenAuthPage` is never passed (`App.tsx`, `PageHeader.tsx`). It flashes on every page load and does nothing when clicked. Render a skeleton instead.
- **Error handling that prints `[object Object]`.** `api.ts:10` (`login`) and `sendReply` pass FastAPI's `detail` straight into `new Error()`. On a 422 that is an array. `linkWhatsApp` already handles it (`typeof detail === 'string'`), so copy that.
- **Simulator and sandbox write into the real inbox.**
  - `+ INBOUND` (`Header.tsx:150`), "SIMULATE CUSTOMER" (`InboxFeed.tsx:205`), "AI DRAFT" and RAG Sandbox all call `/api/v1/ai/reply`, which `api.ts:46` says 404s until "M4".
  - Simulated threads and messages exist only in memory and disappear at the next 5 s poll (`App.tsx:73-75`). The "AI draft" failure path fills the composer with a canned Nepglish apology (`InboxFeed.tsx:117`), which the operator could send to a customer.
  - Hide all of these behind a dev flag such as `NEXT_PUBLIC_ENABLE_SIMULATOR`.
- **Fake stats.** `App.tsx:99-100` and `Footer.tsx` show `TOKEN_USAGE 412/10000`, latency `120 ms` and `SYSTEM ID: SS-AI-KATHMANDU-01`. Remove them or wire them to real data.
- **Catalog and FAQs are local-only.** Adding a product in the Catalog modal disappears on reload, and a new tenant sees "Himalayan Silk" products (`RightInspector.tsx`, `mockData.ts:1-40`). The header tabs "CATALOG" and "RAG SANDBOX" advertise features that do not persist anything.

### P3: security and repo hygiene

- **Unauthenticated Next API routes.** `middleware.ts:27` excludes everything under `api`, so `app/api/meta/*` is reachable without a session.
  - `webhook-logs` (GET) returns whatever was POSTed to `webhook` (POST). `test-connection` always returns "CONNECTED".
  - `webhook` does no signature check. It is dead code because the real webhook goes to FastAPI.
  - Delete `app/api/meta/`. Delete `app/api/amit/page.tsx` (it renders `null`). Change `app/api/health/route.ts`, which still says "SocialSync AI" and reports `hasGeminiKey`, into a plain `{status:'ok'}`.
- **Webhooks return 404 if nginx is not in front.** `middleware.ts:11-13` returns `NextResponse.next()` for `/api/v1/webhooks/*`, and Next has no such route. `docker-compose.yml` starts only the web container. This is fine in production behind nginx, but in local or staging setups without it Meta's callbacks 404. **[backend/infra]** Confirm the routing in each environment.
- **Real Instagram IDs are committed.** `conversation_example.json` contains real usernames and account IDs. `middleware.ts.bak`, `tsconfig.tsbuildinfo` and `.env.bak` are also in the folder. The first two are tracked in git. Remove them and check that `.env.bak` holds no secrets.
- **Docker.** `.dockerignore` excludes `.env*`, and `docker-compose.yml` supplies it at runtime (`env_file`). That is right. If `.env` is missing, `BACKEND_URL` silently falls back to `http://localhost:8000` (`middleware.ts:3`), which is wrong inside a container. Fail loudly instead.
- **OAuth details that need checking. [backend]**
  - The OAuth `state` cookie must be `SameSite=Lax`, because the callback is a cross-site top-level navigation.
  - The `redirect_uri` sent to Instagram must come from a configured public URL, not the request Host. The rewrite sends the backend its own hostname.

## Dashboard

- Only four blocks are shown: new messages, top queries, messages handled and handover, all as per-channel counts for a fixed 24 h (`getDashboard(days = 1)`, `api.ts:129`; the caller passes no argument, `dashboard/page.tsx:34`). There is no date selector, no refresh, no charts and no trend.
- "All the metrics available" is not met. The Instagram profile data (followers, following, posts) exists in `ProfileModal` but never appears on the dashboard.
- A tenant who just logged in with Instagram sees WhatsApp and Facebook rows of zeros (`dashboard/page.tsx:15-20`), with no "connect" prompt. Show only connected channels, and add an empty state that points to Channels.
- The response is used unchecked: `counts[ch]` (`dashboard/page.tsx:22`) prints `undefined` if the backend omits a channel key. Default it with `?? 0`. **[backend]** Confirm that the backend always returns all three keys.
- The page has two `<h1>` elements, one in `Header.tsx` and one in `dashboard/page.tsx:49`. Make the header brand a `<p>` or `<div>`.

## SEO readiness (when you get there)

- Only `/login` can ever be indexed, and it is `'use client'`, so it cannot export its own `metadata`. Every route shares the title in `app/layout.tsx:8-13`. Add a server `layout.tsx` (or move the client form into a child component) so `/login` gets its own title, description and canonical URL.
- The layout has no `metadataBase`, no `robots` metadata and no Open Graph image, although `twitter: summary_large_image` is set (`layout.tsx:12`).
- Fonts load with a render-blocking `<link>` to Google Fonts (`layout.tsx:19-24`). Move to `next/font`.
- `/` is client-only (`app/page.tsx:8`, `ssr: false`), so it renders only a spinner, and the middleware never lets a crawler reach it anyway. A public landing page needs `/` freed, which is another reason to choose option (b) in P1-1 later.
- Terms of service and privacy policy on the login page are `<span>`s (`login/page.tsx:246-248`). Meta app review needs real URLs for both, plus a data-deletion URL for Instagram and Facebook login.
- Accessibility basics on the one public page: the two `<label>`s (`login/page.tsx:212,226`) have no `htmlFor`, and the inputs have no `autocomplete`. The thread cards are `<div onClick>` (`SidebarNav.tsx:158`), so they cannot be reached from the keyboard. Use `<button>`.
