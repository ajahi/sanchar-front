# Sanchar frontend: flow check and code review (Instagram login, dashboard, conversations)

I read every file in the flow and ran `npx tsc --noEmit --incremental false` (exit 0). I passed `--incremental false` because `tsconfig.json:15` sets `incremental: true`, and a plain `tsc --noEmit` would rewrite the tracked `tsconfig.tsbuildinfo`. I did not run the app or the backend. Anything that depends on FastAPI is marked **[backend]**.

## How to read this

I traced the tenant's journey one hop at a time, the way you would trace a packet across a network. For each hop I wrote down the state it should hand to the next hop, then checked the code for it. The first failing hop is what blocks the flow. Everything after it is a separate defect.

| # | Hop | Should hand over | Result | Evidence |
|---|-----|------------------|--------|----------|
| 1 | Anonymous visit to `/` | Sees the login page | PASS (307 to `/login`) | `middleware.ts:21` |
| 2 | Click "Continue with Instagram" | Browser goes to FastAPI OAuth via rewrite | PASS | `login/page.tsx:188`, `middleware.ts:15-17` |
| 3 | Instagram callback | Session cookie set, then redirect to the dashboard | UNVERIFIED **[backend]**, and the frontend cannot put the user there itself | `middleware.ts:22` |
| 4 | Login failure comes back | User sees `ig_error` | PASS for anonymous users, **FAIL** for anyone holding a cookie | `middleware.ts:22` |
| 5 | Land on the dashboard | All metrics | **FAIL.** Lands on `/` (the inbox), and the dashboard is thin | `login/page.tsx:37`, `middleware.ts:22` |
| 6 | Conversations listed per channel on the left | Real threads with previews | PARTIAL. Filter tabs, not grouping; previews empty | `SidebarNav.tsx:151,190` |
| 7 | Click a conversation | Its messages | PASS for fetching, **FAIL** for display (no scroll-to-bottom, fake metadata) | `App.tsx:88-96`, `InboxFeed.tsx:284` |
| 8 | Reply or take over | Message sent, mode saved | Send PASS. Takeover **FAIL** (local only) | `App.tsx:122-139` |
| 9 | Link the other channels | Connect Instagram, Facebook, WhatsApp | WhatsApp only | `MetaSettingsModal.tsx:175-229` |

## Checks to run after fixing

Static checks, derived from the code (not executed):

1. `curl -sI localhost:3000/` returns 307 with `Location: /login`.
2. `curl -sI -H 'Cookie: ns_session=x' 'localhost:3000/login?ig_error=access_denied'` should return 200. Today it returns 307 to `/`, so the error is lost (`middleware.ts:22`).
3. `curl -sI localhost:3000/robots.txt` and `/sanchar-mailbox.svg` should return 200 when logged out. Today both return 307 to `/login` (`middleware.ts:27`).
4. With the backend stopped and a cookie set, opening `/` must settle on a visible error page. Today it loops (finding 2).
5. In the browser, type text in thread A without sending, click thread B, and the input must be empty. Today it is not (finding 3).
6. Log in with Instagram and confirm the URL is `/dashboard`.
7. Take over a thread, wait 6 seconds, and it must still be taken over. Today the 5-second poll undoes it (finding 6).

## Findings, ranked

### P0: blocks the intended flow or can lock the user out

**1. Login does not land on the dashboard, and the frontend has three places that send it to the inbox.**
- `login/page.tsx:37` does `location.assign('/')`.
- `middleware.ts:22` redirects a logged-in `/login` visit to `/`.
- `app/page.tsx` renders the inbox.
- The Instagram callback redirect is set by FastAPI **[backend]**. It must send the user to `/dashboard` as well.

Change:
```diff
- window.location.assign('/');
+ window.location.assign('/dashboard');
```
```diff
- if (hasSession && isLogin) return NextResponse.redirect(new URL('/', req.url));
+ if (hasSession && isLogin && !req.nextUrl.searchParams.has('ig_error'))
+   return NextResponse.redirect(new URL('/dashboard', req.url));
```
The `ig_error` condition also fixes finding 4.

**2. A backend hiccup causes an infinite reload loop between `/login` and `/`.**
- `getMyTenant()` throws on any non-OK status (`api.ts:25`).
- `App.tsx:61` and `PageHeader.tsx:249` treat every failure as "session dead" and call `handleSignOut`.
- `handleSignOut` (`App.tsx:47-50`) calls `logout()`. `fetch` only throws on a network error, so a 502 or 503 from the proxied backend is swallowed.
- The page then goes to `/login`, but the httpOnly cookie is still there, so `middleware.ts:22` bounces it back to `/`.
- `/` runs `getMyTenant()` again, and the cycle repeats. A network-level error is worse: `await logout()` throws, so the user is stuck on a blank inbox with the mock business name.

Sign out only on 401, and never let logout block the redirect:
```ts
// api.ts
export class AuthError extends Error {}
export async function getMyTenant(): Promise<Tenant> {
  const res = await fetch('/api/v1/tenants/me');
  if (res.status === 401) throw new AuthError('Not authenticated');
  if (!res.ok) throw new Error(`Could not load your workspace (${res.status})`);
  return res.json();
}
```
```ts
// App.tsx:61 and PageHeader.tsx:249
.catch((e) => (e instanceof AuthError ? handleSignOut() : setLoadError(e.message)));
// handleSignOut: await logout().catch(() => {}); before the assign
```
Then render `loadError` with a Retry button. This assumes `/api/v1/auth/logout` clears `ns_session` **[backend]**. Please confirm that.

### P1: wrong or dangerous behaviour in the conversation flow

**3. A half-typed reply follows you to another customer.**
- `InboxFeed`'s `inputText` state (`InboxFeed.tsx:73`) is not reset when the thread changes, because `App.tsx:389` mounts `<InboxFeed thread={activeThread} …>` without a `key`.
- Type to customer A, click customer B, press Enter, and the text goes to B.
- The same applies to `showSimulateDropdown`.
- Fix: `<InboxFeed key={activeThread?.id ?? 'none'} …/>`.

**4. The Instagram error message is lost for anyone who already has a cookie.** See the second diff in finding 1. Before the fix, a tenant who is already logged in and fails to re-link Instagram is silently dropped on `/`.

**5. "Save Configuration" overwrites the real business name with a mock name.**
- `MetaSettingsModal.tsx:61` sets `useState(businessName)` once.
- The component stays mounted (it returns `null` at line 101), so the state is captured on first render.
- `App.tsx:25` starts `businessName` as `'Himalayan Silk & Handicrafts (काठमाडौँ)'`, before `getMyTenant` returns.
- Opening Channels shows the mock name in the input, and Save (`:114-117`) writes it into the header.
- Nothing is sent to the backend either way.
- Fix: sync on open with `useEffect(() => { if (isOpen) setBName(businessName) }, [isOpen, businessName])`. Better, drop the field until a PATCH endpoint exists.

**6. Human takeover is cosmetic and reverts within 5 seconds.**
- `handleToggleTakeover` (`App.tsx:122-139`) changes local state only.
- The poll at `App.tsx:80` rebuilds every thread from `mode` (`api.ts:102`).
- It needs a backend call, for example `PATCH /api/v1/conversations/{id}` with `{mode}` **[backend]**. Until then, disable the button.
- Check what the backend does when an agent sends a message while `mode` is still `ai`. If the AI keeps answering, the customer gets two replies **[backend]**.

**7. A failed send loses what the operator typed.**
- `InboxFeed.tsx:96-100`: `handleSend` calls `onSendMessage(...)`, which is async, then runs `setInputText('')` immediately.
- On failure `App.tsx:155` shows `alert(...)` and the text is gone.
- Fix: make `onSendMessage` return a boolean promise, clear the input only on success, and show the error under the input.

**8. Real messages carry fake AI metadata.**
- Every AI bubble shows `CONFIDENCE: 0.00` (`InboxFeed.tsx:330`, from `conf ?? 0`) and `SOURCE: ` followed by nothing (`:333`), because the API DTO has neither field.
- The label reads "SocialSync AI (RAG-Enabled)" (`:316`), which is the old brand.
- `api.ts:85` maps `agent` and `system` to `human`, so system notices display as "Human Operator (Merchant)" with a red "OPERATOR OVERRIDE SENT VIA GRAPH API" badge (`InboxFeed.tsx:359,370`). The badge appears on every historical human message.
- `ai_generated` (`api.ts:76`) is never read.
- Fix:
  - Render the confidence and source chips only when defined.
  - Map `system` to its own centered note.
  - Show the "sent via Graph API" badge only for the message you just sent.

**9. Connection status is fake for Facebook and Instagram.**
- `initialMetaStatus` (`mockData.ts:229-248`) is passed to `MetaSettingsModal` and to the `Header` in `PageHeader.tsx:38`.
- The Facebook card is hard-coded "LINKED & ACTIVE" (`MetaSettingsModal.tsx:186`) and the Instagram card "VERIFIED" (`:214`), with the fake page "Himalayan Silk".
- The Channels modal never uses the real Instagram profile from `getInstagramProfiles`, which is already written (`api.ts:149`).
- `RightInspector.tsx:210` always says "Meta Webhooks 200 OK".
- The "PING WEBHOOKS" button (`MetaSettingsModal.tsx:105-111`) is a `setTimeout` that prints success.
- The callback URL and verify token shown (`:401,62`) are `api.socialsync.np` and `socialsync_meta_wh_sec_991823`. A tenant who copies those into Meta will fail.
- Fix:
  - Drive the Instagram card from `getInstagramProfiles()`.
  - Show Facebook as "Not connected".
  - Delete the fake ping and the fake URL and token.

**10. There is no way to link Instagram or Facebook from inside the app.**
- `INSTAGRAM_LOGIN_URL` is used only on `/login` (grep shows a single use).
- A tenant who signed up with email cannot add Instagram from Channels.
- There is no Facebook path at all.
- WhatsApp linking only appears when the account list is empty (`MetaSettingsModal.tsx:269`), so a second number cannot be added.
- Add a "Connect Instagram" `<a href={INSTAGRAM_LOGIN_URL}>` to the Instagram card, and show the WhatsApp form after the list as well.

### P2: the dashboard and inbox are thinner than the intended flow

**11. The dashboard is not "all the metrics".**
- `dashboard/page.tsx` shows four blocks (new messages, queries, messages handled, handover). The window is fixed by `getDashboard(days = 1)` (`api.ts:129`) with no selector.
- The Instagram profile numbers (followers, following, posts) are fetched in `ProfileModal.tsx` but never appear on the dashboard.
- It always lists WhatsApp, Facebook and Instagram, so a new Instagram-only tenant sees zero rows for two channels with no "connect" prompt.
- `Object.values(data.handover)` (`:41`) throws if the backend omits the field, and the page has no error boundary.
- `key={q.text}` (`:62`) collides on duplicate queries.
- The header badge on this page is the sum of handovers over the window (`:41`). On the inbox it is the count of threads currently in `NEEDS_HUMAN` (`App.tsx:103`). Same badge, two meanings.
- Fix: add a 1/7/30-day selector, show the connected channels' rows first, add the Instagram profile card, and add a first-run card that links to Channels.

**12. The message pane does not scroll to the newest message.**
- `InboxFeed.tsx:284` has no ref or `scrollIntoView` (grep finds only the `useRef` for the image dialog).
- Opening a long thread shows the oldest messages, and a new customer message arrives out of sight.

**13. Sidebar previews are empty for every thread you have not opened.**
- `SidebarNav.tsx:151` reads `thread.messages`, which is `[]` until clicked (`api.ts:103`).
- Add a `last_message` preview to the `/conversations` response **[backend]**.
- The CONF badge (`:208`) also shows `0.00` for every real thread. Hide it when `confidenceScore` is undefined.
- "N ACTIVE" (`:67`) counts all threads, not active ones.
- The left column is one mixed list with a filter, not a list per channel. That may be enough, but say so if you meant grouped sections.
- If the active thread is filtered out of the list, the centre pane still shows it.

**14. Polling and session handling in the inbox.**
- `App.tsx:78` swallows every poll error with `console.error`. If the session expires mid-day the user sees a frozen inbox and is never sent to `/login`.
- The poll keeps running in background tabs, and has no protection against overlapping requests. Pause on `document.hidden`, and treat a 401 as sign-out (reuse `AuthError`).
- Neither `listConversations` nor `listMessages` paginates **[backend]**.

**15. Smaller UI defects.**
- Enter sends while a Devanagari IME is composing (`InboxFeed.tsx:103`). Add `&& !e.nativeEvent.isComposing`.
- `Footer.tsx:240` prints `(latencyMs / 100).toFixed(1)s`, so 120 ms shows as "1.2s". Token usage is fake too (`App.tsx:99-100`).
- The header shows a "LOGIN / SIGN UP" button that does nothing while the tenant loads (`Header.tsx:449-456`, `onOpenAuthPage` is never passed).
- The avatar initials are hard-coded "NP" (`Header.tsx:429`).
- "Meta 24h Window: Active" (`InboxFeed.tsx:163`) and "E2E Verified" (`:435`) are static text. The window is not checked in the UI, so sends after the window fail through the `alert` in finding 7.

### Mock and dead code that misleads

- **Simulator and sandbox:** `+ INBOUND` (`Header.tsx:407`), `SIMULATE CUSTOMER` (`InboxFeed.tsx:200`), `RAGSandboxModal`, and "AI DRAFT" (`:108-124`) all call `/api/v1/ai/reply`. `api.ts:41` says this 404s until M4. Simulated threads use ids like `thread-…`, so the next poll deletes them, and a click on one fires `listMessages` with a bogus id. Hide these behind `process.env.NEXT_PUBLIC_DEV_TOOLS`.
- **Catalog and policy in the right panel:** `RightInspector.tsx:93-119` shows mock prices, delivery fees and a discount code (VINTAGE5) that no backend knows about. The canned replies (`InboxFeed.tsx:126-131`) invent a discount code and a tracking link, and one click puts them in the customer's message box.
- **Leftover routes:**
  - `app/api/meta/*`: `webhook` has no signature check, and `test-connection` always returns success. Both are reachable without a session because the matcher skips `/api`. Meta calls FastAPI, so delete the folder.
  - `app/api/health/route.ts` says "SocialSync" and reports a Gemini key.
  - `app/api/amit/page.tsx` renders null.
  - `middleware.ts.bak` and the tracked `tsconfig.tsbuildinfo` should go.
- **Brand leftovers:** SocialSync appears in `Footer.tsx`, `MetaSettingsModal.tsx`, `InventoryModal.tsx`, `InboxFeed.tsx` and `app/login/page.tsx`.

### SEO and Meta app review

- **Static files behind login:** the current matcher `'/((?!api|_next|favicon.ico).*)'` (`middleware.ts:27`) dropped the `.*\\..*` exclusion that `middleware.ts.bak:24` had. Every path with a file extension is now redirected to `/login` for a logged-out visitor, including `robots.txt`, `sitemap.xml`, and og images. Nothing in the UI uses `public/` today, so nothing looks broken yet. Restore `|.*\\..*` in the exclusion.
- **`/` is the inbox, gated by login, and rendered with `ssr:false`:** crawlers get a redirect to `/login`, which is the only indexable page. When SEO matters, move the inbox to `/inbox` and put a public landing page at `/`, with the redirect logic in `middleware.ts` adjusted to match.
- **Missing metadata:**
  - `layout.tsx` has no `metadataBase` or og image (twitter is `summary_large_image` with no image).
  - There is no `robots.ts` or `sitemap.ts`.
  - Authenticated pages need `robots: { index: false }`.
  - The five Google Fonts in `<head>` (`layout.tsx:19-24`) should use `next/font`.
- **Compliance:** the login page's terms and privacy text are `<span>`s (`login/page.tsx:246,248`), not links. Meta's app review needs a public privacy policy URL and a data-deletion URL for Instagram and Facebook login. Claims such as "GDPR / Nepal Telecomm Ready" and "Meta Graph v21.0 Compliant" (`:289,287`) should not ship unverified.
- **Deployment to verify:** `middleware.ts:3` reads `process.env.BACKEND_URL` in the edge runtime and falls back to `localhost:8000`. In the container that fallback would fail silently. The `.next` directory in the repo is older than the middleware, so I could not check what was baked in. Run `docker compose up` and `curl localhost:3000/api/v1/tenants/me`. Webhook paths (`/api/v1/webhooks/`) return 404 from Next if nginx does not route them to FastAPI, and there is no nginx in `docker-compose.yml`.
