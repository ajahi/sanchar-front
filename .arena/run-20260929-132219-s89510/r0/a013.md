# Sanchar frontend: review and flow check (Instagram login -> dashboard -> conversations)

## Verdict

The pieces exist: Instagram login link, cookie session, a `/dashboard` page, a conversation list with per-channel filters, and a message pane. Three things break the flow you described.

1. **A tenant who signs in does not land on the dashboard.** Every code path sends them to the inbox at `/`.
2. **Once signed in, there is no way to connect or reconnect Instagram.** The only Instagram button is on `/login`, and the middleware bounces signed-in users off `/login`.
3. **The Channels modal shows invented connection state.** Facebook is "LINKED & ACTIVE", Instagram is "VERIFIED", and "PING WEBHOOKS" always returns "200 OK". Nothing is fetched for them, so a tenant with nothing connected sees green.

What I checked:
- I read `middleware.ts`, `app/*`, `src/App.tsx`, `src/api.ts`, `Header`, `PageHeader`, `SidebarNav`, `InboxFeed`, `RightInspector`, `MetaSettingsModal`, `ProfileModal`, `Footer`, `Loader`, `mockData` (the connection-status part), `app/api/**`, `Dockerfile`, `docker-compose.yml`, `next.config.ts`, `package.json`, `.env.example` and `middleware.ts.bak`.
- I only skimmed `RAGSandboxModal`, `InventoryModal` and `InboundSimulatorModal`, because they are mock-only.
- `npx tsc --noEmit --incremental false` printed no errors. I passed `--incremental false` because `tsconfig.json` has `incremental: true`, and a plain run would rewrite `tsconfig.tsbuildinfo` in your project. The typecheck says nothing about behaviour.
- I did not run the app against your backend. Anything that depends on FastAPI is labelled **[backend]**.

Line numbers refer to the files as they are now.

## A. Flow divergences

### A1. HIGH: sign-in lands on the inbox, not the dashboard

There are three landing paths, and two of them are in this repo:
- The email login ends with `window.location.assign('/')` (`app/login/page.tsx:37`).
- A signed-in visitor to `/login` is redirected to `/` (`middleware.ts:22`).
- The Instagram callback redirect is set by the backend **[backend]**, but the frontend gives strong evidence about it:
  - `app/page.tsx:6-8` says the blank screen appears "right after the Instagram redirect" while the `/` bundle loads, so the callback lands on `/`.
  - The comment at `middleware.ts:21` ("keep ?ig_error= from the OAuth callback") implies the error redirect also lands on a non-`/login` path.

`/` is the inbox (`app/page.tsx` renders `src/App.tsx`). `/dashboard` is only reachable through the header pill.

**Fix that needs no backend change.** Make `/` a redirect to `/dashboard` for signed-in users, and move the inbox to `/inbox`:

```diff

+  // Whatever the backend's OAuth callback redirects to ('/'), signed-in users land on the dashboard.
+  if (hasSession && (isLogin || pathname === '/')) return NextResponse.redirect(new URL('/dashboard', req.url));
--- app/login/page.tsx
-      window.location.assign('/'); // full load so middleware sees the new cookie
+      window.location.assign('/dashboard'); // full load so middleware sees the new cookie
--- src/components/PageHeader.tsx   (lines 37 and 40)
-      setActiveTab={(tab) => router.push(tab === 'inbox' ? '/' : `/?tab=${tab}`)}
+      setActiveTab={(tab) => router.push(tab === 'inbox' ? '/inbox' : `/inbox?tab=${tab}`)}
-      onOpenNewInboundModal={() => router.push('/?tab=inbound')}
+      onOpenNewInboundModal={() => router.push('/inbox?tab=inbound')}
--- src/App.tsx   (line 118)
-    if (tab) window.history.replaceState(null, '', '/');
+    if (tab) window.history.replaceState(null, '', '/inbox');
```

Also do `git mv app/page.tsx app/inbox/page.tsx` and change its imports from `../src/...` to `../../src/...`. This move also frees `/` for the public landing page you will want for SEO (section E).

Once the backend redirect points at `/dashboard`, the `pathname === '/'` clause is only a safety net. Keep it anyway.

### A2. HIGH: Instagram cannot be connected or reconnected after sign-in

`INSTAGRAM_LOGIN_URL` is used in exactly one place, the button at `app/login/page.tsx:188`. A signed-in user cannot reach `/login`, because of `middleware.ts:22`. This leaves two dead ends:
- **A tenant who registered by email has no Instagram button anywhere.** `ProfileModal` then says "No Instagram account connected yet" (`ProfileModal.tsx:118`) with no action.
- **The stale-profile message tells the user to do something impossible.** `ProfileModal.tsx:68` says "Log in with Instagram again to refresh", but `/login` bounces them straight back.

The "Channels" modal is the natural home for a Connect Instagram action. It already has a WhatsApp connect flow, and the intended flow says a tenant "can directly link or login from their desired social media".

What to change:
- Add `<a href={INSTAGRAM_LOGIN_URL}>Connect Instagram</a>` to the Instagram card. `/api/v1/*` is handled before the session check in the middleware (`middleware.ts:15`), so the link works while signed in.
- Change the `ProfileModal.tsx:68` message to link to the same URL.
- **[backend]** I cannot see what `/social-accounts/instagram/login` does when a session already exists: link to the current tenant, create a new tenant, or swap the session. If it swaps the session, add a separate `link` endpoint. Test this before shipping the button.

## B. Real bugs in the inbox

### B1. HIGH: any failure of `/tenants/me` signs the user out; a failed logout leaves them stuck

- `getMyTenant()` throws for any non-2xx (`api.ts:25`), including a 500, a 502 while the backend restarts, or a timeout.
- Both `App.tsx:61` and `PageHeader.tsx:30` respond by calling `handleSignOut`/`signOut`, which POSTs `/auth/logout` and clears the session. During development, restarting FastAPI logs you out.
- `signOut` is `await logout(); assign('/login')` (`App.tsx:47-50`, `PageHeader.tsx:22-25`). If `logout()` itself rejects (backend down), `assign` never runs and the promise rejection is unhandled. The user is left on a page with a blank header.
- The middleware only tests that the `ns_session` cookie **exists** (`middleware.ts:19`), never that it is valid. If **[backend]** `/auth/logout` needs a valid session and leaves an expired cookie in place, the flow ping-pongs: `/login` -> `/` -> 401 -> logout -> `/login`.
- After mount the 5-second poll (`App.tsx:67-85`) only does `console.error`. An expiring session mid-use produces a silently frozen inbox.

Fix: sign out only on 401, and always navigate:
```diff
--- src/api.ts
+export class AuthError extends Error {}
 export async function getMyTenant(): Promise<Tenant> {
   const res = await fetch('/api/v1/tenants/me');
-  if (!res.ok) throw new Error('Not authenticated');
+  if (res.status === 401) throw new AuthError('Not authenticated');
+  if (!res.ok) throw new Error(`Tenant lookup failed (${res.status})`);
   return res.json();
 }
--- src/App.tsx  (and the same in PageHeader.tsx)
 const handleSignOut = async () => {
-  await logout();
-  window.location.assign('/login');
+  try { await logout(); } finally { window.location.assign('/login'); }
 };
-      .catch(handleSignOut);
+      .catch((e) => (e instanceof AuthError ? handleSignOut() : console.error(e)));
```
Give `listConversations` the same 401 check (`if (res.status === 401) throw new AuthError(...)`), and have the poll call `handleSignOut` on it. Also add a visible "connection problem" banner when the poll fails several times in a row.

### B2. HIGH: thread status is derived wrongly, so "NEEDS HUMAN" is unreliable

`api.ts:102`: `status: c.mode === 'ai' ? 'AUTO_PILOT' : 'NEEDS_HUMAN'`.
- Any `mode` other than the literal `'ai'` (for example `'human'`, `'manual'`, `'paused'`) is shown as an emergency: a pulsing red banner "! ALERT: HUMAN ESCALATION REQUIRED !", "HIGH PRIORITY", and a count in the INBOX badge. `InboxFeed.tsx:273` then invents a reason: "Customer requested human manager or AI confidence fell below threshold."
- `c.status` is read into the DTO (`api.ts:62`) but never used. Closed or resolved conversations stay in the list and in the "ACTIVE" count.
- I cannot see the backend enum **[backend]**. Map explicitly against the real values, and use `c.status` to filter or label resolved threads.

### B3. HIGH: "Take over as human" and "Resolve & re-enable AI" do nothing that lasts

`handleToggleTakeover` (`App.tsx:122-139`) only edits local state. The next poll (within 5 seconds) rebuilds each thread from the server (`App.tsx:74`: `fresh.map(t => ({ ...t, messages }))`), which puts `status` back to the server's `mode`.

The real risk is worse than the visual revert. After clicking "TAKE OVER AS HUMAN" the operator believes the AI is paused. If the backend never learned that, the AI can keep auto-replying to the same customer while the operator types. Whether sending a human reply flips the conversation to manual mode is **[backend]**.

Fix: add an endpoint such as `PATCH /conversations/{id}` with `{mode}`, call it from `handleToggleTakeover`, and update state from the response. Until it exists, hide both buttons rather than show controls that do not work.

### B4. MEDIUM: the send box discards the draft on failure, and Enter during IME composition sends

- `InboxFeed.tsx:96-100`: `onSendMessage(...)` returns a promise that is not awaited, and `setInputText('')` runs immediately. If the send fails (Instagram rejects messages outside the 24-hour window, or the token expired), `App.tsx:155` shows a browser `alert()` and the operator's text is gone.
- There is no in-flight state, so a double click or repeated Enter sends twice.
- `handleKeyDown` (line 102) sends on any Enter. Users typing Nepali through an IME press Enter to commit composition, and that would send a half-written message. Guard with `!e.nativeEvent.isComposing`. I did not test this with an IME, but the guard is standard.

```diff
--- src/components/InboxFeed.tsx
-  const handleSend = () => {
-    if (!inputText.trim()) return;
-    onSendMessage(inputText.trim(), 'human');
-    setInputText('');
-  };
+  const [sendError, setSendError] = useState<string | null>(null);
+  const [sending, setSending] = useState(false);
+  const handleSend = async () => {
+    const text = inputText.trim();
+    if (!text || sending) return;
+    setSending(true); setSendError(null);
+    try { await onSendMessage(text, 'human'); setInputText(''); }
+    catch (e) { setSendError((e as Error).message); }   // keeps the draft
+    finally { setSending(false); }
+  };
--- src/App.tsx (handleSendMessage: remove the try/catch and alert so the error reaches InboxFeed)
```
Change `onSendMessage`'s type to return `Promise<void>`. Render `sendError` next to the input.

## C. Dashboard

The page is `app/dashboard/page.tsx`, backed by `GET /api/v1/dashboard?days=1`.

1. **Only counts.** It shows four blocks of counts (new, top queries, handled, handover) for a fixed window (`api.ts:129`, default `days = 1`; the page never passes anything else). "Dashboard with all the metrics available" is not met: there is no range selector, no refresh, no trend, and the Instagram profile stats (followers, media count) that the backend already returns to `ProfileModal` are not shown here.
2. **Zero-wall for new tenants.** `LABELS` (lines 8-12) always renders WhatsApp, Instagram and Facebook rows. A tenant who just connected Instagram sees zeros for two channels they cannot use. Show only connected channels, and add an empty state ("No messages in the last 24 hours" plus a link to the inbox or Channels).
3. **Two numbers under one label.** The INBOX badge on the dashboard is the sum of `handover` counts over the window (`page.tsx:41`). In the inbox it is the count of threads currently in `NEEDS_HUMAN`. The same badge means different things on the two pages.
4. **Unvalidated response.** `counts[ch]` (line 22) renders `undefined` if the backend omits a channel key. `top_queries` uses `q.text` as the React key, so duplicates warn.
5. **Errors.** A 401 is handled indirectly, because `PageHeader` fires its own `getMyTenant` and signs out. A 500 shows the bare text "Failed to load dashboard (500)" with no retry.
6. **Loader hides the header.** While loading, the full-screen `Loader` covers the header (`Loader.tsx`, `fixed inset-0 z-50`), so navigation is unavailable until the dashboard responds.

## E. SEO and Meta app review

**Current state**
- Only `/login` is a real public page. `/` redirects a logged-out visitor to `/login` (`middleware.ts:21`), so the login page becomes your indexed homepage.
- Metadata exists only in `app/layout.tsx`: one title and description for every page. `login/page.tsx` is a client component, so it cannot export its own metadata. Put a `layout.tsx` with `metadata` in `app/login/`.
- `twitter: summary_large_image` and `openGraph` have no image or URL, so shared links show no card.
- There is no `app/robots.ts`, `app/sitemap.ts`, favicon (`/favicon.ico` is excluded from the middleware, but the file does not exist, so it 404s), canonical link or structured data. `public/sanchar-mailbox.svg` is unused. Serve it as `app/icon.svg`.
- Fonts are loaded from five Google families through a `<link>` in `<head>` (`layout.tsx:21-24`). That is render-blocking, and it sends visitor IPs to Google while the page claims "GDPR ready". Use `next/font`.

**The middleware blocks static and SEO files.** `middleware.ts:27` no longer excludes paths with a file extension (`middleware.ts.bak:24` did). For a logged-out visitor or crawler, `/robots.txt`, `/sitemap.xml`, images and anything under `/public` redirect to `/login`. Use this matcher:
```diff
-  matcher: ['/((?!api|_next|favicon.ico).*)', '/api/v1/:path*'],
+  matcher: ['/((?!api/|_next/|.*\\..*).*)', '/api/v1/:path*'],
```
The `api/` with a slash also stops the exclusion from matching unrelated paths such as `/apikeys`.

**Public pages need an allowlist.** Meta's app review requires a privacy policy URL and, for Instagram and Facebook login, a data-deletion URL or callback. The links at `login/page.tsx:246-248` are plain `<span>`s. When you build `/privacy`, `/terms`, `/data-deletion` and a public landing page, they must be allowed through `middleware.ts:21`. As written, a reviewer or crawler sees a redirect to `/login`. Something like:
```ts
const PUBLIC = ['/login', '/privacy', '/terms', '/data-deletion'];
const isPublic = PUBLIC.includes(pathname);
if (!hasSession && !isPublic) ...
```
Also add `robots: { index: false }` in the metadata of `/dashboard` and `/inbox`.

**Claims to review before Meta review or public launch.** These are on the public login page: "FREE FOREVER FOR CORE FEATURES" (line 92), "GDPR / Nepal Telecomm Ready" and "Meta Graph v21.0 Compliant" (lines 287-289), and "ESTD. 1932" (line 71). Keep them only if they are true.

## G. Backend-dependent items to confirm (I could not see FastAPI)

1. Where the Instagram callback redirects on success and on error. The frontend hints say `/`; A1 is fixed either way.
2. What `GET /social-accounts/instagram/login` does when a session already exists (A2).
3. The values of `conversation.mode` and `conversation.status`, and whether a human send flips `mode` (B2, B3).
